# バージョンと公開の方針

製品バージョンはルートの`Cargo.toml`で管理し、`--version`にも使います。最新の公開版は`0.19.1`です。マニフェストに番号があるだけでは、公開済みとは限りません。Google API、SDK、カタログスキーマの番号とは別です。

[English](../en/release-policy.md) ·
[実装状態の原本](../../compatibility/features.json)

公開できる版は`MAJOR.MINOR.PATCH`と`MAJOR.MINOR.PATCH-rc.N`です。
`N`は1から始め、すべての数値に先頭の0を付けません。
ほかのプレリリース形式とビルドメタデータは受け付けません。
候補番号は数値順に並び、同じ製品バージョンの正式版はすべての候補より後になります。

## 0.xで機能を追加する

互換対応を続けながら、使える機能を順次公開します。
機能を追加しても、すべて終わるまで公開版を`0.1.0`のままにする方針ではありません。

| 変更 | バージョンの更新 | 例 |
| --- | --- | --- |
| 互換性を保つ不具合・セキュリティ修正 | patchを上げる | `0.1.0`→`0.1.1` |
| 機能追加・非推奨化 | minorを上げ、patchは0 | `0.1.1`→`0.2.0` |
| 互換性を壊す変更 | minorを上げ、patchは0 | `0.2.1`→`0.3.0` |

たとえば初回公開後、初期化を`0.2.0`、互換修正を`0.2.1`、同期を`0.3.0`にできます。
番号の予約ではありません。seed拡張やデータ移行も、同期を待たず別のminorで公開できます。
並列開発した機能は、統合時に実際の公開範囲に合わせて番号を決めます。

最後の公開版との差分から、必要な最大の更新幅を選びます。
コミットやpushごとの更新は不要で、文書だけの変更にも製品リリースは不要です。
依存やベースイメージの更新も、利用者に見える影響で同じように判断します。

patchでは、文書化した契約を守ります。
Google仕様へ合わせる修正でも、利用者の設定変更やデータ移行が必要なら互換破壊です。
CLI、環境変数、設定形式・既定値、対応API、実行環境、永続データを互換性の対象とします。
内部関数や診断文の細かな表現は、安定インターフェースに含めません。
`worker_threads`、`max_blocking_threads`、`catalog_wait_timeout_ms`、`memory_catalog_max_bytes`は調整用の設定です。名前と値の範囲は対象ですが、値がプロセスに与える効果は対象外です。

4つの既定値は認証の設定に従い、その決まり方も対象です。
`cors_fallback`はpermissiveで`allow-all`、strictで`none`です。`signed_urls`はそれぞれ`ignore`と`verify`です。
`test_signer`は、permissiveで`signed_urls=verify`のとき、またはstrictのidentitiesが宣言するときに有効で、それ以外は無効です。
`signed_host_port`はテスト署名者が有効なら`lenient`、それ以外は`exact`です。readyはそれぞれの実際の値を伝えます。
何かを有効・無効にする新しい設定は`enabled`か`disabled`を取ります。`admin_enabled`と`sync_delete_guard`は`true`と`false`のままです。

機械が読む出力は、文言ではなく名前を互換性の対象とします。
対象は起動完了イベント（ready）の項目名、診断行のメンバー名、下に挙げるイベント名、終了コード、利用者向けエミュレーター専用ルートの応答項目です。
メッセージ、`fix`の文、そのほか人が読む文字列はどのリリースでも変わることがあります。

- **イベント。** 対象のイベント名は`ready`、`stopped`、`diagnostics`、`data_dir_created`と、`gcs-mimic import`の`import_page`、`import_summary`、`import_complete`です。
  stderrに出るそのほかのイベントは実装の動きを伝えるもので、名前も項目もどのリリースでも変わることがあります。importの`summary`と`page`の中の項目も同じです。
- **readyの値。** 設定を伝えるreadyの項目は、その設定の文書化した値を使います。`transport`は`tcp`か`unix`です。これらの値は対象です。`message`は対象外です。
- **診断。** 診断行のメンバーは`event`、`level`、`diagnostics`で、各要素は`source`、`key`、`fix`と、ネイティブのオプションを伝えるときの`native_args`です。
  `source`の値は対象です。値は`cli`、`environment`、`config`、`tls`、`identity`、`filesystem`、`catalog`、`initializer`、`seed`、`sync`、`import`、`listener`、`runtime`です。コマンドライン、環境変数、設定ファイルに由来する`key`は、渡された名前そのままです。そのほかの`key`は問題の場所を示すもので、対象外です。
- **終了ステータス。** どのコマンドも、成功は0、失敗は1です。

利用者向けのエミュレーター専用ルートは`/_internal/health`、`/_internal/healthcheck`、`/_internal/ready`、`/_internal/config`、`/_internal/objects`、`/_internal/reset`、`/_internal/reseed`、`/_internal/lifecycle/run`です。
メソッド、成功時のステータス、要求と応答のキーは現在の綴りのまま保ちます。
本文を受け取るルートは64 KiB以上の本文を受け付けます。それより大きい本文をあるリリースが受け付けても、約束ではありません。
管理用のルートは、`admin_enabled`が無効の間は404、ブラウザーからの要求には403、承認していないホストには421を返し続けます。エラー本文の`error.code`も保ちます。エラー本文のそのほかのメンバーは対象外です。
`/_internal/delete_all`はfake-gcs-serverのリセットの書き方で、下のフラグと同じく契約の対象外の移行補助です。
`/_internal/sync`のルートは、サーバーと同じバージョンの`gcs-mimic sync`の間の内部プロトコルで、互換性の対象外です。
0.20.0からは、どちらも`x-gcs-mimic-version`ヘッダーで自分のバージョンを送り、別のリリースの相手を両方のバージョンを示して拒否します。
`gcs-mimic sync`コマンドを使ってください。
ディレクトリ同期は未完成なので、`gcs-mimic sync`のオプションと出力も対象外です。対象は終了ステータスだけです。

`--host`、`--port`、`--port-http`、`--scheme`、`--log-level`はネイティブのオプションで、ほかの文書化したオプションと同じく互換性の対象です。
[オプションの別名](../en/slices/option-aliases.md)にあるそのほかのフラグはfake-gcs-server由来の移行補助で、安定契約の対象外です。
それらが置き換わるネイティブの設定は、通常どおり対象です。

`1.0.0`以降、対象の名前や値は2段階で廃止します。
まずminorで非推奨にします。古い綴りは動き続け、起動時に置き換え先を示す`warn`診断を出し、リリースノートに載せます。
次のmajorで削除します。
fake-gcs-server由来のフラグは契約の対象外なので、先に1つ以上のminorで警告していれば、minorで削除することがあります。

[公開契約の見直し](../en/public-contract-review.md)に、これらの決定と、凍結前に`0.x`のminorで必要な変更を記録しています。
それらの変更を公開するまでは、コードは見直しの棚卸しに書いたとおりに動きます。

互換破壊にはリリースノートと移行手順を用意します。
既存のデータディレクトリを黙って初期化・破棄してはいけません。
スキーマ変更は製品バージョンと分け、更新・バックアップ・旧版へ戻す制限を説明します。
ダウングレード互換は前提にしません。

## 1.0.0の条件

`1.0.0`は機能が揃ったという宣言ではなく、互換性の約束です。
上で定めた公開契約を守り、`1.x`の間は文書化した使い方の変更やデータの喪失なしに更新できることを約束します。
対応する機能は記録した範囲のままで、[台帳](../../compatibility/features.json)で`PARTIAL`の行は`PARTIAL`として文書に示します。
次のすべてが必要です。

1. **公開契約を凍結する。**
   CLIのコマンドとオプション、環境変数、設定ファイルの形式と既定値、データディレクトリ、対応APIの範囲と制限を安定面として文書にします。
   最初のリリース候補の前に、残したくない名前・別名・既定値を見直し、残る互換破壊はすべて`0.x`のminorで出し切ります。
   [公開契約の見直し](../en/public-contract-review.md)に、現在の棚卸し、オーナーの決定とそれに必要な変更、残る提案があります。
2. **サポート対象の全リリースのデータディレクトリから更新できる。**
   各リリースが書いたデータディレクトリを新しいビルドで開き、同じバケット、オブジェクト、世代、メタデータ、バイト列を返すことを確かめます。
   フィクスチャは公開イメージから`scripts/released-data-fixtures.sh`で作り、`tests/it_import_seed/released_data_upgrade.rs`で検証します。
   正式版と各リリース候補に、それぞれdigestを固定したフィクスチャを追加します。
   候補も更新元としてサポートし、後続の候補で互換破壊があっても、最終版は各候補のデータディレクトリを開ける必要があります。
   xtaskの版検査テストは次の候補・正式版へ進む前に過去の公開版のフィクスチャを要求し、統合テストは全フィクスチャが登録され、内容を保って開けることを検証します。
   サポート対象は`0.8.0`以降です（[撤回したリリース](#撤回したリリース)）。
3. **リリース候補を寝かせる。**
   `1.0.0-rc.N`を公開し、互換破壊なしで14日以上置きます。
   互換破壊を入れたら、新しい候補からやり直します。
   候補のコンテナタグは完全なバージョンだけを公開し、`1.0`、majorの別名、`latest`などの浮動タグを動かしません。
   浮動タグの更新対象は正式版だけで判断します。GitHubではプレリリースとして公開し、最新リリースにしません。
   公開レシピは同じソースのイメージと組にするため、既定のイメージを候補の完全なタグに固定します。READMEのクイックスタートが使う`latest`は正式版のままです。
4. **最終ソースで1回検証する。**
   ネイティブ、クロスターゲット、SDK、コンテナ、ブラウザーの検証をリリースするコミットで実行します。
   以前の検証結果では代用しません。
5. **移行範囲を明記する。**
   [fake-gcs-serverの移行ガイド](../en/fake-gcs-server-migration.md)に、対応する移行手順と固定参照版との残る差分を書き、完全な代替とは主張しません。

固定したfake-gcs-server参照版の完全な機能上位互換は、引き続き目標として[完全上位互換の判定](../en/fake-gcs-server-migration.md#delivery-and-full-superset-gate)で追跡します。
`1.0.0`の条件ではありません。
「完全な上位互換」という表現は、その判定を満たしたリリースから使います。
Google Cloud Storage API全体への対応も別の目標です。

`1.0.0`以後は、互換破壊でmajor、互換性のある追加でminor、修正でpatchを上げます。

## 撤回したリリース

`0.1.0`から`0.7.0`は2026-11-02に撤回しました。
使える公開契約ができる前のリリースで、公開を続けると想定外の利用を招くためです。
GitHub Release、ネイティブアーカイブ、GHCRとDocker Hubの固定バージョンのタグとminorエイリアスを削除しました。
Gitタグと[英語のリリースノート](../en/releases/)は、ソースの履歴として残します。

これらのリリースが書いたデータディレクトリはサポートしません。
現在のビルドで開ける場合もありますが、更新は未検証です。
空のデータディレクトリから始めるか、seedし直してください。
この撤回は、`1.0.0`の前に一度だけ行う、公開物の不変ルールの例外です。

## 公開版の一貫性

Gitタグは`vX.Y.Z`または`vX.Y.Z-rc.N`で、バイナリ、アーカイブ名、コンテナの固定タグにも`v`を除いた同じ版を使います。
同じ製品バージョンとソースコミットに対応させます。
公開準備時にはマニフェスト、lockfile、Goパッケージの`moduleVersion`、利用例、リリースノート、成果物の参照を
まとめて更新します。利用例やGoパッケージが別のバージョンを示すと、`scripts/check-release-recipes.sh`が失敗します。ローカルの確認用イメージは公開版ではありません。

公開したタグ、バイナリ、固定バージョンのイメージは置き換えません。
依存やベースイメージだけの修正・再ビルドでも、新しい版として公開します。
各公開版にchecksumとイメージdigestを記録します。

コンテナの`latest`タグは、majorをまたいだ最も新しい安定版です。新しいmajorを公開すると動きます。
`1.0.0`からは、`1`のようなmajorの別名が1つのmajorの系列を追い、`X.Y`と同じ規則でその系列の安定版ごとに進みます。
`0.x`のminorは互換性を壊すことがあるので、`0`の別名は公開しません。

初回`0.x`の範囲は[ロードマップ](roadmap.md#公開と100)に示します。
公開には、対象環境のCI、配布物のビルドに使う依存の最新性、検証済みの利用手順、ライセンス同梱、
checksumと公開先からの取得確認が必要です。ワークフローの設定だけでは満たしません。
現在のイメージ公開手順はネイティブリリースの成功後に進み、
公開操作自体には別途の承認が必要です。
詳細は[英語の公開手順](../en/container-distribution.md)を参照してください。
