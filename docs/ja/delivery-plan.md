# 並列開発と受け入れ条件

<!-- markdownlint-configure-file {"MD013": {"tables": false}} -->

Dockerでの導入と既存用途の移行を優先し、別々に検証できる仕事を並行して進めます。
このページは担当境界の要約です。機能状態を変更するものではありません。

## 着手の前提と担当境界

| 優先度 | 担当する範囲 | 着手に必要な前提 |
| --- | --- | --- |
| 最優先 | 配布・公開手順・利用ガイド | 既存APIと公開の判定条件 |
| 最優先 | CLI・環境変数・URL・Hostルート | 変更する設定の契約 |
| 次 | 共通状態の統合 | 既存バケット・保存処理 |
| 次 | 初期設定ファイルの読込・初期化 | 共通更新処理・ファイル形式 |
| 次 | 監視・再走査・書戻し | 共通更新処理・同期仕様 |
| 次 | seed・既存データの読込 | 対象保存形式・既存取込処理 |
| その後 | Rails・参照版の残機能 | 個々のAPI・プロファイル契約 |
| 最終判定 | リリース統合 | 全参照機能・移行・追加機能 |

配布はRails・初期化・同期の完成を待ちません。
現在の公開手順では、ネイティブリリースと環境別検証も必要です。
イメージをローカルで動かしただけでは、公開レジストリからの取得確認を満たしません。
seedや移行用の読込処理も、監視機能の完成を待ちません。

## 初期化と同期で共有する契約

バケットとprojectの識別、strictでの初期化権限、起動順、復旧後のreadiness、
メモリ使用量を制限した更新・公開処理の入口を先に固定します。
初期化と監視は、その入口を使う別々の処理として作れます。
公開ホスト設定全体を前提にはしません。

共通カタログ、スキーマ、公開処理の変更は、1人の統合担当が管理します。
各担当は自分の読込・監視処理とテストを編集し、共通変更は統合担当へ提案します。
SQLiteを直接書き換えて、条件、hash、世代、履歴、復旧処理を迂回しません。
並列で調査・実装しても、統合は小さな単位で検証します。

## 完了の判定

**設定**は19変数の対応表を使い、待受、API応答用URL、公開URL、Hostルートを分けます。
ホスト・別コンテナ・ブラウザーからの接続、再開URL、最終URLへの署名を確認します。
同時待受、保存モード、通知、location、ログは個別の範囲で実装します。
設定を受け付けて無視するだけでは完了にしません。

**初期化**は、形式のバージョンとCLIを決め、全入力を変更前に検証します。
重複名と未対応設定を拒否し、未作成バケットだけを作ります。
異なるCORS・versioning、API変更、繰り返す起動、項目の削除、
途中停止からの再実行でも、既存設定とオブジェクトを失わないことを確認します。

**同期**は競合、名前、属性の管理主体、反映時間を先に決めます。
両方向の作成・変更・削除・renameに加え、部分書込、一時ファイル、自己通知、
通知欠落、制限付き再走査、ディスク不足、途中停止からの復旧を確認します。
履歴を保持し、競合や失敗を利用者に伝えます。監視だけで完了とはしません。

**seed・移行**は`/data`と`/storage`を区別し、MIME、バケット属性、
xattr・サイドカーの読込契約を固定します。移行元は読取専用にし、別の保存先へ移します。
保持できないACL、履歴、識別子はエラーとして報告します。
現在のファイルだけを移す機能を、完全な無損失移行とは呼びません。

**参照版の残機能**は全ソース調査後、ACL、JSON/XML、batch、内部ヘルパー、
イベント、Storage v1 gRPC、Go組み込み、両保存方式の使い方を個別に検証します。
既存HTTPのSDK・ブラウザー確認は継続できます。
Railsも前提機能は実装済みで、独立した担当がいれば早く進められます。

## 統合と記録

対象プロトコル、フィールド、制限、対象外を決めてから、正常・異常・境界・権限・
競合・再起動の受け入れ条件を固定します。必要なwire、固定SDK、
コンテナ、利用手順で確認し、コマンドと結果を証跡へ残します。

範囲内の失敗を直した後、該当する機能IDだけを台帳で更新します。
APIメソッド全体が`PARTIAL`でも、範囲を固定した振る舞いが完了する場合はあります。
台帳の`PARTIAL`を半分として数えたり、計画から進捗率を作ったりしません。

履歴上のP0〜P7は機能分類で、グループ全体の完了待ちを求める順序ではありません。
既存の完了範囲・個別証跡・全依存は[英語の詳細計画](../en/delivery-plan.md)に保持します。
`1.0.0`は[バージョン方針](release-policy.md#100の条件)の全条件を満たして判定します。
途中の機能追加は別々の`0.x`minorで公開でき、日付や機能別の番号は予約しません。
