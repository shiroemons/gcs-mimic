# 起動フェーズと中断

<!-- markdownlint-configure-file {"MD013": false} -->

対象はDESIGN-062、DESIGN-072、DESIGN-074です。各機能の広い範囲はPARTIALのままです。UX-002の初期ファイル読み込み後にreadyを出す範囲はIMPLEMENTEDを維持します。[英語の契約](../en/slices/startup-phases.md)と[共有契約](../en/slices/onboarding-state-contract.md)を正本とします。

設定・TLS・IDレジストリを検証した後、カタログのopenと復旧、PAP、バケット初期化、seed、bind、保守処理の開始、readyの順に進みます。ready JSONの既存フィールドに`buckets`の適用結果を加えます。

同期ディレクトリを設定した起動では、同期ワーカーの起動に成功してからreadyを出します。readyの`healthcheck_path`とCLIの既定プローブ先は`/_internal/healthcheck`で統一し、従来の`/_internal/ready`も引き続き使えます。TLSとIDレジストリの起動エラーには、秘密のトークン値を出さずに原因を表示します。

0.18.0以降、readyの固定値だった`protocol`と`gcs_api`を削除します。これらを読むスクリプトでは参照を削除してください。ディスク方式では、開いた保存先を絶対パスの`data_dir`で表示し、シンボリックリンクは解決せず指定した名前を残します。`data_dir_state`は、その起動でカタログを初期化した場合が`created`、既存のカタログを開いた場合が`opened`です。メモリ方式では両項目を省略します。既定の保存先は引き続き、作業ディレクトリからの相対パス`data`です。

ディレクトリが存在していても、カタログがなければ`created`です。初回起動が空のDBを作った段階で中断された場合も、次回に初期化すれば`created`になります。初期化が確定済みなら、初回ready前に強制終了していても次回は`opened`です。新規初期化時だけ、stderrにinfoレベルの`data_dir_created`を1件出し、`data_dir`とメッセージに絶対パスを含めます。通常のログレベル設定に従い、後続の起動処理が失敗してもこの通知は残ります。UTF-8で表せないパスは、両イベントの表示だけ置換文字に変え、実際の保存先には元のパスを使います。判定には既存のopen処理が調べたスキーマ版を使い、追加のディレクトリ走査やリクエスト中のファイル参照は行いません。[プロセステストの結果](../en/evidence/ready-event.md)を参照してください。

実行環境のシグナル登録後は、非同期のbind前処理全体をshutdownと競わせます。復旧中に停止要求を受けた場合は、既に開始した復旧が完了してからカタログを閉じます。PAP・seed中は新しい要求を止め、既に開始した書き込みと片付けが終わるまで待ちます。PAP・bindの失敗でも明示的にcloseします。停止要求ではロックを解放してからstoppedを出し、失敗時はreadyを出さず非ゼロで終了します。

strictモードの組み込みID（信頼済みリスナーのアプリと、テスト署名者）は、バケット文書が作るバケットのprojectで暗黙のロールを持ちます。IDレジストリは設定の検証中に読み込むため、このときに限り、バケット文書を設定の段階で一度だけ読み、1つのJSON値として解析します。読めない、大きすぎる、またはJSONとして壊れている文書は、カタログを開く前に、初期化と同じ診断で起動を止めます。設定はその本文を保持し、初期化の検証ジョブはファイルを読み直さずに同じ本文を検証します。これにより、起動中にファイルが変わっても、暗黙のロールのprojectと作成するバケットは同じ版から決まります。

中断できる待機をCancelSafe型で明示し、PAP・初期化・seed・bindを個別にshutdownと競わせます。これはレビュー用の目印で、コンパイラが中断安全性を証明する型ではありません。初期化の読込・検証ジョブはカタログを持たず、中断後に書き込めません。投入済みの管理用SQLはカタログが所有し、closeで完了を待ちます。検証中の本番起動経路を中断するテストも追加しています。ReadyEvent・SeedOutcome・InitOutcomeを型で定義し、初期化結果をreadyに含めます。

seed中のSIGTERM、復旧・PAP中の中断、PAP・bind失敗後の解放、ready前のプローブ失敗、再起動後のデータ保持をテストしています。64 MiBの本文を使い、stagingへの転送中とrename後・commit前にも停止させます。停止後はstagingが空で、blobファイルと確定済みの参照が一致し、再起動で収束することを確認します。起動時間は[測定証跡](../en/evidence/startup-phases.md)を参照してください。

非同期の起動中にshutdownを受け取ると、stderrにstoppingを出してから処理をdrainします。テストはこの受信確認後にロック保持を確かめます。起動前後のclose失敗は共通の診断合成を使い、元の失敗とcloseの種類・原因を残します。

起動失敗時もstderrはJSONLで、1行につき1イベントです。`data_dir_created`の後に`diagnostics`が出る場合もあるため、stderr全体を1つのJSONとして読まず、各行を解析して`event`名で選んでください。

復旧中のshutdownは復旧が完了するまで上限なく待ち、2回目のシグナルによる短縮もしません。起動時間の実測値はshutdown待ち時間の上限ではありません。復旧処理の中身、公開済み本文の保護方式、スキーマは変更していません。設定・TLS・IDレジストリの検証は従来どおりシグナル登録前の同期処理です。このスライスのWindows/Linux実行、コンテナ・SDK通し確認、電源断、cgroupメモリ、cold cacheは未検証です。
