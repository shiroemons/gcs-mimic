# Storage v2 gRPCのバケット操作

対象はRPC-STORAGE-001〜004、BEHAVIOR-RPC-001とAUDIT-008のバケット部分です。下の「2026-11-18のバケットの変更」は、UpdateBucket・LockBucketRetentionPolicy・SetIamPolicy（RPC-STORAGE-005・007・009）とBEHAVIOR-RPC-002のバケットのケースも扱います。正本は[英語の契約](../en/slices/grpc-v2-buckets.md)、状態の正本は`compatibility/features.json`です。

`grpc_listen`を設定したサーバーへ`STORAGE_EMULATOR_HOST_GRPC`を向けると、通常のGo `storage.NewGRPCClient(ctx)`でバケットの作成・取得・一覧・削除を利用できます。JSONと同じカタログを使うため、相互に作成したバケットが見えます。新しい設定はありません。

CreateBucketの保持・soft delete・PAP・CORS・Autoclassは共有の型付き検証を再利用します。
作成全体の共有型は未整備のため、残りの作成項目にはJSON insertパーサーを使い、PARTIALを維持します。UpdateBucketは共有更新型を直接作ります。

名前は`projects/_/buckets/NAME`です。作成時のparentは空または`projects/_`、所有projectは`bucket.project`に`projects/<id>`で指定します。全Storage v2 RPCは共通入口（`src/grpc/v2/routing.rs`）で`x-goog-request-params`を読み、必須とします。メタデータがない、または空の値だけの呼び出しは、理由`GRPC_INVALID_X_GOOG_REQUEST_PARAMS`のINVALID_ARGUMENTです。Cloud Storageは、問われたすべてのRPCでこう答えました（GetObject・GetBucket・ListBuckets・WriteObjectはケース`grpc-probe-routing`、さらに16件はケース`grpc-probe-inferred-routing`、どちらも2026-11-18に記録）。BidiReadObjectは問うておらず、ほかと同じ扱いです。QueryWriteStatusとCancelResumableWriteは、まずupload IDの形を調べ、読めるIDにはメタデータを求め（記録済み）、その後でIDが指すバケットとメタデータのバケットを照合します（セッションと別のバケットを指す場合は記録済み）。この照合は認証と認可のあとに行うため、権限のない呼び出し元は何を指定しても同じ拒否になります。この順序はローカルな選択です。再開するWriteObjectとBidiWriteObjectも、セッションのバケットを同じ方法で照合します（この2つのRPCからの推定です）。

呼び出しは、どのRPCでも、いずれかのRPCが照合するキー（`bucket`・`source_bucket`・`project`・`appendable`）のペアをすべて1回ずつ読みます。値はそのキーの形でなければなりません。`bucket`は`projects/_/buckets/<id>`のリソース名で、違えば理由`GRPC_INVALID_X_GOOG_REQUEST_PARAMS_INVALID_BUCKET_FORMAT`です（値のない`bucket`のペアと、ListBucketsで正しい`project`に添えた素のバケットIDも同じで、記録済み）。`project`は`projects/<id>`で、ほかの形は不正なprojectの名前としての文言で拒否します。同じキーを2回送ると、値が同じでも理由`GRPC_INVALID_X_GOOG_REQUEST_PARAMS_DUPLICATE_ENTRY`で拒否します（`bucket`で記録済み）。そのうえで、そのRPCが照合するキーだけを比べます。`bucket`（リクエストのバケット。バケットを指さないメタデータは空の名前を指すものとして比べます。記録済み）、`project`（CreateBucketとListBuckets。理由`GRPC_INVALID_X_GOOG_REQUEST_PARAMS_PROJECT`で、ListBucketsで記録済み）、`appendable`（書き込み）、RewriteObjectでは`source_bucket`、続いて宛先の`bucket`で、どちらも別の理由を返します（記録済み）。リクエストと異なるバケットは理由`GRPC_INVALID_X_GOOG_REQUEST_PARAMS_BUCKET`で、両方のバケットIDを示します（記録済み）。未知のキー、`routing_token`、未知のキーの不正なペア、末尾の`&`、パーセントエンコードしたキーは無視します（記録済み）。そのRPCが照合しないキーも同じで、Goの`direct_connectivity_diagnostic`もこれに当たります。ストリーミングは最初のメッセージ、rewrite継続はtokenの名前と照合します。値はフォームのパーセントデコードをします。ルーティングがカタログの選択や認可を変えることはありません。バケット名はbucket・object両方のRPCで設定済みの互換プロファイルに従います。

記録がないためローカルな選択なのは、不正な`source_bucket`や`appendable`、`bucket`以外のキーの重複、記録では不正な親と並べたときだけ拒否した、routedな`project`単独の拒否、ListBucketsとCreateBucketでprojectを指さないメタデータ（呼び出しは受け付けます）、不正な名前へのstatus（SPEC-GRPC-ROUTING-NAMES）です。固定するテストは`routing_requires_the_metadata`・`routing_compares_each_field_with_its_own_rule`・`routing_validates_every_routed_key_whichever_rpc_is_called`・`routing_refuses_a_duplicated_key`・`routing_skips_malformed_pairs_under_unknown_keys`・`upload_routing_is_compared_once_the_upload_id_is_read`・`routing_compares_only_the_appendable_flag_of_a_resumed_write`・`grpc_names_follow_the_configured_bucket_profile`です。これらのチェックに対するGoとRustのgRPC SDKでの確認は、2026-11-18に成功しました（BEHAVIOR-RPC-001）。

作成時はlocation、storage class、labels、CORS、versioning、default event hold、retention、soft delete、IAM設定の共有JSON検証を使います。保持期間の小数部は、protoのとおり秒単位に切り捨てます（UpdateBucketと同じです）。1秒未満の期間は期間なしとなり、INVALID_ARGUMENTを返します。protoがOUTPUT_ONLYとするフィールド（`bucket_id`・`metageneration`・`location_type`・`create_time`・`update_time`・`owner`とAutoclassの`toggle_time`・`terminal_storage_class_update_time`）は、`google.api.field_behavior`の定めどおり無視し、サーバーが決めた値を返します。Autoclassは[共有の設定規則（英語）](../en/slices/bucket-autoclass-storage-class.md)に従います。object retentionは`enable_object_retention`で有効にします（[SDK互換（英語）](../en/slices/grpc-v2-sdk-parity.md)）。read maskでは`etag`・`autoclass`・`lifecycle`・`object_retention`も選べます。未対応の意味を持つ設定・read maskは`UNIMPLEMENTED`です。取得・削除のメタ世代条件、prefixとページング、非空バケットの削除拒否に対応します。非空バケットの削除は FAILED_PRECONDITION`The bucket you tried to delete is not empty.`、単独で失敗するnot-match条件は FAILED_PRECONDITION`The resource you requested has not been modified according to the condition you specified.`です（どちらも2026-11-18に記録）。小数を含むsoft deleteの期間は、INVALID_ARGUMENT`Invalid argument.`と`BadRequest`を返します（UpdateBucketで記録。CreateBucketは同じヘルパーを使い、作成の応答自体は、ハーネスがバケットを作れないため記録がありません）。strictでは共有認可を使い、保護されたバケットへの未認証アクセスは`UNAUTHENTICATED`、登録済みprincipalの権限不足は`PERMISSION_DENIED`になります。`allUsers`で許可されたGet/DeleteはJSONと同様に匿名でも成功し、公開アクセス防止も共有の判定に従います。

課金先を指定する`x-goog-user-project`は、2026-11-13から全Storage v2 RPCで無視します（空値も含みます）。JSONの`userProject`も同じく無視します（SPEC-SDK-UNSUPPORTED）。gcs-mimicのバケットではRequester Paysを有効にできないため、課金先が結果を変えることはありません。

projectはIDでも、バケットが返す番号でも指定でき、ListBucketsのページトークンはどちらの書き方でも続きます（BEHAVIOR-COMMON-014）。Storage v1とオブジェクトの転送方式間検証は対象外です。残りの作業は下の台帳のケースのとおりです。AUDIT-008はPARTIALを維持します。性能測定・コンテナ・実クラウド検証は対象外です。

2026-10-28に、型検査、gRPCユニット8件、Goの担当・foundationテスト、最終の`RUST_TEST_THREADS=8 just check`と`just check-sdk`が成功しました。HTTPプロファイルのため、既存のGo V2署名HTTPS専用ケースはSKIPです。台帳の6行は確認済みの範囲と未対応を分けてPARTIALとし、英日対応表を再生成しました。

バケットの作成・更新で拒否する設定（`billing`・`custom_placement_config`・`encryption`・`hierarchical_namespace`・`ip_filter`・`logging`・`rpo`・`website`）は保存されないため、`read_mask`で指定でき、未設定として返します。Cloud Storageも、これらを持たないバケットには未設定として答えました（ケース`grpc-bucket-unset-settings-mask`、2026-11-15に記録）。JavaのSDKは既定のバケット読み取りマスクでこれらをすべて指定します。`satisfies_pzs`は意図して拒否します（SPEC-GRPC-UNMODELED-SETTINGS）。Bucketのフィールドでない最上位の名前は、Cloud Storageの文言でINVALID_ARGUMENT`There is no field for this resource named '<path>'.`です（GetBucketとListBucketsで2026-11-18に記録）。`versioning.enabled`のような入れ子のパスはUNIMPLEMENTEDで、Cloud Storageは入れ子のメンバーを受け付け、メッセージにないメンバーや`labels`のキー、繰り返しフィールド`acl`の下位には「フィールドなし」と答えますが、この拒否は宣言済みのローカルな選択です（SPEC-GRPC-LOCAL-CHOICES）。GetBucketはmaskをバケット名の直後、認可と取得の前に検査し、ListBucketsは呼び出し元・プロジェクト権限・`page_size`・`prefix`の後、ページトークンの前に検査します（順序は負の`page_size`が未知のパスより先であることだけが記録済みです）。ListBucketsの負の`page_size`は、理由`GRPC_PAGE_SIZE_MUST_BE_POSITIVE`の`The requested page_size must be positive.`でINVALID_ARGUMENTです（記録済み）。

バケットのリソースは、2026-11-17に記録したCloud StorageのUpdateBucketの応答全体（ケース`bkt-gaps-legacy-class-region`のステップ`grpc-update-bucket-class-regional`）と、Javaの既定マスクでのGetBucketの応答全体（ケース`grpc-bucket-unset-settings-mask`）に、無視するフィールドなしで一致します。バケットのACLと既定のオブジェクトACLでは、バケットのプロジェクトのチームを指すエントリに、プロジェクトIDで書いた`entity_alt`（`project-owners-{id}`）を付けます。オブジェクトのACLと同じです。ほかのプロジェクト番号のチームには付けません。その番号がどのIDを指すかをgcs-mimicは知らないからです。`create_time`と`update_time`は、記録どおりミリ秒までです。保持と論理削除の有効日時、Autoclassの時刻、均一アクセスのロック時刻も、JSONと同じくミリ秒に切り捨てます（Storage v2では未記録の推定です）。保持期間が0の論理削除ポリシーには、JSONと同じく`effective_time`を付けません。

2026-11-14に、バケットのオプションを`grpc_bucket_options_reject_only_what_is_unsupported`で固定しました。CreateBucketの`predefined_acl`・`predefined_default_object_acl`（バケットは作られない）と、GetBucketの入れ子の`read_mask`は、オプション名を含むErrorInfo付きUNIMPLEMENTEDを返します。実機記録（UTC で 2026-11-13、ケース`grpc-unsupported-options`）で、Cloud StorageはListBucketsの`return_partial_success`を受け付け、`*`と名前を混ぜた`read_mask`をINVALID_ARGUMENTで断ると分かったので、gcs-mimicも同じ応答に揃えました。入れ子の`read_mask`もCloud Storageは受け付けますが、gcs-mimicでは記録済みのローカルな拒否として残します。RPC-STORAGE-002・003・004には成功ケース`grpc_unsupported_option_rejections`として記録し、ほかの未完了ケースは変えていません。

## 台帳のケース

2026-11-18 に、台帳の各行を、確かめられる振る舞いごとの受け入れケースに分けました。2026-11-18 に Cloud Storage から記録した応答は、合わせた動作です。Google が定めておらず記録もない応答はローカルな選択とし、固定するテストと合わせて scoped difference に記録します。概要は次のとおりです。

- 意図した拒否（SPEC-GRPC-UNMODELED-SETTINGS の scoped difference）: JSON API も保存しない作成時の設定（`billing`・`encryption`・`logging`・`website`・`custom_placement_config`・`hierarchical_namespace`・`ip_filter`・`satisfies_pzs=true`・`DEFAULT`以外の`rpo`。どれも ErrorInfo 付きで拒否し、バケットを作りません。空のメッセージは設定なしとして受け付けますが、空の`website`だけは拒否します）、GetBucket と ListBuckets の`satisfies_pzs`の read mask、SetIamPolicy の条件付きバインディングと audit config。
- Storage v2 のすべての RPC の行は BEHAVIOR-RPC-001 に依存します。どの RPC もこのルーティングとリクエストのメタデータの検査を通るためです。下の未完了のケースがあるあいだ、各 RPC の行は PARTIAL のままです。
- 宣言済みのローカルな選択（特記がなければ SPEC-GRPC-LOCAL-CHOICES。最初の 3 件は、記録では Cloud Storage が異なる応答をしました。どれも`grpc-probe`ケースの`local_choice`ステップです）: GetBucket と ListBuckets の入れ子のバケット read mask のパスへの UNIMPLEMENTED、UpdateBucket の`*`の update mask への UNIMPLEMENTED、mask が`location_type`を指す UpdateBucket の metageneration（Cloud Storage は 1 から 2 に進めましたが、gcs-mimic は更新が設定を変えたときだけ metageneration を変えます。ケース`grpc-probe-inferred-bucket-masks`のステップ`update-mask-location-type`）。そのほかのローカルな選択: proto が出力専用としていない作成時のフィールド（空でない`etag`、保持と soft delete の`effective_time`、ロック済みの保持ポリシー、均一アクセスの`lock_time`）の拒否、CreateBucket の小数を含む soft delete の期間への応答、DeleteBucket が認可を最初に行うこと、未確定の appendable オブジェクトだけを持つバケットの削除、記録がない LockBucketRetentionPolicy の 0 以下の一致条件の拒否（ハーネスは実バケットをロックしません）、ListBuckets が read mask を検査する順序、記録がないルーティングの形（上記）と、不正な名前への status（SPEC-GRPC-ROUTING-NAMES）。
- 実装が必要なもの: 入れ子のバケット read mask と UpdateBucket の`*`の mask（どちらも Cloud Storage は受け付けます）、UpdateBucket の predefined ACL、CreateBucket の lifecycle・ACL・predefined ACL。
- 判断が必要なもの: サーバーで`grpc-timeout`を適用するか、gzip のメッセージ圧縮に対応するか。

## 2026-11-18のバケットの変更

応答を変えたものは 2 つに分かれます。2026-11-18 に Cloud Storage へ記録した Storage v2 のプローブ（ケース`grpc-probe-bucket-conditions`・`grpc-probe-bucket-masks`・`grpc-probe-routing`。[証跡（英語）](../en/evidence/provider-differential-gap-probes.md#twelfth-recording-storage-v2-grpc-probes)）で、UpdateBucket・DeleteBucket・GetBucket・ListBuckets とルーティングのメタデータを合わせました。これとは別に、proto の規則で、CreateBucket の保持期間の小数部の切り捨てと出力専用フィールドの扱い、両 RPC での正規形でない`Duration`の保持期間の切り捨てを変えました。これらの多くは変更前の応答を既存のテストが固定しており、修正のたびにそのテストをコードと一緒に変えました。

- UpdateBucket は`bucket.etag`を無視します。proto は、`UpdateBucketRequest`のメタデータに含まれる場合は`etag`が一致するときだけ操作する、と定めています（storage.proto の 2581〜2584 行）。しかし Cloud Storage は、古い ETag・現在の ETag・ETag ですらない値のどれを指定した更新も適用しました（記録済み）。更新の条件になるのはリクエストの metageneration 条件だけです（`grpc_bucket_update_ignores_the_bucket_etag`）。
- バケットの metageneration 条件は、GetBucket・UpdateBucket・DeleteBucket で届いた値をそのまま比べます（記録済み）。0 や負の一致条件は成り立たず FAILED_PRECONDITION`At least one of the pre-conditions you specified did not hold.`、0 や負の不一致条件は常に成り立ち、両条件は一緒に評価します。単独で失敗する不一致条件は、3 つの RPC のどれでも FAILED_PRECONDITION`The resource you requested has not been modified according to the condition you specified.`です。共有の Storage v2 の変換がカタログのエラーからこの文言を作ります。旧 v1 サービスは失敗した条件の文言のままです。現在の metageneration と同じ値の不一致条件は、GetBucket と UpdateBucket で記録しました（ケース`grpc-probe-inferred-bucket-masks`のステップ`get-not-match-current`と`update-not-match-current`）。存在しないバケットは条件より先に NOT_FOUND です。リクエストが一致条件だけを持つ LockBucketRetentionPolicy は、記録がないため、0 と負の値を今もバケットを探す前に INVALID_ARGUMENT で拒否します（`bucket_rpcs_keep_their_own_metageneration_condition_rules`）。
- DeleteBucket は、認可、バケットの有無（条件が失敗する場合も NOT_FOUND）、条件、残っているオブジェクトの順に答えます。後ろの 3 つは記録済みです。オブジェクトが残るバケットは`The bucket you tried to delete is not empty.`、単独で失敗する not-match は`The resource you requested has not been modified according to the condition you specified.`です（`delete_bucket_reports_authorization_existence_conditions_then_contents`）。上の保持状態の規則は`delete_bucket_follows_the_shared_catalog_for_retained_state`で固定しています。
- UpdateBucket のパス: Bucket のフィールドを指さないパスは Cloud Storage の文言の INVALID_ARGUMENT です。出力専用のフィールド（`bucket_id`・`metageneration`・`location_type`・`create_time`・`update_time`・`owner`）、識別子と etag（`name`・`etag`）、作成時に決まる設定（`project`・`location`）のパスは、受け付けて何も変えません（すべて記録済みで、ケースは`grpc-probe-bucket-masks`と`grpc-probe-inferred-bucket-masks`。ただし`location_type`の更新の metageneration は異なります。上記）。パスは、フィールドごとに 1 つの設定（`src/grpc/v2/mask.rs`の`FieldSetting`）で分類します。`versioning.<未知>`と`iam_config.<未知>`は INVALID_ARGUMENT`There is no field for this resource named '<path>'.`、空のラベルキー（`labels.`）は`BadRequest`付きの INVALID_ARGUMENT`Invalid user label:  with value . Reason: Invalid field "user_labels_list"; key is empty.`です（すべて記録済み。mask の順で最初に失敗したパスがエラーを決めます）。空または未指定の`update_mask`は、理由`GRPC_MISSING_UPDATE_MASK_FIELDS`の INVALID_ARGUMENT`Invalid update_mask. Requests should specify at least one update field.`です（`output_only_paths_change_nothing_and_unknown_paths_are_invalid`）。受け付けるパスは型付きの`UpdatePath`に一度だけ解析して mask の順に適用し、自分の設定だけを変えます。`*`、mask が受け付けない別のメッセージフィールドのメンバー（`acl.role`、`retention_policy.is_locked`など。上の未知メンバーの規則は`versioning`と`iam_config`だけで、ほかは問うていません）、メンバー付きで指定した出力専用のフィールドは、パスを示す UNIMPLEMENTED です。Bucket のフィールドでない名前は、大文字小文字の違うつづりも含めて、上の未知フィールドの文言で答えます（`update_mask_paths_select_their_settings_and_refuse_the_rest`）。`*`は、Cloud Storage が全体の置換として受け付けた点で、宣言済みのローカルな選択です。
- 小数を含む soft delete の期間は、UpdateBucket で INVALID_ARGUMENT`Invalid argument.`と`BadRequest`を返します（記録済み）。CreateBucket も共有のヘルパーで同じ応答です（`create_rejects_output_fields_and_fractional_durations_in_order`）。以前は UNIMPLEMENTED でした。
- ListBuckets の負の`page_size`は、未知の read mask パスを併せても、理由`GRPC_PAGE_SIZE_MUST_BE_POSITIVE`の INVALID_ARGUMENT`The requested page_size must be positive.`です（記録済み）。
- GetBucket と ListBuckets は、未知の最上位の read mask パスを INVALID_ARGUMENT、入れ子のパスと`satisfies_pzs`を UNIMPLEMENTED で拒否し、順序は RPC ごとです（`bucket_read_masks_refuse_unselectable_paths_in_each_rpcs_order`）。
- ルーティングのメタデータは、上のとおり必須で、リクエストと照合します（ケース`grpc-probe-routing`と`grpc-probe-inferred-routing`）。
- CreateBucket は、上のとおり保持期間の小数部を切り捨て、出力専用のフィールドを無視します（`create_bucket_rounds_retention_nanos_down`・`create_bucket_ignores_output_only_fields`）。UpdateBucket の切り捨ては`grpc_bucket_update_rounds_retention_nanos_down`で固定しました。
- 両 RPC は保持期間を正規化してから切り捨てます。そのため、nanos の符号が seconds と逆の`Duration`や、nanos が 1 秒以上ある`Duration`も、値どおりに切り捨てます。3600 秒と -1 ナノ秒は 3599、0 秒と 1500000000 ナノ秒は 1 を保存し、1 秒と -1 ナノ秒は 1 秒未満なので INVALID_ARGUMENT を返します。以前は nanos を捨てていたため、順に 3600 を保存、拒否、1 を保存していました（上の二つの切り捨てのテストで固定しています）。
- 新たに固定した拒否: SetIamPolicy の条件付きバインディングと audit config（`grpc_iam_set_refuses_conditional_bindings_and_audit_configs`）、CreateBucket の空の`website`、バケットを探す前に`storage.buckets.update`を求める strict の LockBucketRetentionPolicy（`grpc_retention_lock_requires_bucket_update_permission`）。
