# ボトルネックの探し方

[English](../en/performance-investigation.md)

性能調査を始めるときは、先に[調査結果と採否の一覧](../en/evidence/read-optimization-summary.md)を読みます。
試した案、不採用の理由、まだ測っていない候補、再検討する条件をまとめています。
この手順は性能改善のための調査用です。通常の機能追加ごとにベンチマークを要求するものではありません。

## 調べることを一つに絞る

たとえば「10 MiB・並列128のJSONダウンロードでCPU秒/GiBを減らし、単発転送や小さいオブジェクトを悪化させない」と決めます。
コピー量、確保回数、スレッドの起床、システムコール、カタログ処理のうち、どれが減ると考えているかを書きます。

次の条件を揃えます。

| 条件 | 今回の例 | 揃える理由 |
| --- | --- | --- |
| データ | 100個を順番に取得。1 KiB・1 MiB・10 MiB、末尾確認には10.5 MiB | 同じ1個だけではキャッシュの効果が大きく出る |
| 並列数 | 1と128。適応フレームの境界確認には16と17 | 単発と高並列では負荷の性質が違う |
| API | JSONとXMLを別々に測る | ヘッダーやアダプターの処理が違う |
| 実行条件 | ワーカー数、CPU制限、ストレージ、認証、HTTP/TLS | 使ったCPUや機能の違いを速度差と混同しない |
| ログ・監視 | アクセスログとhealthcheckの設定を記録 | リクエストごとの追加処理やCPU集計に影響する |
| キャッシュ | 全実装に同じ起動・キャッシュ準備・ウォームアップを行う | 片方だけ準備を変えると、変更の効果を切り分けられない |

実験専用のデータとコンテナを使い、ビルドやテストは計測前に終えます。
他プロジェクトやself-hosted runnerは、所有者の許可なく止めません。
共有ホストなら、その制約を結果に残します。

負荷クライアントの[元のソース](../en/evidence/read-load-client.go.txt)と、
[ビルド・投入・実行の手順](../en/performance-investigation.md#start-with-a-question-and-a-controlled-workload)も保存しています。
このクライアントはレスポンスの最後まで読みます。終了コードが0でも`errs`が増える場合があるため、両方を確認してください。
ステータスと長さの検査に加え、ハッシュなどで本文が正しいことも別に確かめます。

## まず速度と資源量を測る

プロファイラーを付けずに、同じ負荷を一つずつ実行します。
実装を測る順番を入れ替え、中央値だけでなく各回の値と最小・最大も保存します。
3回の測定だけで小さい差の有意性を保証できるわけではありません。

| 指標 | 分かること | 分からないこと |
| --- | --- | --- |
| RPS・転送量/秒 | 最後まで完了した転送の速さ | どの処理が原因か |
| p50・p95・p99 | 応答時間の分布 | 別々の実行のp99を平均しても、全リクエストのp99にはならない |
| CPU秒/GiB | 同じ量を送るために使ったサーバーCPU | クライアントを含むホスト全体のCPU |
| CPU pressure・throttling | CPUの実行待ちや制限 | 特定のロックや他プロジェクトが原因だという証明 |
| プロセスRSS | プロセスの常駐メモリ | 終了時点の値だけではピークは分からない |
| cgroup memory | コンテナに課金されたメモリやファイルキャッシュ | RSSとは一致せず、共有ページの課金にも偏りがある |

本文の長さが一定で、すべてのリクエストにエラーがない場合の計算は次のとおりです。

```text
受信GiB = 完了リクエスト数 × オブジェクトのバイト数 / 2^30
サーバーCPU秒 = cpu.statのusage_usec差分 / 1,000,000
CPU秒/GiB = サーバーCPU秒 / 受信GiB
CPU pressure（some）% = some totalの差分 / 実際の経過マイクロ秒 × 100
```

5秒間リクエストを開始しても、最後の転送が終わるのは5秒後より遅くなります。経過時間は実測値を使います。
今回のLinux環境では`/proc/uptime`の精度は約10 msでした。`date +%s%N`が高精度とは限りません。
具体的な採取コマンドは[CPU・メモリの確認](../en/performance-investigation.md#account-for-cpu-and-memory-before-attributing-a-cause)にあります。

## CPUを使っている場所を探す

通常の速度測定とは別の実行で、Linuxの`perf stat`、続いて`perf record`を使います。
サーバーと負荷クライアントのcgroupを分け、サーバーを対象に採取します。
複数プロセスのサーバーでは、親だけでなく既に起動しているワーカーも対象にします。

```sh
perf stat -p "$SERVER_PID" \
  -e task-clock,context-switches,cpu-migrations,page-faults \
  -o "$PERF_OUT/counters.txt" -- \
  "$LOADGEN" -base "$BASE" -bucket load-10485760 -objects 100 \
  -size 10485760 -kind media -c 128 -d 10s

perf record -e cpu-clock -F 199 --call-graph dwarf,8192 \
  -p "$SERVER_PID" -o "$PERF_OUT/perf.data" -- \
  "$LOADGEN" -base "$BASE" -bucket load-10485760 -objects 100 \
  -size 10485760 -kind media -c 128 -d 10s

perf report -i "$PERF_OUT/perf.data" --stdio --no-children \
  --sort dso,symbol --percent-limit 0.5
```

変数、観測用コンテナ、権限、シンボル付きビルドの前提は[英語版の実行手順](../en/performance-investigation.md#use-counters-then-cpu-call-stacks)にあります。
未対応のカウンター、失われたサンプル、解決できない関数名、警告を記録します。
今回のVMではハードウェアのcycles/instructionsを使えず、software cpu-clockを使いました。

読み方には次の区別が必要です。

- `self`はその関数自身のサンプルです。呼び出し先を含む割合は重複するため、単純に足せません。
- `copy_to_user`などが大きければコピー処理のCPUコストが見えています。メモリ帯域が飽和した証明にはなりません。
- CPUサンプルには、ロックやI/Oを待って眠っている時間は現れません。
- シンボル付きビルドも、元のreleaseと同一の機械語になるとは限りません。両方のハッシュを残します。
- 採取中のRPSを、プロファイラーなしのRPSと同列に比較しません。

## システムコールと待ち時間で裏付ける

`strace`は、疑った経路を少数のリクエストで確かめるために使います。
本文をログへ出さないよう、対象を絞ってraw引数を記録します。

```sh
strace -f -p "$SERVER_PID" \
  -e trace=preadv2,pread64,writev,sendfile \
  -e raw=preadv2,pread64,writev,sendfile \
  -o "$PERF_OUT/syscalls.txt"
```

アタッチできたことを確認してから、別ターミナルで既知のファイルを1回取得し、本文を検査します。
終わったら観測用のstraceを終了します。速度測定中は動かしません。
必要なら`read`や`write`も対象に加えます。観測対象に入れていない呼び出しは数えられません。

| 症状 | 次に確かめること |
| --- | --- |
| CPUは高く、コピー関数に集まる | コピーする量、フレーム数、システムコール数。同じデータを共有できるか |
| CPUの実行待ちが多い | CPU制限、ワーカー数、クライアント負荷、ホスト側のスケジューリング |
| CPUは低いのに応答が遅い | I/O待ち、アプリ内のキュー・ロック待ち、遅い受信側 |
| 小さいGETだけ高コスト | メタデータ複製、ヘッダー生成、シリアライズ、確保処理 |
| 書き込みが入るとGETが遅い | キャッシュヒット率と無効化回数。読み取りだけの測定と分ける |

`pidstat`やスレッドごとの`schedstat`も補助になります。
開始時と終了時のスレッドIDを対応させ、新設・終了したスレッドを記録します。
スレッド集合が変わった合計値の差を、そのまま待ち時間として使わないでください。
スケジューラー上の実行待ちは、ロック待ちやディスク待ちとは別です。

## 今回の調査から持ち越す注意点

- 候補だけにキャッシュ操作をした比較は、フレームを変更しない並列1でも大きな差が出ました。その比較は採用せず、全実装の準備を揃え直しました。
- 同じ現行版の10 MiB・JSON・並列128でも、1,438〜2,965 RPSに揺れました。遅い値だけを外して改善を主張していません。
- 最後のフレームをまとめると読み取り回数は13→10になりましたが、本体の安定した高速化は確認できませんでした。
- nginxのsendfile実験は別実装でのコピー回避の観測です。gcs-mimicに組み込んだ性能や互換性の検証にはなりません。
- EAGAINを1回見ただけでは、blocking readへ進んだとは限りません。今回の末尾フレーム候補では次のcached readが成功しました。
- 実験データだけのキャッシュを追い出しても、Docker Desktopの下層までコールドになったとは限りません。ホスト全体のキャッシュは操作しません。

## 結論を次の調査へ残す

結果は、次の項目を一組にして保存します。

1. 仮説と対象の負荷。
2. ソース・バイナリ・ツールの識別情報と測定条件。
3. 各回の測定値、エラー、計算式、観測上の制約。
4. 成功・失敗・境界・キャンセルなど、実際に検証した機能の範囲。
5. 採用・不採用・判断保留の理由と、再検討する条件。
6. 残した未検証事項。

ファイル配置に依存するパッチより、何を減らそうとして何が起きたかを記録します。
チェックサム、認可、永続化、資源の上限を弱めて数字を改善しません。
テストが通ったことと、速度が改善したことは別の結論として扱います。
