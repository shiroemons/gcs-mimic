# Storage v2 gRPC のオブジェクト入出力

<!-- markdownlint-configure-file {"MD013": false} -->

対象は RPC-STORAGE-011、RPC-STORAGE-013、RPC-STORAGE-014、RPC-STORAGE-015、RPC-STORAGE-018、RPC-STORAGE-019、RPC-STORAGE-020、RPC-STORAGE-022、RPC-STORAGE-023、BEHAVIOR-RPC-003 です。広い API 全体の状態は PARTIAL とし、正本の台帳から両言語の対応表を生成します。

確定済みupload_idの完了応答は、ストリームの先頭で再開した場合に返します。
途中で別ストリームが確定した場合、後続データにはFAILED_PRECONDITIONを返します。
それ以外の並行ストリームの挙動は未検証です。

`STORAGE_EMULATOR_HOST_GRPC=127.0.0.1:4444` のように、設定済みの h2c リスナーを指定すると、Go の通常の `storage.NewGRPCClient(ctx)` で Writer、NewReader、NewRangeReader、Attrs、Delete、Objects を使えます。Writer のチャンクサイズを変更せず、小さい本文と 5 MiB の本文を検証しました。JSON と gRPC は同じオブジェクト、世代、権限、ホールド、保持、soft delete を使います。

## ルーティングメタデータ

すべての Storage v2 の呼び出しは `x-goog-request-params` を付ける必要があります。付けない呼び出しや値が空の呼び出しは INVALID_ARGUMENT になります。Cloud Storage は、確かめたすべての RPC で同じ応答を返しました（2026-11-18 にケース `grpc-probe-routing` と `grpc-probe-inferred-routing` で記録）。BidiReadObject は記録していないため、推測で同じ規則を当てはめています。リクエストの bucket と異なるバケットがルーティングされた場合や、バケットをまったくルーティングしないメタデータは、2 つのバケット ID を挙げた INVALID_ARGUMENT になります。呼び出しは、いずれかの RPC がルーティングに使うキーのペアをすべて 1 回ずつ読み、値がそのキーの形であること（`project` は `projects/<id>`）を確かめ、同じキーが 2 回あれば、値が同じでも拒否します（`bucket` で記録し、ほかのキーは推測です）。未知のキー、`routing_token`、未知のキーの下の不正なペアは無視し、比べるのはその RPC がルーティングに使うキーだけです（`routing_requires_the_metadata`、`routing_validates_every_routed_key_whichever_rpc_is_called`、`routing_refuses_a_duplicated_key`、`routing_ignores_unknown_keys_and_compares_only_the_routed_keys`、`grpc_calls_need_routing_metadata_and_ignore_unknown_keys`）。QueryWriteStatus と CancelResumableWrite は、先に upload ID を読みます。ID の形でない文字列はメタデータなしでも応答し（記録済み）、読み取れる ID ではメタデータが必要で、ID が指すバケットをルーティングしていなければなりません（2 つの RPC で記録）。呼び出し元の認証と、そのバケットに対する認可のあとに、ルーティングされたバケットを比べるため、権限のない呼び出し元は何をルーティングしても権限の拒否になります。この順序はローカルな選択です。再開した WriteObject と BidiWriteObject も同じ位置で ID のバケットとルーティングを比べますが、これは 2 つの RPC からの推測で、記録していません（`grpc_io_upload_id_calls_read_the_id_before_the_routing_metadata`、`grpc_io_upload_id_calls_authorize_before_comparing_the_routing`、`grpc_io_resumed_write_compares_the_routed_bucket_after_authorization`）。`grpcurl` のような生のクライアントは、たとえば `-H 'x-goog-request-params: bucket=projects%2F_%2Fbuckets%2F<bucket>'` を付けてください。公式 SDK のクライアントは自分で付けます。

## 書き込みストリーム

WriteObject と BidiWriteObject は同じ処理を使い、チェックサムを確認してから共有カタログで確定します。StartResumableWrite の upload_id で再開でき、QueryWriteStatus は永続化済みのオフセットまたは確定したメタデータを返します。オフセット不一致、CRC32C・MD5 不一致、世代条件の失敗で既存の本文を置き換えません。

- 両 RPC は`finish_write`で応答し、それ以降のメッセージは無視します。後続のメッセージで繰り返された`write_object_spec`や`upload_id`は無視し、`object_checksums`はどのメッセージでも受け付けます（2026-11-18 に記録）。WriteObject は終了メッセージより先を読まないため、ストリームを開いたままにするクライアントがセッションを占有しません（`grpc_io_write_object_answers_at_finish_write_without_reading_further`）。
- アップロードは`finish_write`まで 256 KiB 単位でだけ永続化します。最後の単位を超えたバイトは次のメッセージを待ちます。再開可能なストリームがそのバイトを残して閉じると失敗し、バイトは捨てられます。再開可能なストリームの flush と state_lookup は、永続化済みの単位を`persisted_data_checksums`付きで報告します。書き込みの応答は永続化済みバイトの CRC32C だけを返し、QueryWriteStatus は MD5 も返します（BidiWriteObject は 2026-11-18 に記録し、WriteObject はケース `grpc-probe-inferred-session-states` と `grpc-probe-inferred-granules` で記録。`grpc_resumable_persisted_sizes_carry_the_persisted_checksums`）。再開しない BidiWriteObject のストリームの flush と state_lookup は、永続化済みサイズを常に 0、CRC32C を空のバイト列のものとして報告します。upload ID で再開できない書き込みは、終了するまで何も保持しないためです。3 バイトのあとと 256 KiB 1 単位のあと（ケース `grpc-probe-inferred-granules` のステップ `bidi-single-granule-lookups`）で記録し、複数単位のあとは推測です。
- 最初の`write_offset`が永続化済みサイズより先なら、両方のオフセットを挙げた`GRPC_UPLOAD_INVALID_START_OFFSET`（再開しない書き込みでは`GRPC_UPLOAD_INVALID_START_OFFSET_NEW_UPLOAD`）を返します。`object_size`を満たせないサイズは`GRPC_MISMATCHED_UPLOAD_SIZE`で、誤ったデータ CRC32C より先に報告し、データ CRC32C の誤りは書き込みの条件より先に報告します。サイズの合わない終了メッセージはセッションを終了させます（以上 2026-11-18 に記録）。再開したストリームの最初のオフセットが永続化済みサイズ以下なら受け付け、重なった部分を読み飛ばします。永続化済みサイズは変わりません（記録済み。ケース `grpc-probe-inferred-granules` のステップ `first-offset-zero` と `first-offset-inside-persisted`）。読み飛ばしたバイトは、永続化済みのバイトと比べません。記録では同一のバイトを送っていたため、これはエミュレーターの選択で、先に受け取ったバイトが残ることを `grpc_repeated_bytes_are_skipped_without_comparison` が固定します。永続化済みのバイトの内側に収まる終了メッセージは、`object_size`がなければ永続化済みサイズで確定し、`object_size`と食い違えばセッションを終了させます（記録なし）。`finish_write`のない再開メッセージが`object_size`を超えるバイトを送ると、セッションを終了させます（記録済み。ケース `grpc-probe-inferred-granules`）。
- 再開する書き込みと単発の書き込みは、メッセージを同じ順序で検査します。`WriteStep::admit`（`src/grpc/v2/object_io/step.rs`）がこの順序を保ちます。オフセット、サイズ、データの CRC32C、次にメッセージの`object_checksums`（読み取れること、先に宣言したものと一致すること）、次に条件、最後に完成したオブジェクトの検証です。記録済みなのは、永続化済みサイズより先の最初のオフセットと、満たせない`object_size`が誤ったデータ CRC32C より先に、データ CRC32C の誤りが失敗する条件より先に報告されること、永続化済みサイズより先の最初のオフセットが不正な`md5_hash`より先に報告されることです（ケース `grpc-probe-inferred-session-states`）。宣言した`object_checksums`はストリームの終了時に検証します。一致しなければ、何も書き込む前に INVALID_ARGUMENT `Object crc32c mismatch: server computed: '...', client provided: '...'.` を返し、セッションは開いたままです（終了メッセージより前に宣言した CRC32C で記録）。記録しておらず、これから推測したもの: MD5 でも同じこと、終了メッセージや StartResumableWrite が宣言した checksum でも同じこと、再開しない書き込みの最初のメッセージが`object_checksums`をデータの後に読むこと、セッションの鍵をメッセージより先に確かめること、不正な`md5_hash`とサイズ・データ checksum・条件との前後（`grpc_resumable_write_error_precedence`、`grpc_single_shot_write_error_precedence`、`grpc_resumable_object_checksums_hold_for_their_stream`）。
- すべてのメッセージは共有の`WriteStep`（`src/grpc/v2/object_io/step.rs`）に一度だけ復号し、再開しない経路・再開する経路・appendable の経路が同じ型を使います。

確定済みのupload_idで書き込みを再試行すると、ライブオブジェクトが変わっていても、元の完了時のメタデータをOKで返します。未確定のupload_idストリームを正常にhalf-closeすると、flushやstate_lookupがなくても永続化済みサイズを返します。非再開可能な単発書き込みは、protoの指定どおり、最後のメッセージにfinish_writeが必要です。名前の検証はJSONと共通で、`.`・`..`・ACME challenge接頭辞を拒否し、タブは許可します。ストレージのI/Oエラーは共有の分類で返します。ストレージのドメインエラー（`ObjectError`と`CatalogError`）は、JSON アダプターを経由せず`src/grpc/v2/status.rs`で Status に直接対応づけます。not-match 条件だけが失敗した場合は、「The resource you requested has not been modified according to the condition you specified.」の FAILED_PRECONDITION です（コピー・rewrite のソースは`ObjectError::SourceNotModified`、バケットの削除は`CatalogError::NotModified`。読み取りでも書き込みでも Cloud Storage が同じ応答を返しました。2026-11-18 に記録）。

metageneration の match 条件が 0 の場合、match・not-match の同時指定、負の値は、MoveObject を除くすべてのオブジェクト RPC で拒否せず評価します。MoveObject は match と not-match の組を、値によらず INVALID_ARGUMENT で拒否します（2026-11-18 にケース `grpc-probe-object-conditions` と `grpc-probe-inferred-conditions` で記録）。負の match は成立せず、-1 の not-match は成立します。ただし新しいオブジェクトを作る書き込みと rewrite では失敗します（WriteObject・UpdateObject・GetObject・ReadObject・ComposeObject・RewriteObject・DeleteObject で記録し、BidiReadObject は GetObject・ReadObject からの推測です）。負の世代は引き続き INVALID_ARGUMENT で拒否します。

GetObject は世代・条件・read_mask・`soft_deleted`（世代で指定する soft-deleted の世代。バケットに soft delete ポリシーが必要）に対応します。`restore_token`は INTERNAL「We encountered an internal error. Please try again.」を返します。Cloud Storage が、階層型名前空間のないバケットのライブオブジェクトに対して同じ応答を返しました（2026-11-18 に記録）。

ListObjectsは共有の型付きクエリを直接作り、JSONのURLや一覧リソースを組み立てません。発行済みのNoAclページトークンは引き続き使えます。組み合わせのエラーにはprotoのフィールド名を使い、不正なglobには具体的な構文の説明を返します。

## CancelResumableWrite

CancelResumableWrite は、JSON の session URI への DELETE と同じカタログ処理で resumable session を取り消します。書き込み途中のバイトも破棄され、オブジェクトは公開されません。応答は次のとおりです。

- 取消後の QueryWriteStatus は FAILED_PRECONDITION「Upload has already been cancelled.」（ErrorInfo の reason は`GRPC_UPLOAD_ALREADY_CANCELLED`）、書き込みは同じ文言の INVALID_ARGUMENT です。2 回目の取消は空の応答で成功します（以上 2026-11-18 に記録）。`finish_write`のない再開した書き込みも同じ応答です（2026-11-18 にケース `grpc-probe-inferred-session-states` のステップ `cancelled-write-without-finish` で記録。`grpc_io_ended_sessions_answer_as_recorded`）。
- upload_id が ID の形でない場合（空文字列、バケット部分がない）は INVALID_ARGUMENT「Invalid upload ID '...'.」、読み取れない ID（バケット部分の後が 64 桁の 16 進数でない）は INTERNAL です（どちらも 2026-11-18 に記録）。発行された形の ID で、カタログが知っている session を指さないものは、QueryWriteStatus・再開した WriteObject・CancelResumableWrite のどれでも、同じ文言の INTERNAL です。発行済みの ID の途中または末尾の 1 文字を変えたもの（ケース `grpc-probe-inferred-upload-ids`）、文字を 1 つ足したもの、バケットのリソース名の下の未発行の ID（ケース `grpc-probe-resumable-sessions`）で 2026-11-18 に記録しました。別のバケットの下の session も見つからず、同じ応答です。session は StartResumableWrite からカタログの時計で 7 日後に失効し、その時点から同じ 3 つの呼び出しは INTERNAL になります。この失効の応答は記録していません。カタログは失効した session を存在しないものとして応答し、保守処理がその行を消すため、失効した ID と発行したことのない ID をエミュレーターは区別できないためです（`grpc_io_upload_ids_are_looked_up_after_the_permission_check`、`grpc_io_resumable_sessions_expire_seven_days_after_start`）。lookup は権限の検査のあとなので、権限のない呼び出し元は ID によらず拒否されます。
- 確定済みの upload は FAILED_PRECONDITION「Upload has already been completed.」（reason は`GRPC_UPLOAD_ALREADY_COMPLETED`。2026-11-18 に記録）です。QueryWriteStatus は呼び出し元の ACL と owner を付けたリソースを返し続け、オブジェクトは残ります。削除は DeleteObject を使います。再開した WriteObject は、protoの指定どおり、元の完了済みリソースを OK で返します。
- サイズの合わない終了メッセージが終了させた session: `object_size`を満たさない終了メッセージは`GRPC_MISMATCHED_UPLOAD_SIZE`付きの OUT_OF_RANGE を返して session を終了させ、その後の QueryWriteStatus・CancelResumableWrite と、`finish_write`の有無を問わない再開した WriteObject は、reason `GRPC_UPLOAD_ALREADY_TERMINATED`付きの FAILED_PRECONDITION「Upload has already been terminated.」です（2026-11-18 にケース `grpc-probe-inferred-session-states` で記録。`grpc_io_terminated_sessions_refuse_cancels_and_writes`）。`finish_write`のないメッセージが`object_size`を超えるバイトを送った場合も、session は同じように終了します（記録済み。ケース `grpc-probe-inferred-granules`）。記録しておらず、これから推測した挙動: `object_size`を超える終了メッセージも session を終了させます（拒否だけを記録したため）。エミュレーターが別の理由で終了させた session も同じ応答です。
- 別の書き込みが session を使用中ならサーバーでは `catalog_wait_timeout_ms` まで待ち（組み込みのカタログは待ちません）、それでも解放されなければ再試行できる UNAVAILABLE で、session は変わりません。
- strict では `storage.objects.create` が必要で、viewer は PERMISSION_DENIED、匿名は UNAUTHENTICATED になり、session はそのまま残ります。session を作った本人である必要はなく、この権限を持つ別の呼び出し元（たとえば`roles/storage.objectUser`）も取り消せます。使用中の取消の UNAVAILABLE と、作成者以外の取消は Google が定めていないため、ローカルで選んだ挙動です。

本文の送受信は上限付きで、本文全体を集約しません。既存の 4 MiB の受信メッセージ制限、64 KiB の本文チャンク、max_object_bytes を使い、新しい設定は追加しません。ListObjects のページは約 2 MiB で区切って次ページのトークンを返し、進むように必ず 1 件を含みます。単発書き込みは resumable session の保存枠を使いません。

## 読み取りの mask と順序

記録済みのStorage v2のownerは`entity`だけを持ち、gcs-mimicの応答も同じです。soft-deletedの一覧は[SDK互換（英語）](../en/slices/grpc-v2-sdk-parity.md)で扱います。顧客指定の暗号鍵は[gRPC の CSEK](grpc-v2-customer-supplied-keys.md)のとおりに扱います。GetObjectと一覧のmaskは`Object`の全トップレベルフィールドと`*`を受け付けます。応答にはJSONと同じ`etag`と`update_storage_class_time`が入ります。`acl`と`owner`はmaskで指定したとき（または`*`）だけ返し、JSONの`projection=full`と同じ共有処理で作るため、UBLAが有効な場合や`storage.objects.getIamPolicy`がない場合は空になります。appendable オブジェクトは [Rapid append の契約](grpc-v2-rapid-append.md) で扱います。受け付けて無視せず UNIMPLEMENTED を返します。メタデータに 8 KiB の上限はありません。Cloud Storage は WriteObject で 8192 バイトと 40,000 バイトの値を、UpdateObject で 20,000 バイトの値を保存しました（2026-11-15 に記録したケース grpc-custom-metadata-limit）。JSON にエンコードした固定メタデータとカスタムメタデータが、JSON・XML と共通のローカル上限 40 KiB を超えると、公開せずに INVALID_ARGUMENT を返します。明示的な resumable session は共有処理に従います。件数は既定で無制限で（`max_resumable_sessions`で上限を設定できます）、StartResumableWrite から 7 日で失効します。

単数のメッセージのメンバーは、GetObject・ReadObject（`metadata.`の下）・ListObjects で単独に選べます。`checksums.crc32c`、`checksums.md5_hash`、`owner.entity`、`owner.entity_id`、`customer_encryption.encryption_algorithm`、`customer_encryption.key_sha256_bytes`、`retention.mode`、`retention.retain_until_time`です（`src/grpc/v2/object_io/object_mask.rs`）。Cloud Storage は 3 つの RPC で`owner.entity`を返し、owner を付けずに応答したため、`acl`と`owner`はフィールド全体を指すパスのときだけ埋めます（2026-11-18 に記録）。リソースにないフィールドを指すパスは INVALID_ARGUMENT です。未知の名前、`owner.no_such_field`、`acl.role`は GetObject で記録しました（2026-11-18）。map のキー（`metadata.somekey`）、スカラーの下のパス（`name.x`）、メンバーの下のパス（`owner.entity.x`）、空のパス、末尾のドット、先頭のドットも記録しています（ケース `grpc-probe-inferred-object-masks`）。存在しない名前の下、コンテキストの map の下、タイムスタンプの部分の下のパスは、推測で同じ応答にしています。タイムスタンプの部分（`create_time.seconds`、`create_time.nanos`）と`contexts.custom`は選択できます。Cloud Storage は`create_time.seconds`に秒だけのタイムスタンプを、コンテキストのないオブジェクトの`contexts.custom`に空のメッセージを返しました（記録済み。`a_part_of_a_timestamp_and_the_context_map_are_selected_as_members`）。`nanos`の部分とほかのタイムスタンプは推測です。Cloud Storage の応答を記録していないのは保持のタイムスタンプの部分（`retention.retain_until_time.seconds`、`.nanos`）だけで、ErrorInfo 付きの UNIMPLEMENTED を返します。フィールド全体を指定してください。

read_mask に指定できるフィールドはオブジェクトによらないため、GetObject・ReadObject・ListObjects は mask をリクエストと一緒に、認可と取得より前に検査します。GetBucket と同じ位置です（ListBuckets はプロジェクトの認可の後に検査します）。オブジェクトのフィールドにないパスは INVALID_ARGUMENT で、GetObject は`There is no field for this resource named '...'.`、ListObjects は`Invalid read_mask field: '...'.`です（どちらも 2026-11-18 に記録。GetObject は存在するオブジェクト・存在しないオブジェクト・存在しないバケット、ListObjects は空のページとオブジェクトのあるページ）。選択に対応しない下位パスは ErrorInfo 付きの UNIMPLEMENTED で、存在しないオブジェクト、空のページ、認可されない呼び出し元（匿名を含む）でも報告します。正しい mask なら、存在しないオブジェクトは NOT_FOUND のままです。ReadObjectResponse にないフィールドを指す ReadObject のパス（`read_handle`など）と、`content_range`の下位パスは、未対応の設定と同じく拒否します。ErrorInfo 付きの UNIMPLEMENTED を返し、匿名の呼び出し元には UNAUTHENTICATED を返します。`object_checksums.crc32c`はそのダイジェストだけを選びます（2026-11-18 にケース `grpc-probe-inferred-object-masks` のステップ `read-mask-content-and-object-checksums` で記録）。`object_checksums.md5_hash`が MD5 だけを選ぶのは推測です（`a_read_mask_keeps_only_the_response_fields_it_names`）。拒否する ReadObject のパスと、ReadObject の`metadata.`の下の未知のパス（GetObject と同じ文言）に対する Cloud Storage の応答は記録していません。フィールドを選ぶ ReadObject の mask には`checksummed_data.content`が必要です（INVALID_ARGUMENT「The 'read_mask' field must include checksummed_data.content, but was '...'.」。記録済み）。内容だけを選ぶ mask では、CRC32C なしでバイトを返します（2026-11-18 に記録）。GetObject は不正な顧客指定の暗号鍵と不正な名前を mask より先に報告し、ReadObject も不正な暗号鍵と名前を先に報告します。`restore_token`の拒否と`soft_deleted`の取得は、mask とバケットの認可の後で行います。記録した優先順位のケースは、存在しないオブジェクトより先に不正な暗号鍵と内容のない mask を報告することを示します（`grpc-probe-object-precedence`）。残りの検査の順序はローカルな選択です（SPEC-GRPC-LOCAL-CHOICES）。

ReadObject は次の順にエラーを報告します。不正な顧客指定の暗号鍵、不正な名前、read_mask（上記の拒否するパスを除き、いずれも INVALID_ARGUMENT）、バケットの認可（拒否するのは、バケットが存在せず、呼び出し元がどのプロジェクトでも`storage.objects.get`を持たないときだけです。匿名の呼び出し元には UNAUTHENTICATED、プリンシパルには PERMISSION_DENIED を返します）、負の世代（INVALID_ARGUMENT）、取得と同時のオブジェクトの認可（存在するバケットでは、匿名の呼び出し元は存在しないオブジェクトでも PERMISSION_DENIED）、存在しないオブジェクトの NOT_FOUND、条件の失敗の FAILED_PRECONDITION、末尾を越えるオフセットの OUT_OF_RANGE、最後に負の`read_limit`の INVALID_ARGUMENT です。記録済みなのは、存在しないオブジェクトより先に暗号鍵と mask を報告すること、末尾を越えるオフセットより先に条件の失敗を報告することで、残りの順序はローカルな選択です。`content_encoding`が gzip のオブジェクトは、全体でも範囲指定でも、保存したバイトを展開せずに返します（2026-11-18 に`grpc-probe-object-masks`の`read-gzip`で記録。Storage v2 は展開しません）。JSON と XML の読み取りは BEHAVIOR-OBJECT-017 に従います。

GetObject・ReadObject・DeleteObject は、届いた世代条件と metageneration 条件を Cloud Storage と同じように比べます（2026-11-18 に`grpc-probe-object-conditions`で記録）。metageneration の match が 0 なら成立せず FAILED_PRECONDITION で、match と not-match の同時指定は拒否せず評価します。負の値も評価します。-1 の match は成立せず FAILED_PRECONDITION になり、-1 の not-match は成立します（2026-11-18 にケース `grpc-probe-inferred-conditions` で、GetObject と DeleteObject について記録し、ReadObject は GetObject の規則に従います）。記録していない BidiReadObject は、同じオブジェクトを同じ規則で読むと推測しています。テストは`read_object_refuses_negative_limits_and_offsets_past_the_end`、`get_object_refuses_restore_tokens_and_negative_values`、`write_and_delete_object_compare_negative_conditions`です。

## 台帳のケース

2026-11-18 に、台帳の各行を、確かめられる振る舞いごとの受け入れケースに分けました。実機の Cloud Storage では実行しないため、Google が定めておらず記録もない応答はローカルな選択とし、固定するテストと合わせて scoped difference に記録します。概要は次のとおりです。

- 意図した拒否（SPEC-GRPC-UNMODELED-SETTINGS の scoped difference）: WriteObject・BidiWriteObject・StartResumableWrite での書き込みリソースの`kms_key`とオブジェクトのコンテキスト、ListObjects のコンテキスト用`filter`。GetObject の`restore_token`は未対応の拒否ではなく、記録済みの INTERNAL を返します（階層型名前空間のバケットだけが使うためです）。
- 2026-11-18 の Cloud Storage の記録に合わせたもの: ルーティングメタデータとその拒否、上に挙げた書き込みストリームと resumable session の応答、オブジェクトの条件と read_mask（GetObject・ReadObject・ListObjects）、GetObject の`soft_deleted`と`restore_token`、gzip の読み取り。プローブケースは`grpc-probe-routing`、`grpc-probe-write-streams`、`grpc-probe-bidi-write`、`grpc-probe-resumable-sessions`、`grpc-probe-object-conditions`、`grpc-probe-object-masks`、`grpc-probe-object-precedence`です。
- 推測で決めていた応答を確かめた、2026-11-18 の 2 回目の記録に合わせたもの（ケース `grpc-probe-inferred-routing`、`grpc-probe-inferred-upload-ids`、`grpc-probe-inferred-session-states`、`grpc-probe-inferred-granules`、`grpc-probe-inferred-conditions`、`grpc-probe-inferred-object-masks`、`grpc-probe-inferred-destinations`）: すべての RPC のルーティング、未知の upload ID への INTERNAL、終了した session への FAILED_PRECONDITION、永続化済みサイズ以下から始まる最初のオフセットの受け入れと重なりの読み飛ばし、`object_size`を超えるバイトでの session の終了、ストリームごとの`object_checksums`、負の条件の比較、タイムスタンプの部分・`contexts.custom`・単一のダイジェストの read_mask。記録が推測と一致した箇所は、上の文章で記録済みと書いています。一致しなかった箇所は、エミュレーターを変更しました。
- 残るローカルな選択（SPEC-GRPC-LOCAL-CHOICES。ギャップ項目が各項目と、それを固定するテストを挙げます）: 書き込みが session の lease を持つあいだの CancelResumableWrite の UNAVAILABLE と、session を作った本人に限らず`storage.objects.create`を持つ誰でも取り消せること。7 日での失効と、失効した session への INTERNAL（カタログは発行したことのない ID と区別できません）。`object_size`を超える終了メッセージの後の session の状態、エミュレーターが別の理由で終了させた session、再開メッセージが繰り返したバイトを比べずに読み飛ばすこと、永続化済みのバイトの内側に収まる終了メッセージ、再開メッセージのうち Cloud Storage を記録していない検査（session の鍵と不正な`md5_hash`の位置、MD5 の文言、再開しない最初のメッセージの`object_checksums`をデータの後に読むこと）。記録していないルーティング（不正な`source_bucket`・`appendable`、`bucket`以外の重複キー、ルーティングされた project だけの拒否、ListBuckets で project をルーティングしない場合）、再開した書き込みのルーティングされたバケット、認可の後に比べる順序。mask の後の GetObject と ReadObject の検査の順序と、ReadObject のエラーの順序。ReadObject の応答パスと、保持のタイムスタンプの部分が read_mask で返す UNIMPLEMENTED。BidiReadObject の負の条件の比較。
- Storage v2 のすべての行は BEHAVIOR-RPC-001 に依存します。どの RPC も、そのルーティングとリクエストのメタデータの処理を通るためです。RPC-STORAGE-013 自体には未完了のケースがありません。サーバー側の`grpc-timeout`と gzip のメッセージ圧縮は、SPEC-GRPC-CALL-METADATA の scoped difference です。
- 実装が必要なもの: 書き込みリソースの`predefined_acl`・`acl`・`retention`と出力専用フィールド（proto が出力専用とする`resource.checksums`を検証し続けるかも含む）。
- テストが必要なもの: 記録した優先順位のケースが扱わない DeleteObject・WriteObject のエラーの順序、QueryWriteStatus が返す値が減らないこと、セッションのチェックポイントでの書き込み・同期の失敗とクラッシュ。
- 判断が必要なもの: 使用中のセッションに対して待つか（現在は catalog の待ち時間まで待って UNAVAILABLE）、ABORTED を返すか。
