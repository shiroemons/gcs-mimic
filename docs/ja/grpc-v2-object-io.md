# Storage v2 gRPC のオブジェクト入出力

<!-- markdownlint-configure-file {"MD013": false} -->

対象は RPC-STORAGE-011、RPC-STORAGE-013、RPC-STORAGE-014、RPC-STORAGE-015、RPC-STORAGE-018、RPC-STORAGE-019、RPC-STORAGE-020、RPC-STORAGE-022、RPC-STORAGE-023、BEHAVIOR-RPC-003 です。広い API 全体の状態は PARTIAL とし、正本の台帳から両言語の対応表を生成します。

確定済みupload_idの完了応答は、ストリームの先頭で再開した場合に返します。
途中で別ストリームが確定した場合、後続データにはFAILED_PRECONDITIONを返します。
それ以外の並行ストリームの挙動は未検証です。

`STORAGE_EMULATOR_HOST_GRPC=127.0.0.1:4444` のように、設定済みの h2c リスナーを指定すると、Go の通常の `storage.NewGRPCClient(ctx)` で Writer、NewReader、NewRangeReader、Attrs、Delete、Objects を使えます。Writer のチャンクサイズを変更せず、小さい本文と 5 MiB の本文を検証しました。JSON と gRPC は同じオブジェクト、世代、権限、ホールド、保持、soft delete を使います。

WriteObject と BidiWriteObject は同じ処理を使い、チェックサムを確認してから共有カタログで確定します。StartResumableWrite の upload_id で再開でき、QueryWriteStatus は永続化済みのオフセットまたは確定したメタデータを返します。オフセット不一致、CRC32C・MD5 不一致、世代条件の失敗で既存の本文を置き換えません。ReadObject は範囲と負のオフセット、CRC32C、世代指定に対応し、一覧は prefix・delimiter・ページングに対応します。

確定済みのupload_idで書き込みを再試行すると、ライブオブジェクトが変わっていても、元の完了時のメタデータをOKで返します。未確定のupload_idストリームを正常にhalf-closeすると、flushやstate_lookupがなくても永続化済みサイズを返します。非再開可能な単発書き込みは、protoの指定どおり、最後のメッセージにfinish_writeが必要です。名前の検証はJSONと共通で、`.`・`..`・ACME challenge接頭辞を拒否し、タブは許可します。ストレージのI/Oエラーは共有の分類で返します。

ListObjectsは共有の型付きクエリを直接作り、JSONのURLや一覧リソースを組み立てません。発行済みのNoAclページトークンは引き続き使えます。組み合わせのエラーにはprotoのフィールド名を使い、不正なglobには具体的な構文の説明を返します。

CancelResumableWrite は、JSON の session URI への DELETE と同じカタログ処理で resumable session を取り消します。書き込み途中のバイトも破棄され、オブジェクトは公開されません。取り消した後の QueryWriteStatus・WriteObject・BidiWriteObject、2 回目の取消、未知・不正な upload_id は NOT_FOUND になります。session は StartResumableWrite からカタログの時計で 7 日後に失効し、その時点から QueryWriteStatus・再開した書き込み・取消はどれも NOT_FOUND です。確定済みの upload は FAILED_PRECONDITION です。別の書き込みが session を使用中ならサーバーでは `catalog_wait_timeout_ms` まで待ち（組み込みのカタログは待ちません）、それでも解放されなければ再試行できる UNAVAILABLE です。strict では `storage.objects.create` が必要で、viewer は PERMISSION_DENIED、匿名は UNAUTHENTICATED になり、session はそのまま残ります。session を作った本人である必要はなく、この権限を持つ別の呼び出し元（たとえば`roles/storage.objectUser`）も取り消せます。確定済み・2 回目・書き込み中・失効後の status と、作成者以外の取消は Google が定めていないため、ローカルで選んだ挙動です。

本文の送受信は上限付きで、本文全体を集約しません。既存の 4 MiB の受信メッセージ制限、64 KiB の本文チャンク、max_object_bytes を使い、新しい設定は追加しません。ListObjects のページは約 2 MiB で区切って次ページのトークンを返し、進むように必ず 1 件を含みます。単発書き込みは resumable session の保存枠を使いません。

未対応は、単発書き込みの途中の flush/state_lookup、ネストした read_mask、soft-deletedオブジェクトのGetObjectなどです。記録済みのStorage v2のownerは`entity`だけを持ち、gcs-mimicの応答も同じです。soft-deletedの一覧は[SDK互換（英語）](../en/slices/grpc-v2-sdk-parity.md)で扱います。顧客指定の暗号鍵は[gRPC の CSEK](grpc-v2-customer-supplied-keys.md)のとおりに扱います。GetObjectと一覧のmaskは`Object`の全トップレベルフィールドと`*`を受け付けます。応答にはJSONと同じ`etag`と`update_storage_class_time`が入ります。`acl`と`owner`はmaskで指定したとき（または`*`）だけ返し、JSONの`projection=full`と同じ共有処理で作るため、UBLAが有効な場合や`storage.objects.getIamPolicy`がない場合は空になります。appendable オブジェクトは [Rapid append の契約](grpc-v2-rapid-append.md) で扱います。受け付けて無視せず UNIMPLEMENTED を返します。メタデータに 8 KiB の上限はありません。Cloud Storage は WriteObject で 8192 バイトと 40,000 バイトの値を、UpdateObject で 20,000 バイトの値を保存しました（2026-11-15 に記録したケース grpc-custom-metadata-limit）。JSON にエンコードした固定メタデータとカスタムメタデータが、JSON・XML と共通のローカル上限 40 KiB を超えると、公開せずに INVALID_ARGUMENT を返します。明示的な resumable session は共有処理に従います。件数は既定で無制限で（`max_resumable_sessions`で上限を設定できます）、StartResumableWrite から 7 日で失効します。エラーの順序や、同じ upload_id の複数ストリームの競合は、下の台帳のケースのとおり未確定です。

upload_id を使うストリームでは、非最終メッセージの object_checksums は UNIMPLEMENTED で拒否します。StartResumableWrite または finish_write=true で指定してください。最初のメッセージでの指定は上流の契約では有効です。以前は、共有セッションが変更した checksum を永続化できないことを理由にしていました。しかしセッションのチェックポイントは、各メッセージのオプションを、統合した checksum も含めてオフセットと同じ更新で保存します（`src/storage/catalog/resumable.rs`の`checkpoint_resumable_output`）。このため、最初のメッセージでの受け付けは未対応の作業（BEHAVIOR-RPC-003 の`stream_resumable_first_checksums`）として残します。拒否してもオフセットは進みません。StartResumableWrite の checksum は切断・再起動後も検証され、不一致ではオブジェクトを作成せずセッションを無効化します。

read_mask に指定できるフィールドはオブジェクトによらないため、GetObject・ReadObject・ListObjects は mask をリクエストと一緒に、認可と取得より前に検査します。GetBucket と同じ位置です（ListBuckets はプロジェクトの認可の後に検査します）。`Object`にないフィールドを指すパスは INVALID_ARGUMENT `There is no field for this resource named '...'.`、ネストしたパスは ErrorInfo 付きの UNIMPLEMENTED で、存在しないオブジェクト、空のページ、認可されない呼び出し元（匿名を含む）でも報告します。正しい mask なら、存在しないオブジェクトは NOT_FOUND のままです。ReadObjectResponse にないフィールドを指す ReadObject のパス（`read_handle`など）と、`content_range`・`object_checksums`の下位パスは、未対応の設定と同じく拒否します。ErrorInfo 付きの UNIMPLEMENTED を返し、匿名の呼び出し元には UNAUTHENTICATED を返します。Cloud Storage は`Object`にないフィールドを指す GetObject のパスに INVALID_ARGUMENT を返した（ケース grpc-read-mask）ため、不明な応答パスは保留中のケースです。GetObject は不正な顧客指定の暗号鍵、`soft_deleted`・`restore_token`の拒否、不正な名前を mask より先に報告し、ReadObject は不正な暗号鍵と名前を先に報告します。Google は順序を定めておらず、記録済みの mask の拒否は存在するオブジェクトに対するものだったため、この順序は記録済みのローカルな選択です（SPEC-GRPC-LOCAL-CHOICES）。

同じ 2026-11-18 に、この mask の検査を認可と取得より前に移しました。`src/grpc/v2/object_io/read/mask_tests.rs`のテストは変更より先に書き、結果に対して mask を検査していたあいだは失敗しました（存在しないオブジェクトへの不正な mask は NOT_FOUND、空の一覧への不正な mask は成功でした）。変更後は、存在しないオブジェクトと空の一覧でも不明なパスとネストしたパスを報告します。匿名の呼び出し元を拒否するより先（mask がなければ GetObject・ReadObject は PERMISSION_DENIED、ListObjects は UNAUTHENTICATED）、負の世代・条件や末尾を越える読み取りオフセットより先（mask がなければ INVALID_ARGUMENT と OUT_OF_RANGE）にも mask を報告します。不正な暗号鍵、`soft_deleted`の拒否、不正な名前は mask より先のままです。`cargo test --locked --offline --lib grpc::`の 270 件が通りました。

同じ日に、テストのなかった読み取り側の拒否を`src/grpc/v2/object_io/read/request_refusals.rs`で固定しました。既存の応答を固定するテストなので、変更なしで通ります。`get_object_refuses_unmodeled_lookups_and_negative_values`は、`soft_deleted`の true と`restore_token`を ErrorInfo 付きで拒否し、`soft_deleted`の false は通常の取得として扱い、負の世代と負の条件を INVALID_ARGUMENT で拒否します。`read_object_refuses_negative_limits_and_offsets_past_the_end`は、負の`read_limit`、Cloud Storage と同じ文言の OUT_OF_RANGE になる末尾を越えるオフセット、負の世代と条件を拒否します。`list_objects_refuses_a_filter_and_a_negative_page_size`は、コンテキスト用の`filter`を ErrorInfo 付きで、負の`page_size`を INVALID_ARGUMENT で拒否します。

ReadObject は次の順にエラーを報告します。これも記録済みのローカルな選択です。不正な顧客指定の暗号鍵、不正な名前、read_mask（上記の拒否するパスを除き、いずれも INVALID_ARGUMENT）、バケットの認可（拒否するのは、バケットが存在せず、呼び出し元がどのプロジェクトでも`storage.objects.get`を持たないときだけです。匿名の呼び出し元には UNAUTHENTICATED、プリンシパルには PERMISSION_DENIED を返します）、負の世代、負の条件（どちらも INVALID_ARGUMENT）、取得と同時のオブジェクトの認可（存在するバケットでは、匿名の呼び出し元は存在しないオブジェクトでも PERMISSION_DENIED）、存在しないオブジェクトの NOT_FOUND、条件の失敗の FAILED_PRECONDITION、末尾を越えるオフセットの OUT_OF_RANGE、最後に負の`read_limit`の INVALID_ARGUMENT です。また、`content_encoding`が gzip のオブジェクトは、全体でも範囲指定でも、保存したバイトを展開せずに返します。proto と RPC リファレンスは Storage v2 での展開について何も述べておらず、記録もありません。JSON と XML の読み取りは BEHAVIOR-OBJECT-017 に従います。`read_object_reports_each_failure_before_the_ones_it_precedes`がこの順序を、`read_object_returns_gzip_encoded_bytes_as_stored`が展開しないことを固定し、既存のコードに対して通りました。順序のテストの最初の版は認可を世代の検査より先と想定して失敗しました。オブジェクトの読み取り RPC は取得と同時にオブジェクトへのアクセスを認可するためで、テストをコードの順序に合わせました。

この順序のテストは存在するバケットしか使っておらず、上の順序も当初は、世代と条件をすべての認可より先に検査すると書いていました。実際にはバケットの認可が先で、拒否するのは存在しないバケットのときだけです。`a_missing_bucket_is_authorized_before_the_generation_and_the_conditions`がこれを固定します。存在しないバケットでは、匿名の呼び出し元は UNAUTHENTICATED、どのプロジェクトでも権限を持たないプリンシパルは PERMISSION_DENIED を、負の世代より先に受け取ります。プロジェクトの閲覧者は、世代、条件の順に INVALID_ARGUMENT を受け取り、その後は NOT_FOUND です。`unsupported_read_mask_paths_as_an_anonymous_caller_sees_them`は、ネストした`Object`のパスを匿名で GetObject・ReadObject・ListObjects に送り（ErrorInfo 付きの UNIMPLEMENTED）、拒否する ReadObject の応答パスを匿名の呼び出し元（UNAUTHENTICATED）と認可された呼び出し元（ErrorInfo 付きの UNIMPLEMENTED）から送ります。どちらも既存の応答を固定するテストで、最初から通りました。`cargo test --locked --offline --lib grpc::`の 273 件が通りました。

## 台帳のケース

2026-11-18 に、台帳の各行を、確かめられる振る舞いごとの受け入れケースに分けました。実機の Cloud Storage では実行しないため、Google が定めておらず記録もない応答はローカルな選択とし、固定するテストと合わせて scoped difference に記録します。概要は次のとおりです。

- 意図した拒否（SPEC-GRPC-UNMODELED-SETTINGS の scoped difference）: WriteObject・BidiWriteObject・StartResumableWrite での書き込みリソースの`kms_key`とオブジェクトのコンテキスト、ListObjects のコンテキスト用`filter`、階層型名前空間のバケットだけが使う GetObject の`restore_token`。
- 記録済みのローカルな選択（SPEC-GRPC-LOCAL-CHOICES）: CancelResumableWrite が返す FAILED_PRECONDITION・NOT_FOUND・UNAVAILABLE と、session を作った本人に限らず`storage.objects.create`を持つ誰でも取り消せること。session の 7 日での失効と、失効後に QueryWriteStatus・再開した書き込み・CancelResumableWrite が返す NOT_FOUND。GetObject・ReadObject・ListObjects が read_mask をリクエストと一緒に、認可と取得より前に検査すること。暗号鍵から`read_limit`までの ReadObject のエラーの順序。ReadObject が gzip のオブジェクトを展開せずに保存したバイトを返すこと。
- Storage v2 のすべての行は BEHAVIOR-RPC-001 に依存します。どの RPC も、そのルーティングとリクエストのメタデータの処理を通るためです。RPC-STORAGE-013 自体には未完了のケースがありませんが、BEHAVIOR-RPC-001 のルーティングを確かめる SDK、サーバー側の`grpc-timeout`、gzip のメッセージ圧縮が未完了のあいだは PARTIAL のままです。
- 実装が必要なもの: 書き込みリソースの`predefined_acl`・`acl`・`retention`と出力専用フィールド（proto が出力専用とする`resource.checksums`を検証し続けるかも含む）、GetObject の`soft_deleted`、ネストした read_mask と ReadObject の応答の下位パス、不明な`Object`フィールドは INVALID_ARGUMENT なのに UNIMPLEMENTED を返す、ReadObject の不明な応答パス、再開可能・単発の書き込みと QueryWriteStatus の`persisted_data_checksums`（現在は appendable だけが返します）、単発ストリームの途中の flush と state_lookup、upload_id ストリームの最初のメッセージの`object_checksums`、`finish_write`の後にストリームの終了を待つ間も writer lease を持ち続ける WriteObject の再開。
- テストが必要なもの: DeleteObject・WriteObject のエラーの順序、QueryWriteStatus が返す値が減らないこと、セッションのチェックポイントでの書き込み・同期の失敗とクラッシュ。
- 判断が必要なもの: オブジェクトの前提条件の検証規則（GetObject・ReadObject・BidiReadObject・DeleteObject・WriteObjectSpec（WriteObject・BidiWriteObject・StartResumableWrite）・AppendObjectSpec は緩く、変更系の RPC は metageneration 条件の 0 と match・not-match の同時指定を拒否します。規則を決めると応答が変わるか確定するため、該当する行にはそれぞれこのケースがあります）、再開したストリームの最初のメッセージが永続化済みオフセットより前から始めてよいか（proto の`write_offset`の説明（1411〜1415 行）と WriteObject の説明（480〜489 行）が食い違っています）、使用中のセッションに対して待つか ABORTED を返すか、SDK の half-close を確認したうえで BidiWriteObject の`finish_write`後のメッセージを報告するか。
