# ファイル保存の仕組み

gcs-mimicはメタデータをSQLite、オブジェクト本体を別ファイルへ保存します。
SQLiteは組み込みなので、データベースサーバーの準備は不要です。
内部ファイル名はオブジェクト名ではなくIDです。
現在、保存先を`バケット名/オブジェクト名`として直接編集する使い方はできません。

[English: 実ファイルの調査](../en/fake-gcs-server-storage.md) ·

## 初期ファイルと永続データを分ける

| 用途 | gcs-mimic | fake-gcs-server |
| --- | --- | --- |
| 初期ファイルの入力 | `--seed-dir` | `-data` |
| APIで更新する永続データ | `--data-dir` | `-filesystem-root` |
| 再起動時の初期ファイル再読込 | しない | seed指定時は実行 |
| 永続データの名前 | 本体は内部ID | バケット・オブジェクトのパス |

fake-gcs-serverの公式イメージは`/data`を初期入力として使い、
ファイル方式の永続データは既定で`/storage`へ保存します。
`/data`だけをマウントしても、APIで新規保存したデータの永続化にはなりません。
入力と保存先は、同じ形のディレクトリでも別のコピーです。

```text
<seed-or-storage-root>/
  first-bucket/
    nested/
      seed.txt
  second-bucket/
```

fake-gcs-serverは空のバケットも読み込み、拡張子からContent-Typeを求めます。
gcs-mimicの初期読込は`application/octet-stream`です。
gcs-mimicはカタログに初期化済みの印を保存し、APIで変更したデータを再読込で戻しません。
設定とマウントの例は[Dockerでの使い方](container-usage.md#初期ファイルを読み込む)にあります。

## fake-gcs-serverの実ファイルはどう動くか

調査対象はfake-gcs-server`v1.56.1`、コミット
`896ece51e49eed0946089f3089f6343855c0d106`です。
2026-10-24にソースとmacOS ARM64のファイル方式を確認しました。

本体は実ファイル、属性は対応環境なら`user.metadata`拡張属性へ保存します。
拡張属性を使えない場合は隣接する`<object>.metadata`のJSONです。
バケット属性はバケットディレクトリの隣の`<bucket>.bucketMetadata`に置きます。
本体だけコピーしても、世代・hash・ACLなどを含む保存状態の移行にはなりません。

| 操作 | macOSの拡張属性方式で確認した結果 |
| --- | --- |
| 初期入力のファイルを変更 | 起動中のAPI内容は変わらない |
| APIでアップロード | 永続保存先に名前付きファイルを作成 |
| 既存ファイルをその場で上書き | GETの本体とサイズは変わる |
| 上書き後に属性を確認 | hashと世代は古いまま |
| 拡張属性のない新ファイルに置換 | オブジェクトGETは404 |
| 属性のないファイルを追加 | GETとバケット内一覧は404 |
| 既存ファイルを削除 | GETは直ちに404 |

その場での上書きでは、拡張属性を保持しました。
エディターが保存時に別ファイルへ置き換える場合は結果が異なります。
実ファイルが読めることと、安全な双方向同期ができることは別です。

ファイル方式ではreseedや同じseedを使う再起動で、同名のAPI変更を上書きします。
無関係なAPI作成オブジェクトは残ります。メモリ方式のreseedは、
ソース上はバックエンド全体の置換であり、この実行調査では確認していません。
ファイル方式はversioningを拒否し、メモリ方式が世代を保持します。

この調査はサイドカー方式、Linux・Windows、停電、同時編集の実行検証を含みません。
全13件の結果は[英語の実行記録](../en/evidence/fake-gcs-server-filesystem.txt)を参照してください。

## 永続データを変更せずに検査する

開発版では、停止したfake-gcs-serverの永続データをdry-runで検査できます。
実際の移行や再開処理は未実装です。DESIGN-062、DESIGN-072、DESIGN-073、
AUDIT-014の状態は引き続きPARTIALです。

書き込み元を停止するか、不変のスナップショットを用意してください。
可能なら読み取り専用でマウントします。宛先には、既存の親ディレクトリの下にある
未作成の名前か、ソースと重ならない空のディレクトリを指定します。

```sh
cargo run --locked --offline -- import fake-gcs-server \
  --source source-snapshot --data-dir converted-data \
  --metadata-mode sidecar --source-platform unix --dry-run
```

拡張属性方式のスナップショットには`--metadata-mode xattr`を指定します。
方式はルート全体で固定し、読み取りエラーが出ても別方式へ切り替えません。
ソースがWindowsなら`--source-platform windows --metadata-mode sidecar`を使います。
`--dry-run`は必須です。宛先、カタログ、移行マーカー、リスナーは作りません。

既定ではメタデータだけを検査します。`--verify-bodies`を加えると、
本文を64 KiBずつ一度だけ読み、保存されたMD5・CRC32Cと照合します。
本文、権限、mtime、ctime、拡張属性は変更しません。読み取りでatimeが変わる場合はあります。

標準出力はJSON Linesです。ヘッダー、最大256件の記録・診断を含むページ、
正確な件数を含む集計を順に出します。標準エラーには共通の診断形式で修正方法を出します。
メタデータだけの検査は`bodies_verified: false`です。
`complete`は走査の完了、`eligible`は検出した問題による移行可否を示し、
どちらも移行の完了を意味しません。
`buckets`と`objects`は発見した候補数、`eligible_buckets`と`eligible_objects`は
出力した適格な記録の数です。不適格な候補は、フィールド、原因、修正方法を診断に出します。
移行元を比べる指紋`manifest_sha256`と、同一実行中のinode・ctimeの変化を調べる
`stat_observations_sha256`は別に計算します。どちらも形式の版を持つSHA-256です。

サイドカーを含めて10000エントリー、バケット配下32階層、属性64 KiB、
本文1 GiBを上限とします。走査上限を超えた場合や、対応できない属性・破損・
チェックサムの不一致がある場合は失敗します。元のAPI名は保存形式から復元できないため、
正規化されたディスク上の名前だけを報告し、`original_names_verified: false`を明示します。
ディレクトリだけの項目から空のオブジェクトを作ることはありません。

ネイティブWindowsでの実行とファイルID・ctimeの取得は未検証です。
メモリ方式の全世代エクスポートは別の未実装機能です。
詳細な範囲と検証結果は[英語の契約](../en/slices/source-storage-contract.md#executable-dry-run)と
[検証記録](../en/evidence/import-dry-run.md)を参照してください。

## SQLiteと実フォルダの同期は両立できるか

両立できますが、現在のgcs-mimicには双方向同期がありません。
予定している要件は、指定した`バケット/オブジェクト`のディレクトリを外部から編集でき、
APIでの変更も同じ場所へ反映されることです。初回seedや単発の移行だけでは満たせません。

設計候補ではSQLiteと内部の本体を保持し、別の編集用ディレクトリを同期します。
公開済みの内部本体は直接変更しません。
外部変更も共通の取込・hash計算・世代更新・公開処理を通します。
ファイルサイズやSQLiteだけを更新しても、APIの状態を整合させることはできません。
編集用レイアウトや新しいCLIは未確定です。

実装前に、APIと外部編集の競合、特殊な名前の表現、メタデータの管理主体、
反映までの時間を決めます。部分書込、エディターの一時ファイル、通知の欠落、
自分の書戻しによる再通知、再起動・ディスク不足からの復旧も検証対象です。
世代履歴、バケット設定、権限を保ったまま反映する必要があります。

## 保存方式の評価範囲

SQLiteは一覧検索や条件付き更新に使い、本体はストリームで別ファイルへ保存します。
ファイルのrenameとSQLのcommitは別操作で、まとめて1つの原子的操作にはなりません。
復旧処理と記録済みのプロセス停止検証はありますが、すべての停電状況を保証しません。
内部データディレクトリを直接書き換えないでください。

同条件の比較ベンチマークは実施しておらず、SQLiteが常に速いという判断ではありません。
詳細な選定理由は[英語の保存方式調査](../en/storage-backends.md)、
実装の依存と順序は[開発計画](delivery-plan.md)を参照してください。
