# gcs-mimic 0.28.0

0.28.0 removes bidirectional directory synchronization and makes `seed_dir` a live, read-only input instead: the server watches the folder while it runs, republishes changed files, creates buckets for new top-level directories and deletes the objects of removed files that seeding published. Everything else keeps its meaning, but the removal and the new deletion rule are breaking; read [What may need attention](#what-may-need-attention) and the [upgrade steps](#upgrade-steps) before you start a data directory with this release.

The [feature matrix](../feature-matrix.md) lists the exact supported subsets.

## What may need attention

- **Directory synchronization is gone.**
  - `sync_dir`, `sync_delete_guard`, `sync_reinitialize`, `max_sync_entries`, `max_sync_depth` and `GCS_MIMIC_SYNC_TOKEN` are no longer settings, the `gcs-mimic sync` commands no longer exist, and the `/_internal/sync` routes and the `sync` object of the ready answer are removed. Supplying a removed setting, in a flag, an environment variable or the JSON configuration, stops startup with guidance to use `seed_dir`; `gcs-mimic sync` exits 1 with the same guidance.
  - Use `seed_dir` to load a folder. It only reads the folder: API writes never appear in it, and edits made in the folder reach the catalog through the watch below.
  - A seed directory that still holds `.gcs-mimic-sync.json` or `.gcs-mimic-sync-work/` stops startup with guidance, because the workspace may hold the only copy of a file a write-back displaced. gcs-mimic never deletes either; inspect them, remove them yourself and start again.
- **Removing a fixture file now deletes the object seeding published for it.** 0.27.0 and earlier never deleted an object because its seed file was gone. Now a startup replay, a reseed and the watch delete an object when seeding published it (or found it identical to a version it already owned) and nothing has changed it since: neither its body nor its metadata, and no hold or retention period protects it. An object an API request wrote or edited stays, and so does an identical object that an earlier release seeded, until its file changes and is published again. While the server runs, a pass deletes only when the pass just before it and this one both found the file gone, the later at least a second after the first; a pass in between that saw the file, could not decide or failed starts the wait again. At startup and on a reseed (on Unix) one proof suffices, and only for a name the walk never listed and a lookup proves absent: a file that was listed and then went missing, as during an editor's rename-save, keeps its object, warns with `seed_skipped` and is decided by the next replay. A removed top-level directory deletes the objects below it that seeding published, never the bucket. If your tests relied on deleting a file to leave its object in place, keep the file or recreate the object through the API.
- **`seed_dir` is watched while the server runs.** `seed_watch_interval_ms` defaults to 1000 and takes 0 to 86400000; 0 replays the folder only at startup, as 0.27.0 did. Set `GCS_MIMIC_SEED_WATCH_INTERVAL_MS=0` to keep the old behavior. A file an API request overwrote or deleted keeps the API's state until the file changes again, and a bucket the API deleted, or deleted and created again, is left alone by the passes even if its directory goes away and comes back; only a restart or a reseed creates it again.
- **The catalog moves to schema 59, one way.** Schema 58 retires the synchronization tables and the change journal, which nothing reads any more; schema 59 adds the records seeding keeps per file. A 0.27.0 binary refuses a data directory migrated to 58 or 59 as a newer schema, so keep the backup you take before upgrading to roll back.
- **`lifecycle_execution` defaults to `enabled` in every configuration.** 0.27.0 defaulted to `disabled` when `sync_dir` was configured and to `enabled` otherwise. Only former synchronization users see a change: stored Delete rules in their catalog execute after the upgrade unless they set `lifecycle_execution` to `disabled`.

## Upgrade steps

1. Stop the server and back up the data directory. Restore it with the matching 0.27.0 executable to roll back.
2. If you used `sync_dir`, replace it with `seed_dir` pointing at the folder, or at a copy of it. Remove `sync_delete_guard`, `sync_reinitialize`, `max_sync_entries`, `max_sync_depth` and `GCS_MIMIC_SYNC_TOKEN` from your command lines, Compose files and configuration, and any use of `gcs-mimic sync` or `/_internal/sync` from your scripts.
3. Delete `.gcs-mimic-sync.json` and `.gcs-mimic-sync-work/` from a former synchronization folder after you have checked that nothing in the workspace is a file you still need. Startup stops until they are gone.
4. Start the new release. If the catalog still named files that may hold your edits, the first start writes `sync-retired.json` to the data directory (`sync-retired.1.json` and on when one with other content exists) and warns once with `sync_retired_files_listed`. It lists the copies in `sync-conflicts/`, the entries that may remain in each folder's `.gcs-mimic-sync-work/`, and the folders, with paths as the old process saw them. Compare them with your files, delete what you no longer need, and delete the manifest once you have checked it. gcs-mimic never deletes `sync-conflicts/` or its copies.
5. On native Windows, plan for the limit below: a removed file never deletes its object.
6. Decide on the watch: keep the 1000 ms default, set another interval, or set 0 to replay the folder at startup only.

Every start logs the warning `sync_retired_files` while a manifest remains or `sync-conflicts/` holds entries, and `--log-level error` hides it, so a quiet log does not mean the files are gone. See [files left by directory synchronization](../container-usage.md#files-left-by-directory-synchronization).

## Changes

### Live seed directory

- While the server runs, a pass walks `seed_dir` every `seed_watch_interval_ms` and commits what it found in one short transaction. It republishes a changed file, publishes a new one, creates the bucket of a new top-level directory, and deletes the object of a removed file as above. Passes never write to the folder. See [passes while the server runs](../slices/seed.md#passes-while-the-server-runs).
- A pass leaves what it cannot replay as it is and reports it: an unusable entry, a file past `max_object_bytes`, a directory past `max_buckets_per_batch`, an object a hold or retention period protects, and a directory whose bucket name belongs to another project. A walk that failed or stopped at `max_seed_entries` or `max_seed_depth` proves nothing absent, so that pass deletes nothing.
- A name whose lookup cannot decide (always on Windows, where nothing proves a file absent, and on Unix for example after a permission error) never deletes its object. It is reported only while seeding purely owns the live object (the owned version is the live version and the body matches): as a pass problem, or as `seed_skipped` at startup and on a reseed. Otherwise the record becomes a tombstone, counted in `tombstones` and not reported. On Windows the report stops when the file returns, when the API deletes, overwrites or edits the object, or on a reset.
- Passes never forget a bucket mark, on any platform. A bucket the API deleted, or deleted and created again, stays untouched by passes even if its directory goes away and comes back, so the API's deletion stands and a recreated bucket keeps its content. Only a restart or a reseed replays such a directory; startup and reseed drop the marks of unlisted directories.
- A pass that meets a bucket of another project under a directory's name reports a problem and skips the directory; startup still fails.
- A failed deletion, such as a full disk, during a replay or a pass fails with its cause and changes nothing.
- Passes emit no bucket notifications, like a startup replay. A pass that panics makes `/_internal/healthcheck` report not ready until a replacement pass, which starts at once, completes; a pass that ends with an error still counts as running and keeps the server ready.
- A pass that cannot run emits the warning `seed_pass_failed` on stderr, with the pass number as `pass` and the whole chain of causes as `cause`. It warns once when passes start failing and again only when the failure's reason changes; when a pass succeeds again, the info-level `seed_pass_recovered` reports it with the number of failed passes as `failed_passes`. `GET /_internal/seed` still shows every pass. `--log-level warn` hides `seed_pass_recovered`, and `--log-level error` hides both.
- A problem's `reason` and the report's `error` are sentences, for example "the file changed while it was read: its size, modification time changed", "the catalog stayed busy" or "the disk under data_dir is full".
- With `admin_enabled`, `GET /_internal/seed` reports whether passes run, their interval and the last pass, and `POST /_internal/seed/wait` starts a pass at once and answers the report of the first pass that started after the request and left no removed file waiting for its second proof, so `pendingDeletions` is 0. It answers 400 `invalid` when no passes run, and 503 with `Retry-After: 1` when the time runs out ("No pass over seed_dir finished within N ms without a removed file waiting for its second proof; retry, or wait longer with timeoutMs") or the server closes ("The server is closing, and no further pass over seed_dir runs"). A pass report carries counts, the first 100 problems with their paths, and whether the walk was complete and clean.
- `gcs-mimic seed status` and `gcs-mimic seed wait [--timeout DURATION] [--require-clean]` call those routes and print the answer as one JSON line. `seed wait` exits 1 when the pass has an error or is not complete, and with `--require-clean` when it is not clean, so a test setup can wait for its fixtures after editing the folder.

### Removed synchronization

- The catalog drops the synchronization tables and the change journal at schema 58, writes `sync-retired.json` when rows still named user bytes, and never deletes `sync-conflicts/`.
- Startup refuses a seed directory that still holds the synchronization marker or workspace, as described above.

## Fixes

- A reseed or a reset to the startup state that finds a seed directory replaced during the walk, or a fixture that keeps failing to open, answers 503 with `Retry-After: 1` and changes nothing, so the next attempt reads the tree as it is then. A seed root or directory replaced during the walk answered 409 in 0.27.0 and said that import state was active, which was false. At startup the same failures stop the server with the unreadable-fixture guidance.
- A fixture removed after its directory was listed is skipped with a `seed_skipped` warning ("removed after its directory was listed") and the rest of the tree is replayed, instead of the removal passing without a trace.
- A fixture modified in place while a startup replay or reseed walks the tree publishes the new bytes it holds when it is read, as 0.27.0 did; a file that changes during the read itself still fails the attempt as a changed source.

## Compatibility and migration

The catalog schema moves from 57 to 59 when 0.28.0 first opens a data directory of 0.8.0 through 0.27.0, and the migration is one way. A 0.27.0 binary cannot open the result. `GET /_internal/seed`, `POST /_internal/seed/wait` and `gcs-mimic seed` are additions; the routes need `admin_enabled` and answer 404 without it, like the other management routes.

The Go packages accept a binary of the same minor release, so upgrade the Go module together with the binary.

## Known limitations

- The watch polls. A change reaches the catalog within about `seed_watch_interval_ms` plus the time one pass takes, and a removal later still, because its second proof must come from the very next pass, at least a second after the first. Use `gcs-mimic seed wait` to wait for it instead of sleeping.
- A pass reads a file again where its identity, size or times differ from what seeding recorded. On a filesystem with coarse timestamps, such as FAT or exFAT, an edit that keeps the size and restores the modification time can be missed until a reseed or a restart replays the folder.
- A removed file never deletes its object on native Windows.
- Renaming a file only by case on a case-insensitive filesystem, such as the macOS and Windows defaults, publishes the new name and keeps the object of the old one, because a lookup of the old name still finds the file. Delete that object through the API or reset.
- `--log-level error` hides the `sync_retired_files` warning.
- The pass tests ran on one macOS ARM64 host. Linux and Windows hosts, container bind mounts and network or case-insensitive filesystems have no recorded run of them yet; the [seed slice](../slices/seed.md) lists them as pending.
- The limitations listed for [0.27.0](0.27.0.md#known-limitations) still apply, and these changes do not close the [1.0.0 gate](../release-policy.md#the-100-gate).
