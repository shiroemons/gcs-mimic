# gcs-mimic 0.2.1

0.2.1 makes catalog schema upgrades visible: a data directory written by a
newer release is rejected with recovery instructions, and an upgrade migration
is logged. It publishes `ghcr.io/shiroemons/gcs-mimic:0.2.1` for `linux/amd64`
and `linux/arm64` and native archives for all eight macOS, Windows and Linux
targets. The [0.2.0 release notes](https://github.com/shiroemons/gcs-mimic/blob/v0.2.0/docs/en/releases/0.2.0.md)
describe the gRPC listener, bucket and object policies and HTTP/1.1 behavior;
the [feature matrix](../feature-matrix.md) lists the exact supported subsets.

## Changes

- Starting with a data directory whose catalog schema is newer than the
  release supports now fails with a `data_dir` diagnostic that names the
  stored and supported schema versions and the ways to recover: run a release
  that supports the schema, restore a backup taken before the upgrade, or use
  a different data directory. It previously reported only
  `catalog unavailable or already in use`. The catalog file is not modified.
- Migrating a data directory from an older schema logs one `info` event,
  `catalog_schema_migrated`, with `from` and `to` versions before `ready`.
  New and already current data directories log none, and a `log_level` of
  `warn` or `error` hides it.
- Release build jobs keep Windows test files on the workspace volume and build
  their test binaries with line tables only.

## Compatibility and migration

No migration is required. The data-directory schema remains
`PRAGMA user_version = 27`, shared with 0.2.0, so 0.2.0 and 0.2.1 open each
other's data directories. Only 0.2.1 and later explain a newer schema; 0.2.0
and 0.1.x still report `catalog unavailable or already in use`. Upgrading from
0.1.x migrates schema 21 to 27 as described in the 0.2.0 notes; back up the
data directory first.

## Verification

The [release workflow](https://github.com/shiroemons/gcs-mimic/blob/v0.2.1/.github/workflows/binaries.yaml)
creates this Release only after `validate`, including the dependency freshness
check, Foundation and all eight native build/test jobs succeed at the tag's
SHA. The
[container workflow](https://github.com/shiroemons/gcs-mimic/blob/v0.2.1/.github/workflows/ghcr.yaml)
then builds both Linux architectures natively, verifies their SBOM and
provenance, publishes the multi-architecture tag and checks anonymous pulls.
