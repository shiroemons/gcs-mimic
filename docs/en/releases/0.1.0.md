# gcs-mimic 0.1.0

The 0.1.0 behavior baseline is `fa7c3bb`. The commit named by `v0.1.0` adds
only these notes and documentation corrections on top of it; the protected
application, test, build and distribution inputs are identical to the baseline.
See the [final candidate check](https://github.com/shiroemons/gcs-mimic/blob/v0.1.0/docs/en/evidence/dist-release-notes.md#final-tag-candidate).
The [release contract](https://github.com/shiroemons/gcs-mimic/blob/v0.1.0/docs/en/slices/dist-release-notes.md#publication-contract-inputs-and-final-notes)
identifies the publication checks and their owners.
Archives and `SHA256SUMS` are attached to this Release; container
digests and anonymous pulls are checked after image publication under the
[distribution contract](https://github.com/shiroemons/gcs-mimic/blob/v0.1.0/docs/en/container-distribution.md).

## Included workflows

- Persistent multiple-bucket JSON CRUD, prefix/paginated listing, bucket labels
  and default storage class PATCH/PUT, versioning and default event-based holds
  in the documented subsets.
- Bounded object media, multipart and resumable uploads; metadata and byte-range
  reads, listing, updates, deletion, copy, compose and multi-call rewrite.
  Supported generation/metageneration conditions and checksums protect mutation
  publication. Version history persists across restarts. Concurrent uploads are
  not capped separately: beyond `max_connections` they wait instead of failing.
- Explicit permissive and strict local authentication profiles, registered test
  principals and scoped bucket IAM enforcement. Public URL construction does
  not grant access; `allUsers` and `allAuthenticatedUsers` remain distinct.
- XML object GET/HEAD/PUT, V4 RSA query signing and validation, configured
  virtual-host suffixes, two response-header overrides, public access prevention
  and separate JSON/XML CORS behavior, within their recorded contracts.
- HTTP, local HTTPS or both listeners together; CLI/environment/JSON
  configuration with log-level filtering; health/readiness probes and a
  container healthcheck that follows the configured scheme and listener;
  disk-backed SQLite metadata and opaque blob files; and non-root Linux
  containers for `linux/amd64` and `linux/arm64`.
- A versioned bucket initialization file (`GCS_MIMIC_BUCKETS_FILE`) that
  creates missing buckets on every start while preserving existing settings,
  and a one-time `BUCKET/OBJECT` seed directory for a fresh catalog.
- `gcs-mimic import fake-gcs-server` converts a stopped fake-gcs-server
  filesystem snapshot (sidecar or xattr metadata) into a new data directory,
  preserving live object bytes, generations, checksums and timestamps, with
  `--dry-run` inspection and resumable progress.
- A [fake-gcs-server Compose replacement guide][migration] and pinned Go and
  Ruby SDK checks of a representative application flow, plus the existing
  scoped HTTPS/browser journeys. These establish the documented subsets, not
  full SDK or Rails compatibility.

The [feature matrix][matrix] and linked slice contracts define
the exact supported scope and deviations. A working workflow does not promote
its entire Google API method to IMPLEMENTED. This independent emulator does not
provide Google's infrastructure, identity issuance or durability SLA.
The [release-scope evidence table](https://github.com/shiroemons/gcs-mimic/blob/v0.1.0/docs/en/evidence/dist-release-notes.md#first-useful-release-and-included-workflow-mapping)
maps the first-release roadmap requirements to ledger rows, statuses and
executed evidence.

## Compatibility and migration

This is the first product release; **no migration from an earlier released
gcs-mimic version is required**. Existing development data is not disposable:
preserve backups and use the matching configuration when upgrading a development
checkout. This release introduces no catalog reset.

The 0.1.0 data-directory baseline is `catalog.sqlite3` with SQLite
`PRAGMA user_version = 21`. The schema number is independent of product version
0.1.0. Startup upgrades compatible schemas 0–20 in place, except unreleased
intermediate schema 2, which is rejected because deleted generation history
cannot be recovered; future schemas, incompatible schemas and corrupt catalogs
are also rejected, and version 0 must be empty.
Future 0.x releases must provide and test a documented forward-upgrade path from
this baseline, preserving stored data; required migrations and backup steps must
be stated before upgrade. They must never silently reset an existing data
directory. This is the release's upgrade obligation, not a claim that future
schemas are implemented. Downgrade compatibility is not promised. Before an
upgrade, stop the server cleanly and back up the entire data directory, including
its catalog, any WAL files and blobs, as one consistent set.

fake-gcs-server is a migration source, not an earlier version of this product.
Its flags, environment and persisted backend are not interchangeable with
gcs-mimic. Use the [migration guide][migration] and explicit
`GCS_MIMIC_*` settings. Startup rejects fake-gcs-server flags and the known
`FAKE_GCS_*` environment variables with the replacement setting, and warns on
unknown `FAKE_GCS_*` names. The `legacy-emulator` profile covers only its
documented compatibility subset. Where the representative application flow
differs from fake-gcs-server `v1.56.1` (copy replay returns 412, a cancelled
resumable session returns 499 and then 410, CORS headers), gcs-mimic follows
the Google contract; see the
[recorded comparison](https://github.com/shiroemons/gcs-mimic/blob/v0.1.0/docs/en/slices/migrate-app-scenario.md#source-comparison).

The current config file is the flat JSON
[`config/development.json`][config]; TOML is a future
design example. Precedence is CLI > `GCS_MIMIC_*` environment > JSON > defaults.
HTTPS is the default; the HTTP quick start explicitly selects HTTP.
Strict signing binds the final externally visible host, path, query, method and
required headers. Preserve the documented SDK endpoint/signing adaptations.

Later configuration compatibility changes and directory synchronization ship
as separate 0.x releases. Compatible fixes use patch versions; breaking 0.x
changes use a new minor. See the
[version policy](https://github.com/shiroemons/gcs-mimic/blob/v0.1.0/docs/en/release-policy.md).

## Platform verification

The [release workflow](https://github.com/shiroemons/gcs-mimic/blob/v0.1.0/.github/workflows/binaries.yaml)
creates this Release only after its `validate`, reusable Foundation and all
four native Linux build/test matrix jobs succeed at the tag's SHA. These gates
cover:

- Version and release-notes file checks, and dependency freshness.
- Pinned Rust and current-stable checks, including generated-document checks
  and type checks of the Windows, musl and macOS targets.
- Native Linux AMD64 (`ubuntu-24.04`) and ARM64 (`ubuntu-24.04-arm`)
  container build/smoke checks and the pinned Go SDK suite.
- Native Linux GNU and musl ARM64 and x86-64 build/test execution in the
  [target matrix](https://github.com/shiroemons/gcs-mimic/blob/v0.1.0/docs/en/binary-distribution.md#target-matrix).
  The publishing job checks every checksum and remote tag identity before
  creating the Release.

The [pre-tag evidence](https://github.com/shiroemons/gcs-mimic/blob/v0.1.0/docs/en/evidence/dist-release-notes.md#final-tag-candidate)
records the pre-tag run of the same workflow separately from these final gates.
Historical local [onboarding](https://github.com/shiroemons/gcs-mimic/blob/v0.1.0/docs/en/evidence/container-onboarding.md)
uses native ARM64 and emulated AMD64 Docker Desktop; it does not establish
native archive verification.

## Known limitations

- **0.1.0 ships Linux archives and `linux/amd64`/`linux/arm64` images only.**
  macOS and Windows archives are not published: their native test suites fail
  on GitHub runners (macOS TLS tests; several Windows catalog tests and a test
  process abort). Use the container image on macOS and Windows hosts. The
  macOS and Windows recovery notes below describe the intended scope for when
  those archives return.
- Directory synchronization is incomplete and not supported in 0.1.0. The
  `sync_dir` setting only exports API objects to a directory; external
  file edits are not imported and no status or recovery command exists. Do not
  enable it. One-time seed loading reads `BUCKET/OBJECT` bytes and does not
  replay on later starts; the bucket initialization file is the way to add
  buckets later.
- Source import covers live objects of the fake-gcs-server filesystem backend.
  Memory-backend state, archived versions, ACLs and retention are not imported.
- gRPC is unavailable, including fake-gcs-server's Storage v1 subset, as are
  Go embedding and an in-memory backend. Complete reference parity, ACLs/UBLA
  transitions, broader Google API coverage and Rails Active Storage integration
  remain incomplete.
- Strict authorization uses local test identities. Signing/error/query edge
  parity and SDK endpoint/hash caveats remain documented gaps. Parent public
  access prevention is LOCAL_SIMULATION. Do not use permissive authentication
  as a security boundary.
- Windows' intended recovery scope is normal restart and process termination,
  using file flushes, write-through blob publication and SQLite WAL/FULL.
  Windows directory namespace durability after OS crash or power loss is not
  guaranteed; native recovery/control-event checks are part of release CI.
- macOS ARM64 evidence covers normal restart and selected forced-termination
  publication boundaries. It does not establish every fsync/deletion window,
  macOS Intel execution, OS-crash recovery or power-loss durability. Unix
  directory fsync and SQLite WAL/FULL are not evidence of tested power loss.
  Missing committed blobs block readiness rather than silently losing entries.
- Daily dependency detection ran on every day from 2026-10-22 to 2026-10-25,
  including the weekend; the weekly exception-review cycle has not been
  exercised. Foundation CI runs pinned and current-stable Rust, but no build
  from automatically updated dependency candidates exists.
- Ruby SDK checks require the pinned local Ruby and gem graph. Foundation CI
  runs Go but has no Ruby SDK lane.
- One local measurement on Linux ARM64 Docker Desktop (source `bb8dd5c`,
  128 MiB memory limit, one CPU) recorded idle process RSS up to 8.7 MiB and
  cgroup memory up to 3.9 MiB, and 1 GiB media and resumable transfers with
  process RSS up to 9.8 MiB, no transfer error and no OOM kill. Cgroup memory
  reached the limit through file cache during transfers. Upload CPU was 4.4 s
  (media) and 6.6 s (resumable) per GiB. See the
  [measurement](https://github.com/shiroemons/gcs-mimic/blob/v0.1.0/docs/en/evidence/dist-resource-measurement.md).
  It was not repeated on the release source or AMD64, and no comparative
  performance claim is made.
- Native binaries are unsigned and macOS archives are not notarized. Packaging
  checksums and container SBOM/provenance do not supply code signatures,
  vulnerability scanning or byte-identical rebuild guarantees.
