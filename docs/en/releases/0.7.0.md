# gcs-mimic 0.7.0

0.7.0 makes gcs-mimic a drop-in replacement for an existing fake-gcs-server
deployment: the image name is the only required change, and fake-gcs-server
flags and `FAKE_GCS_*` variables now start the server with a warning instead
of stopping it. It also adds a verified Rails Active Storage setup for
development and test, and SDK setup for Go, Ruby, Node.js, Python and PHP.
It publishes `ghcr.io/shiroemons/gcs-mimic:0.7.0` for `linux/amd64` and
`linux/arm64`, mirrors the same digest to Docker Hub as
`shiroemons/gcs-mimic:0.7.0`, and publishes native archives for all eight
macOS, Windows and Linux targets. The [0.6.0 release notes](0.6.0.md) describe
the previous published release; the [feature matrix](../feature-matrix.md)
lists the exact supported subsets.

## Changes

### fake-gcs-server settings

- `serve` translates fake-gcs-server flags (one or two hyphens) and the known
  `FAKE_GCS_*` variables that have a native equivalent: scheme, host and port,
  HTTP port, external URL, public host, data, TLS files, CORS headers,
  location and log level. Each one logs a warning naming its `GCS_MIMIC_*`
  replacement. A flag outranks a variable, as in fake-gcs-server, and within
  one source a translation overrides a native value with a warning, so the
  image's own `GCS_MIMIC_LISTEN` does not defeat an existing `FAKE_GCS_PORT`.
- A command line that starts with a fake-gcs-server flag runs `serve`, so a
  Compose `command` written for fake-gcs-server works unchanged.
- `-backend memory` and `-filesystem-root` only warn. Data is kept in
  `GCS_MIMIC_DATA_DIR`; `-filesystem-root` is not used as the data directory,
  because a reused fake-gcs-server volume is owned by root and the image runs
  as UID 10001.
- Event settings (`-event.*`, `FAKE_GCS_EVENT_*`) and unknown backends still
  stop startup, so a test that waits for notifications fails visibly.
- Helper commands such as `healthcheck` and `url` still reject legacy names.

See [legacy setting aliases](../slices/legacy-setting-aliases.md).

### Container healthcheck

- When gcs-mimic runs as PID 1, as in the image, and the probe derived from
  the environment fails, `gcs-mimic healthcheck` retries with the server's own
  command-line options, so a Compose `command` such as `-scheme http` no
  longer leaves the container unhealthy. Ordinary setups never read them.
  On Apple Silicon, a read-only amd64 container under Rosetta cannot use this
  fallback, because Rosetta needs a writable root to emulate the process's
  `/proc` entry; use the native arm64 image or `GCS_MIMIC_*` variables there.

### Authentication

- In strict mode, an unknown bearer token shaped like a JWT, such as the
  self-signed token googleauth sends for a non-Google `universe_domain`, logs
  one `auth_self_signed_jwt_rejected` warning per process. The `401 Invalid
  Credentials` response is unchanged, and the token is not logged.

### Documentation

- [Rails Active Storage](../rails-active-storage.md): one `config/storage.yml`
  entry with a non-Google `universe_domain` lets Active Storage use the
  emulator in development and test without contacting Google OAuth, while
  production keeps its own entry. The page covers the bucket file with CORS,
  Rails in Compose with the `gcs.localhost` alias, and CI.
- [SDK setup](../sdk-setup.md) gives copyable Go, Ruby, Node.js, Python and PHP
  settings and notes where `STORAGE_EMULATOR_HOST` differs between SDKs.
- The README was rewritten around the quick start, Compose, SDK setup and
  migration. The quick start now retries the first request with
  `--retry-all-errors`, because the published port can return an empty reply
  right after `docker run`.

### SDK tests

- `just check-active-storage` adds `attachments.rb`, which checks the
  documented `storage.yml` entry through a `has_one_attached` model: uploads,
  URLs, redirect and proxy serving, V2 and V4 direct uploads with
  browser-equivalent CORS requests, no OAuth request 400 days after startup,
  and a production boot that generates no key.

## Compatibility and migration

0.7.0 uses the same catalog schema, 35, as 0.6.0, so a data directory from
0.6.0 needs no migration. Upgrading from 0.4.1 or earlier also applies the
[0.5.0 migration](0.5.0.md#compatibility-and-migration).

- fake-gcs-server flags and `FAKE_GCS_*` variables that stopped startup in
  0.6.0 now start the server and warn. Remove them, or rename them to the
  `GCS_MIMIC_*` names in the warnings, to silence the warnings.
- Within one source, a `FAKE_GCS_*` value now overrides a `GCS_MIMIC_*` value
  for the same setting. Remove one of them if both are set.
- Rails apps that followed the earlier application-built Active Storage recipe
  should switch to the `storage.yml` entry: the earlier recipe's one-day token
  expiry made googleauth try to refresh at Google after a day.

## Verification

The [release workflow](https://github.com/shiroemons/gcs-mimic/blob/v0.7.0/.github/workflows/binaries.yaml)
creates this Release only after `validate`, including the dependency freshness
check, Foundation and all eight native build/test jobs succeed at the tag's
SHA. The
[container workflow](https://github.com/shiroemons/gcs-mimic/blob/v0.7.0/.github/workflows/ghcr.yaml)
then builds both Linux architectures natively, verifies their SBOM and
provenance, publishes the multi-architecture tag and checks anonymous pulls,
and the Docker Hub workflow mirrors that digest.

Before the release commit, the pre-push checks passed locally on macOS: format,
clippy, cross-compilation checks including the Linux glibc target, all 49 Rust
test binaries and doctests, the compatibility ledger check, the pinned Go,
Ruby, Node.js, Python and PHP SDK suites, and both Linux container smoke
tests. The release-input freshness check
(`cargo xtask dependencies check --scope release`) reported every input
current.

The first pre-push run failed the `linux/amd64` container smoke test: on Apple
Silicon, Rosetta crashed the healthcheck while it read `/proc/1/cmdline` on the
read-only root, and the published 0.6.0 image stayed healthy in the same
setup. The healthcheck now reads PID 1's options only after the environment's
probe fails, and the complete pre-push run passed on the final source.

`just check-active-storage`, which is not part of the pre-push checks, passed
its storage.yml cases (10 PASS) and production check; its scenario still
reports the known default-authentication failure of an entry without
`universe_domain`, as in earlier releases. A Rails app with Puma was checked
in Chrome with Rails on the host and in Compose; see the
[Active Storage scenario](../slices/sdk-active-storage-scenario.md#storageyml-emulator-recipe).
