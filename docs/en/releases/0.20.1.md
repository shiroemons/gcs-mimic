# gcs-mimic 0.20.1

0.20.1 lets `@google-cloud/storage` 9.0.0, the new major release of the official Node.js client, delete and list objects. objects.delete and objects.list now ignore query parameters they do not declare, as Cloud Storage does; 0.20.0 answered 400. No command, option, environment variable, default or machine-readable output changes, and no setting or data needs attention when upgrading from 0.20.0.

It publishes `ghcr.io/shiroemons/gcs-mimic:0.20.1` for `linux/amd64` and `linux/arm64`, mirrors the same digest to Docker Hub as `shiroemons/gcs-mimic:0.20.1`, and publishes native archives for all eight macOS, Windows and Linux targets. The [feature matrix](../feature-matrix.md) lists the exact supported subsets.

## Changes

### Undeclared query parameters on objects.delete and objects.list

`@google-cloud/storage` 9.0.0 sends `File#delete` with `responseType=text` and the source of its `validateStatus` function as query parameters, and `Bucket#getFiles` with `autoPaginate`. 0.20.0 answered both with 400 `Unknown query parameter for this method`, so the client could neither delete nor list objects, and helpers built on them, such as `Bucket#deleteFiles`, failed too.

Recorded against Cloud Storage, objects.delete deleted the object with those parameters and with `projection=noAcl`, and objects.list answered 200 with `autoPaginate=false` and an arbitrary name. fake-gcs-server v1.56.1 reads only the parameters it knows on both routes. Both profiles now ignore an undeclared name on these two methods.

- Standard parameters that gcs-mimic does not implement, such as `userProject`, `quotaUser` and `callback`, are still rejected with 400 `badRequest`.
- A declared parameter with a malformed value, such as `generation=x`, is still rejected.
- The other object methods keep the 400 for an undeclared name; Cloud Storage's treatment there is not recorded yet.

### Node.js client setup

`@google-cloud/storage` 9.0.0 and 8.4.0 are both tested; every stage of the Node.js suite runs on each. 9.x sends every request through its auth client, even for a custom `apiEndpoint`. Without credentials it fails with `Could not load the default credentials`; where Application Default Credentials exist, it fetches a real access token from Google and sends it to the emulator. Pass `authClient: new PassThroughClient()` from `google-auth-library`, which works on 8.x too:

```js
import {Storage} from '@google-cloud/storage';
import {PassThroughClient} from 'google-auth-library';

const storage = new Storage({projectId: 'local-project',
  apiEndpoint: 'http://localhost:4443', authClient: new PassThroughClient()});
```

9.0.0 also no longer sends a `userProject` given to `storage.bucket()` on `getFiles`; pass it to the call. The [SDK setup guide](../sdk-setup.md#nodejs) describes both.

## Compatibility and migration

The catalog schema is unchanged at 53, so a data directory moves between 0.20.0 and 0.20.1 in either direction without a migration. A request that 0.20.0 refused with 400 now succeeds on these two methods; nothing that succeeded before changes.

A `gcs-mimic sync` command and the server it manages must still be the same release, so upgrade both together. The Go package accepts a binary of the same minor release, so `go/fakestorage` from 0.20.0 and 0.20.1 works with either binary.

## Dependencies and project

- No Rust dependency, Rust toolchain, container base or build tool changes. The package version and the Go package's `moduleVersion` move to `0.20.1`, and the recipes pin `0.20.1`.
- The official Node.js SDK suite, scorecard and Testcontainers check move to `@google-cloud/storage` 9.0.0. The suite keeps 8.4.0 in `sdk-tests/node/storage-8`, which the daily dependency check compares with the newest 8.x release only.
- The Go SDK suite, scorecard and facade move to google.golang.org/api v0.314.0.
- The [differential reference](../../../compatibility/differential/reference/gcs.json) gains the two Cloud Storage recordings, cases `obj-delete-undeclared-query` and `obj-list-undeclared-query`.

## Known limitations

- The released-data fixtures for 0.20.1 are added after publication, as for earlier releases.
- The limitations listed for [0.20.0](0.20.0.md#known-limitations) still apply, and these changes do not close the [1.0.0 gate](../release-policy.md#the-100-gate).
