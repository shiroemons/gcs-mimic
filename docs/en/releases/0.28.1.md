# gcs-mimic 0.28.1

0.28.1 fixes how the server treats gzip-compressed request bodies, XML multipart aborts, escaped resumable session keys and connections that close after their reply, and brings each of them closer to Cloud Storage. No command, option, environment variable, default or machine-readable output changes, and no setting or data needs attention when upgrading from 0.28.0.

The [feature matrix](../feature-matrix.md) lists the exact supported subsets.

## Fixes

### Compressed request bodies

Cloud Storage's front end expands a body sent with `Content-Encoding: gzip` before it routes or authenticates the request, as the [transport gzip observations](../evidence/transport-gzip-provider-observations.md) record from 2026-11-25. 0.28.0 checked the caller first, so a refused caller got 401 or 403 for a body that does not decode. A caller who got through received a JSON error instead of Cloud Storage's text page, and a member whose trailer CRC-32 or size disagreed with the data was refused.

- JSON API bodies and the metadata of a resumable initiation are now expanded before dispatch. A body that does not decode answers 400 with the `text/plain; charset=utf-8` text `Could not decompress request body.`, whoever sends it and whatever route it names, with the CORS headers of a CORS route. A body that decodes meets the same checks, in the same order, as the same body sent plain.
- Each member's header, deflate data and trailer must be complete, but the trailer's CRC-32 and size are no longer compared with the data, as on Cloud Storage. An empty body is not decoded.
- A media or multipart upload body still streams to its handler. Its first bytes are checked before dispatch, so a body that does not start a gzip member answers 400 before the caller is checked. A failure later in the body replaces the handler's answer with the same 400 once the handler reads it.
- A body is expanded before its caller is authorized, so the decoder permits are now split by authentication, which reads only the headers and the query. Callers who authenticate, and every caller in permissive mode, share the `ceil(max_blocking_threads / 4)` permits as before. Anonymous callers on the public listener and callers whose credentials fail share one permit of their own, so in strict mode they cannot hold back the callers who authenticate.

### XML multipart uploads

- An abort no longer waits for the parts still being uploaded. 0.28.0 waited behind a part whose body had stalled for up to `catalog_wait_timeout_ms` and then answered 503. Now the abort retires the upload at once and answers 204, as Cloud Storage does. Each part still streaming then fails with 404 `NoSuchUpload` when its commit finds the upload gone, and its staged bytes are reclaimed. A completion still waits for the parts in flight; a completion and an abort wait for each other.
- `NoSuchUpload` on a part, completion or listing of an aborted or unknown upload now says `The requested upload was not found.`, Cloud Storage's wording, instead of `The multipart upload does not exist`. The code and status are unchanged.

### Resumable uploads

- An initiation whose query spells the session key with an escape, `upload%5Fid`, now names that session, as on Cloud Storage, and answers 404 when the session does not exist. 0.28.0 started a new session. A key that does not decode names no session.

### Request deadlines and connections

- With `body_inactivity_timeout_ms` set, only the time the server waits for the next chunk of a request body counts as the client's silence. The server's own work on a chunk, such as a write that waits for a busy disk, is now the handler's time under `request_timeout_ms`, which each chunk starts again. 0.28.0 could answer 408 `uploadBrokenConnection` to a client that kept sending.
- When a catalog wait ends because `object_request_timeout_ms` ran out before `catalog_wait_timeout_ms`, the 503 now names the upload finalization timeout and advises `object_request_timeout_ms`, instead of advising a larger `catalog_wait_timeout_ms` that could not help. The status stays 503 `backendError`.
- A server at `max_connections` closes, for each waiting client, the connection that turned idle first. A connection now takes its place in that line when its response ends, rather than when its watch task next runs, so a busy runtime no longer closes a younger idle connection while an older one keeps its slot.
- A connection that closes after its reply, a timeout reply or an error response to a request that carried a body, no longer joins the idle line. 0.28.0 could hand it to a waiting client, which closed it before its lingering close, so a client still sending the rejected body could lose the error reply to a reset. Such a reply and its close are bounded by the five-second close budget. See the [deadline table](../design.md#implemented-foundation-and-extension-boundaries) and the [connection semantics evidence](../evidence/http-connection-semantics.md#idle-line-order-and-request-body-silence-verified-2026-11-24).

### Seed directory

- A seed pass that shutdown interrupts no longer warns with `seed_pass_failed` or counts as a failed pass. A pass that meets an unhealthy catalog still warns.
- A panic while walking `seed_dir` is reported before the import fails on it, so a seed that fails at startup logs the panic before the process exits.

## Compatibility and migration

The catalog schema is unchanged at 59, so a data directory moves between 0.28.0 and 0.28.1 in either direction without a migration.

The changed answers correct behavior to match Cloud Storage and need no change to a documented integration. A refused caller whose compressed JSON body does not decode now gets 400 instead of 401 or 403. A gzip member with a mismatched trailer is accepted. An abort answers 204 at once, and a part in flight answers 404 instead of the abort answering 503. An `upload%5Fid` initiation names its session. Human-readable messages changed for `NoSuchUpload` and the catalog wait 503; the [release policy](../release-policy.md#product-version-and-compatibility) does not cover message wording.

The Go packages accept a binary of the same minor release, so the Go module of 0.28.0 and of 0.28.1 works with either binary.

## Known limitations

- A media or multipart upload whose caller the handler refuses before it reads the body keeps that refusal (401 or 403) when the body starts a gzip member but is cut short later. Cloud Storage reads the body and answers 400. The [transport gzip observations](../evidence/transport-gzip-provider-observations.md#known-differences) list this and the other known differences.
- The released-data fixture for 0.28.1 and the Go module's `SHA256SUMS` for 0.28.1 are added after publication, as for earlier releases. Until `go/v0.28.1` is tagged, a Go module revision between this release and that commit cannot download its binary; set `GCSM_BINARY` there.
- The limitations listed for [0.28.0](0.28.0.md#known-limitations) still apply, and these changes do not close the [1.0.0 gate](../release-policy.md#the-100-gate).
