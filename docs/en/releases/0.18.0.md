# gcs-mimic 0.18.0

0.18.0 starts executing stored lifecycle rules and makes the breaking changes that the [public contract review](../public-contract-review.md) decided before the 1.0.0 freeze. Stored `Delete`, `SetStorageClass` and `AbortIncompleteMultipartUpload` rules now act on objects and uploads, including rules stored by earlier releases. fake-gcs-server flags are either translated exactly or refused, seven environment variables used by clients, the sync CLI and Compose move to `GCSM_*`, and the ready event drops two fixed fields and reports the data directory. Read [Breaking changes](#breaking-changes) and the [upgrade checklist](#upgrade-checklist) before upgrading from 0.17.1: the catalog schema changes and a downgrade needs a backup.

It publishes `ghcr.io/shiroemons/gcs-mimic:0.18.0` for `linux/amd64` and `linux/arm64`, mirrors the same digest to Docker Hub as `shiroemons/gcs-mimic:0.18.0`, and publishes native archives for all eight macOS, Windows and Linux targets. The [feature matrix](../feature-matrix.md) lists the exact supported subsets. Rows marked `PARTIAL` keep their listed missing cases.

## Breaking changes

### fake-gcs-server flags

A flag copied from a fake-gcs-server command line is now accepted only when every request that worked because of it gives the same result in gcs-mimic; serving more requests than fake-gcs-server is allowed. Any other flag stops startup with exit status 1 and an `error` diagnostic keyed by the flag as you typed it, which names the native replacement. All refused flags are reported together, before a catalog is opened or a ready event is written.

| Flag | 0.17.1 | 0.18.0 | What to edit |
| --- | --- | --- | --- |
| `--filesystem-root PATH` | Ignored with a warning | Refused | Remove it. Store data with `--data-dir PATH` (`/var/lib/gcs-mimic` in the image); convert a stopped fake-gcs-server data directory with `gcs-mimic import fake-gcs-server --source DIR --data-dir NEW` |
| `--external-url URL` | Became `api_base_url` | Refused | Replace it with `--api-base-url URL`, using an address every client can reach, or omit it so links follow each request |
| `--cors-headers HEADERS` | Discarded the list and selected `cors_fallback=allow-all`, also in strict mode | Refused in every authentication mode | Remove it. Permissive mode already allows every origin on buckets without rules; add `--cors-fallback allow-all` only if you need that in strict mode, or set `cors` on the buckets |
| `--location LOCATION` | Became `default_location` | Refused | Replace it with `--default-location LOCATION`. It applies only to new buckets without an explicit location |
| `--event.*` without a Pub/Sub emulator host | Reached native validation | Refused | Set `PUBSUB_EMULATOR_HOST` or `--pubsub-emulator-host HOST:PORT`, or remove the flags. gcs-mimic never publishes to Google |
| `--event.list none` | Disabled the global rule | Refused, because fake-gcs-server has no such value | Use native `--event-list none` |
| `--port-http N` without `--scheme both` | Ignored with a warning | Startup fails | Add `--scheme both`, or remove the unused port |

`--host`, `--port`, `--port-http`, `--scheme` and `--log-level` are native options and print no notice. `--backend filesystem`, `--public-host`, `--data`, `--cert-location`, `--private-key-location` and the `--event.*` flags with an emulator host keep their translations. Instead of per-flag warnings, startup now prints one `info` diagnostic with key `native_equivalent`. Its `native_args` array holds the complete native options; pass each element as one argument. When no value contains a quote, backslash or control character, its `fix` text also ends with a shell line you can copy. `--log-level warn` or `error` hides this notice. Extract the array with jq:

```sh
jq -c '.diagnostics[]? | select(.key == "native_equivalent") | .native_args' server.log
```

`--public-host` has one documented difference: a request to a subdomain of the public host is treated as a virtual-hosted bucket. Send JSON API requests to a host outside those subdomains, or set `--api-base-url`. The [option aliases](../slices/option-aliases.md#behavior) list every flag and the reason each refused flag cannot be translated.

### Environment variable names

The server reads `GCS_MIMIC_*`; every other program in this project reads `GCSM_*`. The server still stops on an unknown `GCS_MIMIC_*` name and ignores every `GCSM_*` name, so an application and the emulator can share one `.env` file.

| Old name | New name | Used by |
| --- | --- | --- |
| `GCS_MIMIC_ENDPOINT` | `GCSM_ENDPOINT` | Client examples and SDK harnesses |
| `GCS_MIMIC_GRPC_ENDPOINT` | `GCSM_GRPC_ENDPOINT` | Rust client example and SDK harness |
| `GCS_MIMIC_SYNC_TOKEN` | `GCSM_SYNC_TOKEN` | `gcs-mimic sync`; `--token-file` takes precedence |
| `GCS_MIMIC_BINARY` | `GCSM_BINARY` | Go subprocess package |
| `GCS_MIMIC_PORT` | `GCSM_PORT` | Compose host port publication |
| `GCS_MIMIC_IMAGE` | `GCSM_IMAGE` | Compose image selection |
| `GCS_MIMIC_TLS_DIR` | `GCSM_TLS_DIR` | Compose certificate mount selection |

Rename these variables in shell exports, shared `.env` files and Compose invocations. There is no fallback: an old name never supplies a value.

- `gcs-mimic serve` and `gcs-mimic healthcheck` without `--url` stop on each old name and name its replacement.
- `gcs-mimic sync` stops on `GCS_MIMIC_SYNC_TOKEN` even when it is empty, `GCSM_SYNC_TOKEN` is set or `--token-file` is given.
- The Go package and the example programs stop on their old name when no new name or explicit option supplies the value.
- Compose reads `GCSM_PORT`, `GCSM_IMAGE` and `GCSM_TLS_DIR` itself, and on its own it would ignore an old name and use its default image and port. The shipped `compose.yaml`, `examples/strict-local/compose.yaml` and `examples/full-stack/compose.yaml` therefore pass the three old names into the server only when they are set, so startup fails with the replacement instead. Remove the old names from your shell and `.env` even when the new name is also set. A Compose file of your own that does not pass them through cannot detect them. `compose.tls.yaml` requires `GCSM_TLS_DIR`.

Server setting names are unchanged. Repository test, script and SDK harness variables also moved to `GCSM_`, and the signed-browser script's former `BIN` suffix merged into `GCSM_BINARY`. Past release notes and evidence keep the names that were used at the time.

### Ready event fields

| 0.17.1 | 0.18.0 | What to edit |
| --- | --- | --- |
| `protocol: "http1"` | Absent | Remove the lookup or assertion; no replacement field is added |
| `gcs_api: "json-bucket-object-media-crud"` | Absent | Remove the lookup or assertion; no replacement field is added |
| No data directory fields | Disk: absolute `data_dir` and `data_dir_state`, `"created"` or `"opened"`; memory: both absent | Read the optional pair to identify the store; do not require them in memory mode |

```sh
jq 'select(.event == "ready") | {data_dir, data_dir_state}' server.log
```

Field names in the ready event, diagnostic keys, event names, exit codes and the response fields of the user-facing emulator routes are now part of the compatibility contract; wording is not. See the [release policy](../release-policy.md#product-version-and-compatibility).

## New behavior

### Lifecycle rules execute

Earlier releases stored lifecycle rules and returned them without acting on them. 0.18.0 runs them in the background, on the server's clock, for rules added through the JSON and gRPC APIs and for rules stored by earlier releases.

- **Delete** removes matching objects through the ordinary delete path. Holds, bucket retention, object retention, versioning and each bucket's soft-delete policy apply. In a versioned bucket a matching live object first becomes noncurrent; noncurrent rules act on a later pass. Buckets without soft delete lose the deleted bytes.
- **SetStorageClass** changes the class of the existing generation in place: generation and body bytes stay, metageneration increases once, and `timeStorageClassUpdated` records the change. JSON and gRPC now return that stored time as `timeStorageClassUpdated`, which earlier releases always reported as the creation time. The [storage class contract](../slices/lifecycle-storage-class.md) lists the supported transitions.
- **AbortIncompleteMultipartUpload** aborts matching incomplete XML multipart uploads, including uploads started before the upgrade. Age counts from initiation, and prefix and suffix conditions use the object name. The upload and its parts are removed together and their bytes reclaimed. Uploads with a part write or completion in progress are skipped until a later pass. Abort emits no object notification.
- Lifecycle configuration now accepts the size conditions `sizeAboveBytes` and `sizeBelowBytes`, which earlier releases refused.

Execution is controlled by `lifecycle_execution`: `--lifecycle-execution`, `GCS_MIMIC_LIFECYCLE_EXECUTION` or JSON `"lifecycle_execution"`, with the values `enabled` and `disabled`.

- Without `sync_dir` the default is `enabled`.
- With `sync_dir` the default is `disabled`, so stored rules do not delete host files unexpectedly. Startup emits one `lifecycle_sync_disabled` diagnostic when this default disables stored rules, whether they exist at startup or are added later. With an explicit `enabled`, Delete also removes the synchronized host files; a class change does not rewrite them.
- A data directory used with directory synchronization and started without `sync_dir` follows the first rule: execution is enabled by default, and files tracked before can be removed when synchronization resumes. Set `disabled` for such a run.
- `disabled` keeps stored rules inactive in either mode. The ready event reports the effective `lifecycle_execution`.

Documented differences from Google:

- Google gives Delete priority when several actions match at once. gcs-mimic lets a Delete that has `matchesStorageClass` yield to an applicable transition, so Nearline at age 30 plus a Standard-only Delete at age 60 keeps the object in Nearline when the first pass runs at age 100. The new class is evaluated again at once, and a Delete that still matches runs in the same pass.
- Execution is simulated locally. Google's asynchronous timing and its configuration propagation of up to 24 hours are not simulated.
- Lifecycle waits for object retention even before archiving a live version, newer-version counts exclude soft-deleted versions, and soft deletion emits the ordinary local delete event. Provider parity for these choices is unverified.
- For multipart abort, age zero means the next UTC midnight strictly after initiation, a full day when initiation is exactly at midnight. Google's documentation does not settle this case.

A pass evaluates current rules and facts at the current time, so a delayed pass can differ from passes that ran on time, in both directions. It can keep an object that timely passes would have deleted. It can also delete an object that timely passes would keep, in three tested forms: removing successors that an older version's `numNewerVersions` transition needed, an overwrite during a stop removing a live-only transition, and class-gated transitions taking a different path because the delayed pass chooses a colder class directly. Rules added to aged objects act on their current state immediately, and a backdated Custom-Time takes effect at once. The [storage class contract](../slices/lifecycle-storage-class.md#delayed-pass-differences) gives each example.

### Lifecycle run route

`POST /_internal/lifecycle/run`, available with `admin_enabled` and the existing management guards, runs one pass at the current time. It takes an empty body and answers `enabled`, `scanned`, `deleted`, `archived`, `transitioned`, `aborted`, `blocked` and `skipped`. `scanned` includes visited uploads and object versions; `skipped` counts malformed stored versions and uploads in use. With execution disabled it answers `enabled: false` and zero counts. A corrupt stored rule or version is isolated with a diagnostic emitted once per revision, and healthy objects and buckets continue. See the [execution contract](../slices/lifecycle-execution.md).

### Data directory report

Disk startup reports the absolute `data_dir` and whether it `created` a new catalog or `opened` an existing one, in the ready event. The path is made absolute from the working directory without resolving symbolic links. A directory without an initialized catalog, including an empty database left by an interrupted first start, counts as `created`; once initialization commits, the next start reports `opened` even after a crash. A start that creates a catalog also emits one `info` event, `data_dir_created`, on stderr. Memory mode reports neither. The default `data_dir` remains `data`, relative to the working directory. See the [startup contract](../slices/startup-phases.md).

### Release candidates

Releases may now be published as candidates, `X.Y.Z-rc.N`, ahead of a stable version. A candidate publishes only its exact container tag, never moves `X.Y` or `latest`, and appears as a GitHub prerelease. Its recipes pin its own exact image. Each candidate is a supported upgrade source. See the [release policy](../release-policy.md#the-100-gate).

## Compatibility and migration

0.18.0 upgrades the catalog from schema 52 to 53 when it opens a data directory, even with lifecycle execution disabled. Older binaries refuse schema 53, so returning to 0.17.1 requires restoring a backup taken before the upgrade; there is no in-place downgrade.

### Upgrade checklist

- **Back up the data directory.** Stop the server and copy the complete data directory before the first start with 0.18.0.
- **Stored lifecycle rules start executing.** Without `sync_dir`, rules already in the catalog can delete objects, change storage classes and abort multipart uploads as soon as maintenance starts. Start with `lifecycle_execution=disabled` if you want to review them first.
- **fake-gcs-server flags.** Replace every refused flag listed above, and add `--scheme both` wherever `--port-http` is used.
- **Environment variables.** Rename the seven variables above, including in `.env` files and CI, and remove the old names.
- **Ready-event readers.** Remove reads of `protocol` and `gcs_api`.
- **Scheme.** The default stays `https` in this release. It changes once, in the next minor release, together with a single port that accepts both HTTP and HTTPS; set `--scheme` explicitly if you depend on the current default.

## Known limitations

- Lifecycle `matchesPattern` and `REGIONAL` or `RAPID` object and action classes are not supported. Lifecycle rules cannot be set through the XML API or the bucket initialization file. Empty hierarchical-namespace folder cleanup is not supported.
- While any bucket has rules, a write in any bucket can cause a rescan of every rule-bearing bucket, at most once a second. At most 1024 actions run in one pass, which can stop partway through a generation's class changes; the next pass continues.
- A multipart abort page holds up to 128 uploads until it commits and can delay other catalog requests. A failed abort page stops the other lifecycle actions for that bucket in that pass. Corrupt upload rows are not isolated.
- The released-data fixtures contain no lifecycle rules, so execution of rules stored by an actual earlier release is verified only with a synthetic schema 52 catalog. No 5 TiB body was uploaded to verify size conditions at that size.
- `data_dir_created` can appear even when a later startup phase fails. The test for a working directory that is not valid UTF-8 runs only on Linux.
- A Compose file that does not pass the old Compose variable names into the server cannot detect them.
- The limitations listed for [0.17.1](0.17.1.md#known-limitations) still apply, and these changes do not close the [1.0.0 gate](../release-policy.md#the-100-gate).
