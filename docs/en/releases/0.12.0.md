# gcs-mimic 0.12.0

0.12.0 makes the defaults work without tuning. A migration from fake-gcs-server now needs only `GCS_MIMIC_SCHEME=http` and the data mounts: returned links follow the address each client connected to, capacity limits no longer stop ordinary local workloads, far fewer conditions answer 503, and soft delete is off unless you turn it on. Several defaults change, so read [Compatibility and migration](#compatibility-and-migration) before upgrading.

It publishes `ghcr.io/shiroemons/gcs-mimic:0.12.0` for `linux/amd64` and `linux/arm64`, mirrors the same digest to Docker Hub as `shiroemons/gcs-mimic:0.12.0`, and publishes native archives for all eight macOS, Windows and Linux targets. The [feature matrix](../feature-matrix.md) lists the exact supported subsets. Rows marked `PARTIAL` keep their listed missing cases.

## Changes

### Defaults

| Setting | 0.11.0 | 0.12.0 | Accepted values |
| --- | --- | --- | --- |
| `max_connections` | 32 | 1024 | 1 to 1048576 |
| `max_object_bytes` | 1 GiB | 5 TiB | 1 byte to 5 TiB |
| `header_read_timeout_ms` (new) | none | 30000 | 0 disables; no upper limit |
| `body_inactivity_timeout_ms` (new) | none | 0 (disabled) | 0 disables; no upper limit |
| `request_timeout_ms` (new) | none | 180000 | 0 disables; no upper limit |
| `connection_timeout_ms` | 5000 | unset; an alias for the three above | 0 disables; no upper limit |
| `object_request_timeout_ms` | 900000 | 0 (disabled) | 0 disables; no upper limit |
| `catalog_wait_timeout_ms` | 30000 | 120000; also bounds the wait for a busy session | 0 waits without a limit; no upper limit |
| `keep_alive_timeout_ms` | 120000 | 120000 | 0 disables; no upper limit |
| `tls_handshake_timeout_ms`, `shutdown_timeout_ms` | 5000 | 5000 | 0 disables; no upper limit |
| `worker_threads`, `max_blocking_threads` | 2, 8 | 2, 8 | 1 to 1024 |
| `memory_max_bytes`, `memory_catalog_max_bytes` | 64 MiB, 16 MiB | 64 MiB, 16 MiB | Up to 1 TiB |
| `default_soft_delete_retention_seconds` | 604800 (0 with `--backend memory`) | 0 on every backend | 0, or 1 to 3155760000 |
| `max_resumable_sessions`, `max_rewrite_sessions` (new) | fixed 128 | 0 (unlimited) | 0 to 4294967295 |
| `max_seed_entries`, `max_seed_depth` (new) | fixed 10000, 32 | 10000, 32 | 1 to 100000000, 1 to 1024 |
| `max_buckets_per_batch` (new) | fixed 1000 | See `--help` | 1 to 1000000; buckets one initialization file or one seed may declare |
| `max_sync_entries`, `max_sync_depth` (new) | fixed 10000, 128 | See `--help` | 1 to 100000000, 1 to 1024; require `sync_dir` |
| `max_grpc_streams` (new) | fixed 8 | 100 | 1 to 65536; requires `grpc_listen` |

Cloud Storage documents no seconds for waiting on a request head, for silence on a body or for a whole request, and it asks for "reasonably long" upload timeouts, so these values are local choices. The [source record](../sources.md#timeouts-and-limits-behind-the-local-defaults) lists the pages checked and what they say.

Fixed limits are gone unless Cloud Storage documents them as part of its contract, and past a limit that remains a request waits for its turn instead of failing at once. The [source record](../sources.md#documented-limits-that-remain) lists the limits kept.

### Advertised URLs

- Without `api_base_url` or a runtime `externalUrl`, `Location`, `mediaLink` and `selfLink` use the `Host` of each request and the scheme of its connection, so the host and other containers share one server. Setting either value still fixes the URL.
- A request to an XML virtual bucket host (`bucket.storage.example:4443`) gets links on the configured domain with the same port and the scheme of its connection (`storage.example:4443`), never with the bucket label. A setup whose DNS resolves only the bucket names needs an explicit base.
- An invalid or missing `Host` falls back to the base derived from the bound listener, which the ready event reports. `X-Forwarded-*` and `Forwarded` stay ignored, so a reverse proxy that rewrites `Host` needs an explicit base.
- A `Host` only renders links. The management Host guard reads only the fixed settings, so a derived base never admits the name it came from. A runtime `publicHost` alone no longer fixes the API base.
- Without an explicit base, a PATCH or PUT may repeat a `selfLink` or `mediaLink` read through another `Host`, and a repeated resumable completion answers with links for the retrying `Host`.

### Soft delete

- A new bucket without a policy now stores none on every backend, so an overwrite or delete frees the body at once and `softDeletePolicy` is omitted.
- The server setting, the JSON API, the initialization file and gRPC accept any retention from 1 second to 3155760000 seconds. Cloud Storage defaults to seven days and accepts 0 or 7 to 90 days, so both the default and the range are local choices, and a test of its rejection below seven days cannot run against the emulator. The differential cases `soft-delete-below-minimum` and `patch-soft-delete-below-minimum` record this as a `note`.
- Expired bodies are now freed by the maintenance pass without waiting for a request to that bucket. It wakes at the next hard delete time and does not poll. Three consecutive failed passes take readiness down until one succeeds.

### Fewer 503 responses

- Catalog calls past the 32 admission slots wait instead of failing, and a client that disconnects gives up its place.
- A copy or compose keeps its transfer for as long as it progresses. The transfer used to expire 15 minutes after it began.
- An XML multipart completion reports its outcome however long the assembly takes, instead of a 503 for an upload that then succeeds.
- With `--backend memory`, finished resumable records and finished rewrite records may each fill a quarter of `memory_catalog_max_bytes`, so they cannot exhaust it.
- A request for a busy session waits up to `catalog_wait_timeout_ms`, so a retry takes over from an abandoned chunk. A retried rewrite call also waits for the step its cancelled request left running, and returns that step's stored result.
- Different part numbers of an XML multipart upload write at the same time. A later write of the same number waits for its turn, and the last to finish wins. Completion and abort wait for the parts in flight and hold back parts that arrive after them, up to `catalog_wait_timeout_ms`. Each part also checks the upload's total when it commits, and only the part that passes `max_object_bytes` fails.
- A request that arrives during a reset, reseed or seed commit waits, then runs against the state the job left. While the job waits for active uploads to drain, reads keep running and only new uploads wait behind it. A copy with an idempotency token waits the same way.
- A reset no longer gives up after one second. It waits up to `catalog_wait_timeout_ms` and the request deadline, and keeps a budget for its work after the wait. A reset also waits for a seed commit under way, which on the memory backend could leave an object without its bytes.
- Management calls, publications and seeding follow `catalog_wait_timeout_ms` instead of a fixed 30 seconds. The limit of 32 waiting management calls is gone, and a third reseed or publication waits for its turn instead of failing. A catalog no server configured, as during `import`, keeps 30 seconds.
- A reseed spends `catalog_wait_timeout_ms` only on waiting, so a large tree may take longer. The request deadline and a client that disconnects still end it.
- Synchronization control requests no longer fail past 32 at a time or when the mirror's command queue is full. A wait lasts until its `timeout_ms`, which still answers 408, and other commands until `object_request_timeout_ms`, which is disabled by default.
- The fixed 128-entry limits on resumable sessions, unfinished rewrites, XML multipart uploads and derived transfers are gone, and startup no longer fails on a count. `max_resumable_sessions` and `max_rewrite_sessions` set a limit if you want one.
- Finished resumable sessions and completed rewrites are each kept for seven days or the 4096 most recent, whichever is fewer, and never fail a new session. Rewrite used to keep 128.
- Upload replay records last ten minutes, and at most the 4096 most recent are kept. A full table drops its oldest record instead of failing the upload.
- Undelivered notifications are limited to 4096 messages or 16 MiB. A full outbox drops its oldest message and lets the write through, because Cloud Storage does not fail an object write over Pub/Sub. `notification_outbox_evicted` warns at most once a minute.

### Buckets, synchronization and import

- `max_buckets_per_batch` limits the buckets one initialization file or one seed may declare, not the buckets a server holds. The file limit follows it, at 1 KiB per allowed bucket and at least 1 MiB in all.
- `max_sync_entries` and `max_sync_depth` replace the fixed size of a synchronized tree. One directory no longer stops at 10,000 names, and Linux no longer stops at 1022 watched directories. When the kernel refuses a watch, the message names `fs.inotify.max_user_watches`.
- A scan and a watch now accept exactly as many levels as export can create. They used to accept one fewer, so an object at that level stopped its root on the next scan.
- The conflict budget of a synchronized root grows from 1 GiB to 1 TiB, so an API overwrite of a tracked file up to that size no longer pauses the root.
- `import fake-gcs-server` accepts `--max-object-bytes`, `--max-entries` and `--max-depth`. The values identify an import, so a resume must repeat the values of its first run. The snapshot format has no directories and rejects `--max-depth`.

### Connections

- Startup raises the soft `RLIMIT_NOFILE` to three descriptors per connection plus 64, and warns when the platform refuses. With `grpc_listen`, the raise also aims at connections times streams times two, without a warning when that falls short.
- A full server closes one idle connection, the one idle longest, for each waiting client. It used to close every idle connection, which could break pooled clients reusing them.
- gRPC connections now join that line and send GOAWAY when their turn comes. A new connection joins after its first stream ends or a grace of up to five seconds, and a stream that races the GOAWAY keeps running.
- `max_grpc_streams` replaces the fixed eight streams per connection. The default of 100 is the minimum RFC 9113 section 6.5.2 recommends. Each stream can buffer a message of up to 4 MiB, so one connection can reach 400 MiB, which is close to the Compose `mem_limit` of 512 MiB. Lower the setting to limit that memory.
- The listen backlog grows from 128 to 1024.
- Accepted sockets enable TCP keep-alive with four probes, so an idle connection to a peer that vanishes without a FIN releases its slot after 90 seconds on every platform, even with every timeout disabled. A socket with unacknowledged data falls under the kernel's retransmission limit instead.
- Each connection phase has its own limit. gRPC uses `header_read_timeout_ms` for the handshake and HTTP/2 pings, `keep_alive_timeout_ms` for idle connections and `body_inactivity_timeout_ms` for silence on an open stream, replacing a fixed 60 seconds.

### Compose and examples

- `compose*.yaml` no longer pin `GCS_MIMIC_API_BASE_URL`; it passes through only when set in your environment. `nofile` is 4096 and `mem_limit` is 512 MiB, sized for the larger connection default.
- `config/development.json` no longer sets `max_connections` or `connection_timeout_ms`.
- `GCS_MIMIC_SCHEME` still defaults to `https`.
- The image's `/tmp` is now writable by its unprivileged user, and `SQLITE_TMPDIR` points at the data volume so a read-only root works too. SQLite needs a temporary file when a large statement spills its journal, and without a writable directory that request answered 503 `disk I/O error`. If you move the data directory on a read-only root, set `SQLITE_TMPDIR` to the same place.

### Dependencies and project

- `socket2` 0.6.5 becomes a direct dependency for TCP keep-alive. Tokio already resolves it, so no package or version is added.
- `max_seed_entries` and `max_seed_depth` replace fixed limits, and the seed metadata budget grows with the entry limit.
- [Evidence](../evidence/zero-config-defaults.md) records the tests and measurements below.

## Compatibility and migration

0.12.0 keeps catalog schema 50, but 0.11.0 refuses a data directory past its former limits: more than 128 active or 256 total resumable sessions, 128 unfinished rewrites, 128 XML multipart uploads or 128 derived transfers of either kind. Total sessions pass that count in ordinary use, because 0.12.0 keeps up to 4096 finished ones, so back up the stopped data directory before upgrading if you may need to go back.

### Upgrade checklist

- **Remove settings you added to get working.** You can drop `GCS_MIMIC_API_BASE_URL`, `GCS_MIMIC_LISTEN`, `GCS_MIMIC_MAX_CONNECTIONS`, `GCS_MIMIC_MAX_OBJECT_BYTES`, `GCS_MIMIC_CONNECTION_TIMEOUT_MS`, `GCS_MIMIC_OBJECT_REQUEST_TIMEOUT_MS`, `GCS_MIMIC_CATALOG_WAIT_TIMEOUT_MS` and `GCS_MIMIC_DEFAULT_SOFT_DELETE_RETENTION_SECONDS=0`. See the [migration guide](../fake-gcs-server-migration.md#replace-a-fake-gcs-server-compose-service). Settings that remain still apply.
- **Existing buckets keep seven days.** A policy is stored per bucket and is not rewritten, so a bucket 0.11.0 created keeps its 604800 seconds after the upgrade. To stop retaining, send `softDeletePolicy.retentionDurationSeconds` 0 for that bucket or recreate it.
- **Tests that restore deleted objects.** New buckets have no policy now. Set a policy on the bucket, or `GCS_MIMIC_DEFAULT_SOFT_DELETE_RETENTION_SECONDS=604800` to get the earlier default back.
- **Links.** A client now gets the address it connected to. Keep `GCS_MIMIC_API_BASE_URL` to fix one address, as a reverse proxy that rewrites `Host` needs. An XML virtual-host setup can drop it when the configured domain itself resolves. Keep it if DNS resolves only the bucket names.
- **Shared or exposed servers.** `max_object_bytes` of 5 TiB also widens the gzip upload expansion limit, so a small body can expand that far. Disabled body limits let a stalled client keep its slot. On a shared server or one listening on `0.0.0.0`, lower `max_object_bytes` and consider setting `body_inactivity_timeout_ms`.
- **Going back to 0.11.0.** Restore the backup taken before the upgrade, because 0.11.0 can refuse a directory that 0.12.0 has used. See above.
- **Parsers of the ready event.** `connection_timeout_ms` is gone from `ready`, replaced by `header_read_timeout_ms`, `body_inactivity_timeout_ms` and `request_timeout_ms`.
- **`--tls-handshake-timeout-ms 0`** now disables the limit. It used to be rejected.

To restore 0.11.0 behavior:

| To get back | Set |
| --- | --- |
| Soft delete on new buckets | `GCS_MIMIC_DEFAULT_SOFT_DELETE_RETENTION_SECONDS=604800` |
| One fixed link address | `GCS_MIMIC_API_BASE_URL=http://HOST:PORT` |
| Connection and object limits | `GCS_MIMIC_MAX_CONNECTIONS=32`, `GCS_MIMIC_MAX_OBJECT_BYTES=1073741824` |
| The single five-second deadline | `GCS_MIMIC_CONNECTION_TIMEOUT_MS=5000` |
| Transfer and catalog limits | `GCS_MIMIC_OBJECT_REQUEST_TIMEOUT_MS=900000`, `GCS_MIMIC_CATALOG_WAIT_TIMEOUT_MS=30000` |
| Session limits | `GCS_MIMIC_MAX_RESUMABLE_SESSIONS=128`, `GCS_MIMIC_MAX_REWRITE_SESSIONS=128` |

### Behavior changes in detail

- **Retries can publish again.** A single-request upload or copy with an idempotency token gets its first answer back only while its record exists. After ten minutes, or after 4096 later token-bearing publications dropped it, a retry is a new write. Resumable uploads create no such records. Send `ifGenerationMatch` or read the object back if a duplicate matters. See the [replay contract](../slices/sdk-upload-replay.md).
- **Notifications can be lost.** With Pub/Sub unreachable, a full outbox drops its oldest messages. Delivery stays at-least-once only for messages still in the queue. See the [notification contract](../slices/pubsub-notification-delivery.md).
- **Stalled transfers wait.** No default bounds a stalled upload or download, and a catalog wait lasts up to two minutes where it used to last 30 seconds, so a client timeout may now fire first.
- **Suites that reset between tests.** A request overlapping a reset now waits for it instead of answering 503. A test that expected that 503 must expect the request to run on the cleared state.
- **New log events.** `grpc_handshake_timeout` reports a gRPC client that sent no preface in time. `grpc_idle_reclaimed` (debug) reports an idle gRPC connection closed for a waiting client. `tcp_keepalive_failed` (debug) reports a socket that could not enable keep-alive.
- **Timeout replies.** A deadline answers as before, with 408 `uploadBrokenConnection` for object uploads and 503 `backendError` otherwise, and each message names the setting to raise.

### Local measurements

One run of each scenario on the integrated release build, native on macOS arm64. These are facts about that run, not guarantees; see the [evidence](../evidence/zero-config-defaults.md).

- Go SDK, 32 parallel, 800 uploads and read-backs: no failures (0.11.0: 17 to 22 failures).
- 96 parallel GETs of 4 MiB, 480 requests: no failures.
- Mixed load, 48 parallel, 15 seconds: 27,444 operations, no 503 or connection error, peak RSS 38 MiB (0.11.0: 449 responses of 503 and many connection errors).
- 300 resumable uploads left unfinished: all succeed and can continue after a restart (0.11.0: 503 from the 129th).
- A write that stalls for 8 seconds and for 70 seconds: succeeds.
- 3 GiB POST and GET: contents match, peak RSS 17 MiB.
- 300 MiB overwrite and delete: space reclaimed at once.
- `kill -9` twice: no loss among 787 acknowledged writes.
- 1000 transfers in flight, half uploads and half downloads: about 230 MiB RSS while held, with peaks of 266 to 343 MiB.

The same scenarios in the final image on Docker Desktop, with only `GCS_MIMIC_SCHEME=http` and the `/data` and data volume mounts, also passed. A data directory that ran out of space answered 503 with guidance, also for a 617 KB gzip body expanding past it, kept serving and recovered after a delete. See the [evidence](../evidence/zero-config-defaults.md) for those runs.

## Known limitations

- A client that stays connected but stops sending an upload body holds up a reset. The reset waits up to `catalog_wait_timeout_ms`, and new uploads wait behind it for that long. It then answers 503 "made no changes" and changes nothing. The client disconnecting clears this. With `catalog_wait_timeout_ms` of 0, it lasts until the reset's client disconnects.
- With the default `body_inactivity_timeout_ms` of 0, a part of an XML multipart upload whose body stops holds up that upload's completion in the same way, and new parts wait behind the completion. Past `catalog_wait_timeout_ms` the completion answers 503 and the part can resume.
- An unfinished XML multipart upload expires after seven days, where Cloud Storage sets no limit. This is a deliberate difference: abandoned parts do not appear in object listings, so they would use disk without anyone noticing. `/_internal/reset` and abort also remove them.
- Overwriting a tracked file larger than 1 TiB stops synchronization of its root, because the conflict budget stays at 1 TiB under the 5 TiB object limit.
- At a full server, if a stream raced the GOAWAY of a reclaimed gRPC connection, the waiting client waits until another connection ends, at most its keep-alive. It does not fail.
- With `grpc_listen` and the default `max_grpc_streams`, one connection can buffer up to 400 MiB of received messages, close to the Compose `mem_limit` of 512 MiB. Lower `max_grpc_streams` if that memory matters.
- One HTTP batch runs two calls at a time. A larger batch takes longer but does not fail.
- A `shutdown_timeout_ms` of 0 waits for unfinished requests without a limit.
- The limitations listed for [0.11.0](0.11.0.md#known-limitations) still apply, and these changes do not close the [1.0.0 gate](../release-policy.md#the-100-gate).
