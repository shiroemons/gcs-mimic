# gcs-mimic 0.3.0

0.3.0 makes fixture loading work like fake-gcs-server: mount a
`BUCKET/OBJECT` tree at `/data` and it is applied on every startup, with no
other setting. It also implements gRPC `CancelResumableWrite`, lists legacy v1
buckets across projects when the project is omitted, and keeps directory
synchronization running past names the host cannot represent. It publishes
`ghcr.io/shiroemons/gcs-mimic:0.3.0` for `linux/amd64` and `linux/arm64`,
mirrors the same digest to Docker Hub as `shiroemons/gcs-mimic:0.3.0`, and
publishes native archives for all eight macOS, Windows and Linux targets. The
[0.2.1 release notes](https://github.com/shiroemons/gcs-mimic/blob/v0.2.1/docs/en/releases/0.2.1.md)
describe the previous release; the [feature matrix](../feature-matrix.md) lists
the exact supported subsets.

Seeding behavior changes in ways that can overwrite API changes on restart.
Read [Compatibility and migration](#compatibility-and-migration) before
upgrading a deployment that sets a seed directory or mounts `/data`.

## Changes

### Seed files

- A configured seed directory is applied before readiness on every startup,
  not only when a data directory is first initialized. Missing buckets and
  objects are created. An object whose bytes or metadata differ from what
  seeding writes, including API metadata edits, is replaced as a new
  generation; only an exact match keeps its generation. Objects without a seed
  file are kept, and removing a seed file never deletes an object.
- A held or retained object that needs replacement is left unchanged, counted
  as `blocked` and reported by a `seed_blocked` warning.
- Regular files directly under the seed root, such as `README.md`, are skipped
  with a `seed_skipped` warning instead of stopping startup.
- The new `default_seed_dir` setting (`--default-seed-dir`,
  `GCS_MIMIC_DEFAULT_SEED_DIR`, JSON `default_seed_dir`) is used only when
  `seed_dir` is unset and the directory exists without overlapping `data_dir`
  or `sync_dir`. The image sets it to `/data`.
- `seed_content_type` now defaults to `extension`, so `logo.png` is stored as
  `image/png`. The same setting governs files ingested from `sync_dir`.
- The ready event's `seed` field reports `buckets`, `objects`, `replaced`,
  `unchanged`, `blocked` and `skipped_os_metadata`.

See the [seed replay change](seed-replay.md) and
[loading local files](../container-usage.md#load-local-files) for details.

### gRPC

- Storage v2 `CancelResumableWrite` discards a resumable session through the
  same catalog cancellation as the JSON session `DELETE`. Later status queries,
  writes and repeated cancellation return `NOT_FOUND`; a finalized upload
  returns `FAILED_PRECONDITION` and keeps its object. Strict mode requires
  `storage.objects.create`, as resumed writes do.
- In strict mode, anonymous callers of Storage v2 object I/O and update/copy
  RPCs now receive `UNAUTHENTICATED`, like JSON, XML and the other RPCs. They
  previously received `PERMISSION_DENIED`.
- Legacy Storage v1 `ListBuckets` without a project lists every project's
  buckets in name order, as the reference emulator does, instead of returning
  `INVALID_ARGUMENT`. Strict callers see only projects where they hold
  `storage.buckets.list`.

### Directory synchronization

- Object names with `:` or `\` components are recorded as findings and
  skipped on every OS instead of stopping the whole mirror, so later objects
  keep exporting. Matching host files are counted as unrepresentable.

### Distribution

- The release workflow mirrors the verified GHCR index to Docker Hub without
  rebuilding, so both registries serve the same digest.

## Compatibility and migration

The data-directory schema remains `PRAGMA user_version = 27`, shared with
0.2.0 and 0.2.1, so these releases open each other's data directories. No
catalog migration runs.

- Deployments that set `seed_dir` and then change seeded objects through the
  API see those changes replaced on the next restart. Remove `seed_dir` after
  the first start, or move fixtures that should stay editable out of the seed
  tree.
- Objects seeded as `application/octet-stream` by earlier releases are
  replaced once with the extension-derived type. Set
  `GCS_MIMIC_SEED_CONTENT_TYPE=octet-stream` to keep the previous type, which
  also restores it for `sync_dir` ingestion.
- An image deployment that mounts something other than fixtures at `/data`,
  without using it as `data_dir` or `sync_dir`, now seeds from it. Mount it
  elsewhere, or set `GCS_MIMIC_SEED_DIR` to the intended fixture directory.
- The ready event's `seed.existing_objects` field and the `skipped` outcome are
  removed; read `unchanged` and `replaced` instead.
- Strict gRPC clients that matched `PERMISSION_DENIED` for anonymous Storage v2
  object calls should expect `UNAUTHENTICATED`.

## Verification

The [release workflow](https://github.com/shiroemons/gcs-mimic/blob/v0.3.0/.github/workflows/binaries.yaml)
creates this Release only after `validate`, including the dependency freshness
check, Foundation and all eight native build/test jobs succeed at the tag's
SHA. The
[container workflow](https://github.com/shiroemons/gcs-mimic/blob/v0.3.0/.github/workflows/ghcr.yaml)
then builds both Linux architectures natively, verifies their SBOM and
provenance, publishes the multi-architecture tag and checks anonymous pulls,
and the Docker Hub workflow mirrors that digest.

Before the release commit, Foundation checks passed on Linux with the pinned
and current stable Rust, the macOS, Windows and Linux musl portability tests,
both native container smoke tests, including seed replay and the implicit
`/data` mount, and the pinned Go SDK suite. The pinned Ruby SDK suite passed
locally on macOS.

## Known limitations

- Seeding has no file watcher and no reseed endpoint; restart to apply edits.
- Seed replay is applied file by file, not as one directory-wide transaction.
- The [0.1.0 known limitations](0.1.0.md) and the feature matrix still apply
  to unimplemented API areas.
