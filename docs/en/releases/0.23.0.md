# gcs-mimic 0.23.0

0.23.0 accepts customer-supplied encryption keys over Storage v2 gRPC, stores custom metadata past 8 KiB as Cloud Storage does, and fixes the answers that kept official SDK workflows from working: Java's gRPC bucket reads, Python's appendable writes and XML multipart uploads, PHP's `gs://` stream wrapper, and requests the C++ and Ruby SDKs send. A gcs-mimic-only run of the [nine-SDK scorecard](../../../sdk-scorecard/README.md) on the release source passes every case. No command, option, environment variable or configuration setting changes.

It publishes `ghcr.io/shiroemons/gcs-mimic:0.23.0` for `linux/amd64` and `linux/arm64`, mirrors the same digest to Docker Hub as `shiroemons/gcs-mimic:0.23.0`, and publishes native archives for all eight macOS, Windows and Linux targets. The [feature matrix](../feature-matrix.md) lists the exact supported subsets.

## What may need attention

- **Custom metadata past 8 KiB is stored.** Cloud Storage did not enforce its documented 8 KiB custom metadata limit (recorded 2026-11-15): PATCH, multipart insert, resumable start and completion and XML PUT stored an 8193-byte value, an 8193-byte key and totals past 8192 bytes, and Storage v2 `WriteObject` and `UpdateObject` stored values of 8192 to 40,000 bytes. 0.22.0 refused them with JSON and XML 400 and gRPC `RESOURCE_EXHAUSTED`. The only remaining bound is local: fixed and custom metadata past 40 KiB once encoded as JSON answer 400 `invalid` or `INVALID_ARGUMENT` and publish nothing, because stored session, completion and rewrite rows keep a copy of them.
- **A null custom metadata value is stored as the empty string on every write but PATCH.** A resumable start, a multipart insert, a copy, a rewrite, a compose destination and a PUT now keep the key with `""`, as recorded from Cloud Storage, even for a key the copy source has. 0.22.0 removed the key. PATCH still removes it.
- **A declared upload length of 0 leaves the total open.** A resumable session started with `X-Upload-Content-Length: 0` accepts chunks whose total is open and completes at any size, as Cloud Storage answered. 0.22.0 took the 0 as the session's total and refused the first chunk with 400 `Inconsistent upload total`, which broke PHP's `gs://` writes. A nonzero declared length still binds the total.
- **Generation precondition pairs follow Cloud Storage.** A move with both `ifGenerationMatch` and `ifGenerationNotMatch`, or the metageneration, source and source metageneration pairs, answers 409 `conflict` with Cloud Storage's message instead of 400 `invalidArgument`. A restore evaluates such a pair instead of refusing it, so `ifGenerationMatch=0` with `ifGenerationNotMatch=1` and no live object answers 412 `conditionNotMet`.
- **gRPC bucket read masks may name settings gcs-mimic never stores.** `billing`, `custom_placement_config`, `encryption`, `hierarchical_namespace`, `ip_filter`, `logging`, `rpo` and `website` are returned unset, as Cloud Storage answers for a bucket without them, instead of failing with `UNIMPLEMENTED`. The Java SDK names all of them in its default mask. `satisfies_pzs` and nested paths stay `UNIMPLEMENTED`.

## Changes

### gRPC

- Storage v2 accepts customer-supplied keys. `WriteObject`, non-appendable `BidiWriteObject` and `StartResumableWrite` take the key from the request that starts the write, which encrypts the new object or binds the session; a malformed key fails before any byte is staged. `GetObject`, `ReadObject` and `BidiReadObject` verify the key in the same catalog read that selects the generation, reveal checksums only with it, and need it again on a resume. `UpdateObject` reveals checksums only with the right key, `ComposeObject` decrypts every component with one key and encrypts the result with it, and `RewriteObject` reads the source key from `copy_source_encryption_*` and the destination key from `common_object_request_params`, so a rewrite can encrypt, decrypt or rotate a key. Key errors answer `INVALID_ARGUMENT` with one `BadRequest` field violation and the recorded wording. `DeleteObject` ignores a supplied key, as Cloud Storage does; `RestoreObject` and appendable writes refuse one.
- A creating appendable `BidiWriteObject` stream answers its opening message with the unfinalized resource and a write handle, as a takeover already did. Python's `AsyncAppendableObjectWriter` waits for that answer before it sends data.
- The legacy Storage v1 adapter applies the same 40 KiB metadata bound to its uploads, updates and compositions instead of an 8 KiB cap.
- A `MoveObject` onto its own source answers `INVALID_ARGUMENT` "Source and destination object names must be different." instead of a message about custom metadata.

### JSON and XML

- Each XML multipart part answers with two `x-goog-hash` fields, `crc32c=` and `md5=`, for its own bytes, as Cloud Storage documents. The Python SDK's `transfer_manager.upload_chunks_concurrently` checks every part's CRC32C from them by default.
- Methods without a body accept a `Content-Length` of zero written with leading zeros, such as `Content-Length: 00`, as Cloud Storage did on a bucket read, an object read and an object delete.
- Object restore accepts the empty JSON object `{}` that google-cloud-cpp 3.13.0 sends; any other JSON body, and `{}` without a JSON content type, still fail.
- Bucket restore accepts the form body that google-cloud-storage 1.62.2 for Ruby sends with the same parameters as the URL query, as object restore and retention lock already did. A form body that adds or changes a parameter, and any JSON body, still answer 400.
- XML POST policy documents accept an expiration with up to nine fractional digits, as google-cloud-cpp 3.13.0 writes it; digits beyond the microsecond are dropped, which can only end a policy earlier.

### Server, startup and diagnostics

- A notification setting that fails validation is named in the diagnostic: an invalid topic, an event bucket name or object prefix that is too long, and an unknown `event_list` entry no longer all name `--pubsub-emulator-host`.
- Failures that answered "custom metadata exceeds 8 KiB" now name their cause: an upload completion too large to keep for replay is a 400 that names the metadata, the ACL and the 64 KiB record; a stored deadline that overflows or a stored `customTime` that does not parse is corrupt stored data; an upload replay snapshot of another object is unavailable; and an imported element without both hashes, Replace mode and an absent destination is an administrative 400 that lists them.

## Compatibility and migration

The catalog schema is unchanged at 53, so a data directory moves between 0.22.0 and 0.23.0 in either direction without a migration. Apart from the changes listed under [What may need attention](#what-may-need-attention), each change accepts a request that 0.22.0 refused, reports a failure 0.22.0 misreported, or brings an answer closer to Cloud Storage.

A `gcs-mimic sync` command and the server it manages must still be the same release, so upgrade both together. The Go package accepts a binary of the same minor release, so upgrade `go/fakestorage` to 0.23.0 together with the binary.

## Dependencies and project

- rusqlite moves to 0.43.0 (libsqlite3-sys 0.40.0, bundled SQLite 3.54.1). Its new `Error::Empty` for an empty or comment-only statement does not reach gcs-mimic, which prepares only static SQL. No Rust toolchain or container base changes. The development-only Java SDK suite and scorecard probe move to Maven 3.10.1. The package version and the Go package's `moduleVersion` move to `0.23.0`, and the recipes pin `0.23.0`.
- The [SDK scorecard](../../../sdk-scorecard/README.md) adds an official C++ SDK probe (google-cloud-cpp 3.13.0) and defines all 106 cases in one catalog that every run is checked against: five more shared cases, `grpc` cases that Go, Java, Python and Rust emit under SDK-neutral IDs, and SDK-specific cases for the workflows each public API reaches beyond the shared core. Its [seventh 2026-11-15 comparison](../../../sdk-scorecard/results/2026-11-15-7/summary.md) runs 2,324 cases: gcs-mimic scores 99.8 with Core 100, floci-gcp 74.2, fake-gcs-server 39.2 and gcp-storage-emulator 35.7. The one case gcs-mimic failed there, PHP's `sdk.stream_wrapper`, passes in a later gcs-mimic-only run with the declared-length fix.
- The differential reference grows from 108 to 122 cases, recording custom metadata limits over JSON, XML and gRPC, gRPC customer-supplied keys, bucket read masks naming unset settings, and resumable sessions that declare a length. A case can now repeat a text body (`body_repeat`) to send a 256 KiB chunk.
- The [feature ledger](../../../compatibility/features.json) moves the C++ SDK row (AUDIT-003) to `PARTIAL` and records each SDK's scorecard evidence on the rows it exercises.

## Known limitations

- The released-data fixtures for 0.23.0 are added after publication, as for earlier releases.
- A chunk past a nonzero `X-Upload-Content-Length` is refused with 400 and the session stays usable, where Cloud Storage fails the whole session and repeats its error (`SPEC-RESUMABLE-DECLARED-LENGTH-OVERRUN`). A resumable 308 after data carries `Range` but not the `x-goog-running-hash` and `x-range-md5` headers Cloud Storage sends (`SPEC-RESUMABLE-RUNNING-HASH`).
- Over Storage v2, a key on a later message of a keyless write fails with `INVALID_ARGUMENT` where Cloud Storage answers `INTERNAL`, and `BidiReadObject`, rewrite continuations and `RestoreObject` follow local rules (`SPEC-GRPC-CSEK`). Legacy Storage v1 requests cannot supply keys.
- The limitations listed for [0.22.0](0.22.0.md#known-limitations) still apply, and these changes do not close the [1.0.0 gate](../release-policy.md#the-100-gate).
