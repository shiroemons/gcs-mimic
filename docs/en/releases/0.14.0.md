# gcs-mimic 0.14.0

0.14.0 lets a local setup check access the way production does without changing how the application's servers call Cloud Storage, with a few environment variables in the existing compose.yaml. A trusted listener keeps the application's own servers working unchanged while the browser-facing port keeps every strict check, public and private buckets are declared as JSON in `GCS_MIMIC_BUCKETS`, a built-in test signer replaces key setup, and Go-signed URLs work on a local port. No certificate, key or identity file has to be prepared. A client that pauses a request body no longer gets 503, permissive mode allows browser requests without CORS rules, and denials and several other errors now name their actual cause. One catalog schema change and several defaults and replies change, so read [Compatibility and migration](#compatibility-and-migration) before upgrading.

It publishes `ghcr.io/shiroemons/gcs-mimic:0.14.0` for `linux/amd64` and `linux/arm64`, mirrors the same digest to Docker Hub as `shiroemons/gcs-mimic:0.14.0`, and publishes native archives for all eight macOS, Windows and Linux targets. The [feature matrix](../feature-matrix.md) lists the exact supported subsets. Rows marked `PARTIAL` keep their listed missing cases.

## Which setup to use

| Goal | Setup |
| --- | --- |
| Behave like fake-gcs-server | The defaults with `GCS_MIMIC_SCHEME=http`. Browser requests now work without CORS rules, as fake-gcs-server allowed them |
| Production-like access: private buckets stay private, public ones are read through `allUsers`, the browser uses signed URLs, application servers keep their own Cloud Storage calls | Strict mode with the trusted listener: copy the [strict local recipe](../../../examples/strict-local/README.md) as it is |
| Check signed URLs as Cloud Storage does while strict mode is not an option yet | Permissive mode with `GCS_MIMIC_SIGNED_URLS=verify` |

Start with the defaults. When signed URLs or private buckets need production-like checks, use the recipe: it needs `GCS_MIMIC_SCHEME`, `GCS_MIMIC_AUTH_MODE=strict`, `GCS_MIMIC_TRUSTED_LISTEN`, the bucket JSON in `GCS_MIMIC_BUCKETS` and, for signed URLs or for Rails and other clients that use the test signer's credentials, `GCS_MIMIC_TEST_SIGNER=enabled`, all inside the service's `environment:`. It needs no certificates, no key generation and no identity file. The [full application example](../../../examples/full-stack/README.md) shows the same server with a Go API, a Rails app and a frontend.

The trusted listener covers only the requests the application's servers send themselves. fake-gcs-server checks no signature, so an application may leave the URLs it hands to browsers unsigned against the emulator. In strict mode those requests get 401, and permissive `GCS_MIMIC_SIGNED_URLS=verify` allows them because they carry no signature to check, so the application has to sign them. An application that signs without a key in production needs emulator signing options, because Go storage finds no identity when `STORAGE_EMULATOR_HOST` is set. The [strict local recipe](../../../examples/strict-local/README.md#what-the-trusted-listener-does-not-cover) lists these cases.

## Changes

### Request bodies and timeouts

- A pause while the client sends any request body, including JSON and XML resource bodies, no longer counts against `request_timeout_ms`. Only `body_inactivity_timeout_ms` bounds it, and that limit is disabled by default. An object metadata `PATCH` whose body paused past `request_timeout_ms` used to answer 503.
- The reply names the limit that expired:

| Limit that expired | JSON API | XML API |
| --- | --- | --- |
| `body_inactivity_timeout_ms` | 408 `uploadBrokenConnection` | 400 `RequestTimeout`; a silent upload body answered 408 before |
| `object_request_timeout_ms`, upload | 408 `uploadBrokenConnection` | 408 `uploadBrokenConnection` |
| `object_request_timeout_ms`, other transfer | 503 `backendError` naming `object_request_timeout_ms` | `ServiceUnavailable` |
| `request_timeout_ms` | 503 `backendError` | `ServiceUnavailable`; uploads answered 408 before |

- The XML API documents a silent socket as 400 `RequestTimeout`, which clients do not retry, while 408 and 503 are retried. The JSON API documents only `uploadBrokenConnection` under 408.
- With the default `body_inactivity_timeout_ms` of 0, a client that declares a body and stops sending holds its connection and nothing is logged. Set the limit to find such a client: it then fails and the server logs `connection_timeout`.

### Error messages

- A full store names only the remedy of the storage that ran out: free space in the data directory, `memory_max_bytes` for RAM objects, or `memory_catalog_max_bytes` for the RAM catalog. This also applies to seeding and bucket initialization at startup. Each message still starts with "Storage capacity exhausted;".
- An out-of-range V4 expiry says "X-Goog-Expires must be a whole number of seconds from 1 to 604800." (`X-Amz-Expires` for the AWS algorithm), and for 0 adds that the signer's expiry was probably less than one second away, as Go storage writes then. The reply stays 400 `InvalidAuthentication`.
- A signature that does not match the request but would match it without the port in Host says so and names `signed_host_port=lenient`. Every other mismatch keeps "The request signature does not match."
- A strict-mode denial through the JSON or XML API names who was refused and which permission was missing, in Cloud Storage's form: `PRINCIPAL does not have storage.objects.get access to the Google Cloud Storage object. Permission 'storage.objects.get' denied on resource (or it may not exist).` The principal is the token holder, the signer of a signed URL or the trusted listener's principal. An anonymous bucket or object request answers 401 with "Anonymous caller does not have ...". Statuses, reasons and XML codes are unchanged, and the message never names the bucket or the object, so a missing bucket reveals no more than before.
- With `GCS_MIMIC_LOG_LEVEL=debug`, each denied JSON or XML response logs an `authorization_denied` event with the principal, the permission, the resource kind and the bucket, never tokens or signatures. Nothing is logged at info and above. gRPC denials carry the new message for registered callers but are not logged, and most anonymous gRPC denials keep "Login Required".
- An unknown signer's message depends on where keys come from: the registered identities in strict mode, the identity file, JSON API HMAC keys and the test signer in permissive `verify`, or a note that the built-in test signer is disabled.
- `POST /_internal/reseed` answers 400 `invalid` without `Retry-After` for failures another attempt cannot fix: a configured `max_seed_entries`, `max_seed_depth` or `max_buckets_per_batch` exceeded (named in the message), invalid names or content in the fixture tree, an unreadable fixture, or a missing root. A refused write answers 403 `forbidden`. Only failures a later attempt can finish keep 503 with `Retry-After: 1`. The reason for an invalid fixture state changes from `invalidArgument` to `invalid`.

### Signed URLs

- `signed_urls` (`--signed-urls`, `GCS_MIMIC_SIGNED_URLS`): `ignore`, the permissive default and the earlier behavior, or `verify`. Permissive `verify` checks signed XML requests exactly as strict mode does, then grants permissive access without permission checks. It covers signed URLs, V2/V4/AWS4 `Authorization` header signatures, aws-chunked uploads and POST policies, so S3-style clients that sign with made-up HMAC keys are rejected; create HMAC keys through the JSON API for them. Strict mode always verifies and rejects `ignore`.
- In permissive mode an identity file is accepted only with `signed_urls=verify`, and its identities may declare only `id` and `public_keys`.
- `signed_host_port` (`--signed-host-port`, `GCS_MIMIC_SIGNED_HOST_PORT`): `exact` or `lenient`. Go storage drops a non-default port from the Host it signs, so its URLs for `localhost:4443` fail exact verification. Lenient checks such a signature once more without the request's port and accepts it only if that matches; the host name and every other signed part stay bound. It logs `signature_host_port_omitted` once per process. By default the built-in test signer's own RSA signatures are checked leniently, because its published key already marks a local test, and every other signature exactly, HMAC keys included. An explicit `lenient` applies to every signer, an explicit `exact` to the test signer too, and an explicit `lenient` where nothing is verified fails startup. The ready event reports `signed_host_port` and, when it is lenient, `signed_host_port_signers` (`all` or `test-signer`).

### Built-in test signer

- `test-signer@gcs-mimic.invalid` signs with the published test key that the repository already used for its tests. Its private key is public: use it only for local tests.
- `test_signer` (`--test-signer`, `GCS_MIMIC_TEST_SIGNER`): an explicit value wins. Otherwise it is enabled in permissive mode with `signed_urls=verify`, and in strict mode exactly when the identity document declares `test-signer@gcs-mimic.invalid`. Enabling it where nothing is verified fails startup.
- In strict mode an enabled signer warns at startup that anyone can authenticate as it and reach `allAuthenticatedUsers` grants. When the identity document does not declare it, it holds `roles/storage.objectUser` in the projects the bucket document names and in `seed_project`: enough for signed GET and PUT, overwrite, and Rails' delete, list and metadata updates, but no IAM or bucket administration. A declared entry replaces those implicit roles.
- `gcs-mimic test-signer credentials` prints its service account JSON, so an image or binary user needs no repository checkout: `docker run --rm ghcr.io/shiroemons/gcs-mimic:0.14.0 test-signer credentials > test-signer.json`.
- `gcs-mimic url sign` without `--signer` and `--private-key` signs as the test signer. Giving only one of them remains an error.

### Trusted listener for application servers

- `trusted_listen` (`--trusted-listen`, `GCS_MIMIC_TRUSTED_LISTEN`), strict mode only, adds a plain HTTP listener for the application's own servers. A request without credentials there acts as `trusted_principal` (`--trusted-principal`, `GCS_MIMIC_TRUSTED_PRINCIPAL`), a registered identity, and passes the normal strict checks; a request with credentials authenticates as on the main listener.
- Without `trusted_principal`, it acts as the built-in `trusted-app@gcs-mimic.invalid`, which holds `roles/storage.admin` in the projects the bucket document names and in `seed_project`, and has no token or key, so only the trusted listener reaches it. A declared entry with that id replaces the implicit grants. Strict mode then starts without any identity document, as it also does with an explicit `test_signer=enabled`.
- Browser-initiated requests, with an `Origin` header or a `Sec-Fetch-Site` other than `none`, get 403. The Host must be an IP literal, a `localhost` name, a single-label name such as a Compose service name, or a name in `trusted_allowed_hosts` (`--trusted-allowed-hosts`, `GCS_MIMIC_TRUSTED_ALLOWED_HOSTS`); any other Host gets 421, which stops DNS rebinding. Every response carries `Cross-Origin-Resource-Policy: same-origin` and `X-Content-Type-Options: nosniff`.
- Never publish the trusted port. These checks keep web pages out, not other programs that reach it.

### Bucket and identity documents inside compose.yaml

- `GCS_MIMIC_BUCKETS` (`--buckets`, JSON key `buckets`) and `GCS_MIMIC_IDENTITIES` (`--identities`, JSON key `identities`) carry the bucket and identity documents as JSON text, so a Compose service needs neither a file nor a `configs:` block. Each is mutually exclusive with `GCS_MIMIC_BUCKETS_FILE` or `GCS_MIMIC_IDENTITY_FILE`, accepts the same document with the same limits, and is named in diagnostics without echoing its text. Compose expands `${VAR}` inside them; write a literal `$` as `$$`.
- Inline buckets default to `buckets_file_mode=reconcile`, because compose.yaml is then the source of the settings: an edited `GCS_MIMIC_BUCKETS` makes Compose recreate the container on a plain `docker compose up -d`, and the next start applies it to the existing volume. A bucket file keeps the `create` default.

### Bucket file

- An entry may write `iamPolicy` with `bindings`, for example `allUsers` with `roles/storage.objectViewer` on a public bucket. It replaces the bucket's whole policy, as `setIamPolicy` does, and a grant to `allUsers` or `allAuthenticatedUsers` that public access prevention forbids fails startup before anything changes. Releases up to 0.13.0 reject the member, so a file that uses it never silently loses its grants there.
- `buckets_file_mode` (`--buckets-file-mode`, `GCS_MIMIC_BUCKETS_FILE_MODE`): `create`, the default and the earlier behavior, or `reconcile`, which also applies each entry's written members to its existing bucket. Members an entry omits stay as they are, a different location is kept with a warning, and an unchanged file writes nothing.
- In `create` mode an entry edited after its bucket exists warns at every start until the bucket or the entry matches again. A member the entry stops writing warns once, and the bucket keeps its value. The first start that finds a bucket without a recorded entry, such as one 0.13.0 created, warns once if the bucket differs and then records the entry.
- The ready event's `buckets_file` gains `unapplied` and `reconciled`. A partially applied bucket counts in both.
- The migration guides recommend writing the buckets inline in `GCS_MIMIC_BUCKETS`, and keep a bucket file written with Compose `configs.content` as an alternative, which needs `docker compose up -d --force-recreate` to apply an edit.

### CORS

- `cors_fallback` defaults by mode: `allow-all` in permissive mode, as fake-gcs-server allowed every origin, and `none` in strict mode, as Cloud Storage refuses a bucket without `cors` rules. An explicit value wins, and buckets with stored rules always follow them.
- When the permissive default is what allowed an XML cross-origin request to a bucket without rules, the server logs one `cors_fallback_default` info event per bucket, because Cloud Storage would refuse it.

### Documentation

- The container and migration guides start with which setup to use, recommend strict mode with the trusted listener for production-like checks, and compare permissive, strict and fake-gcs-server. The [strict local recipe](../../../examples/strict-local/README.md) is the block to paste, and the [full application example](../../../examples/full-stack/README.md) wires it to a Go API, a Rails app and a frontend with a different port per worktree.
- The Rails guide adds a strict path with the built-in test signer, a container setup whose host port no longer has to be 4443 (`GCS_MIMIC_LISTEN` follows the published port), and two verified ways to point `public: true` URLs at the emulator, which google-cloud-storage always builds on `storage.googleapis.com`: a `public_url` method in the `EmulatorGcs` adapter (recommended) or an initializer.
- Troubleshooting explains how to find a client that stops sending a request body.
- Two stale statements were corrected: strict anonymous requests do match `allUsers` grants, and every accepted IAM policy write advances bucket metageneration.

### Dependencies and project

- No dependency is added.
- The container build copies `fixtures/signing/test-only-private.pem` and `test-only-public.pem`, which the binary embeds as the test signer. The image grows by those two files.
- The Windows archives embed the development certificates and the test signer key with LF line breaks, as the other targets do. The 0.13.0 Windows archives embedded the certificates with CRLF, so `gcs-mimic tls ca` printed CRLF there.
- The container smoke test runs the strict local recipe and the full application example with the built image, with stand-in containers for the application services.
- The Go SDK suite starts a third server with the trusted listener, the test signer and lenient host ports, and runs the unmodified SDK against it. The strict Rails suite runs every case with a signer that holds only `roles/storage.objectUser`.

## Compatibility and migration

0.14.0 moves the catalog from schema 51 to schema 52, which adds the table that records each bucket file entry and its written members. The migration runs automatically and one way, so 0.13.0 cannot open a data directory that 0.14.0 has used. Back up the stopped data directory before upgrading if you may need to go back.

### Upgrade checklist

- **First start.** Each existing bucket that differs from its bucket file entry warns once, because 0.13.0 recorded no entry. Edit the entry, change the bucket through the API, or set `GCS_MIMIC_BUCKETS_FILE_MODE=reconcile` to apply the entry.
- **Browser requests in permissive mode.** An XML cross-origin request to a bucket without `cors` rules now succeeds, because `cors_fallback` defaults to `allow-all` there. Set `GCS_MIMIC_CORS_FALLBACK=none` to keep 0.13.0's refusal; strict mode keeps it by default.
- **403 and 401 messages.** A strict JSON or XML denial names the principal and the permission instead of "Forbidden", and an anonymous bucket or object denial reads "Anonymous caller does not have ..." instead of "Login Required". Tests that compare the whole message need the new text.
- **Parsers of the ready event.** New fields: `signed_host_port`, `signed_urls`, `test_signer`, and `buckets_file.unapplied` and `buckets_file.reconciled`. `cors_fallback` now reports `allow-all` for a default permissive server. `trusted_listen` and `trusted_principal` appear when the trusted listener is set, with the effective principal.
- **Timeout replies.** A server-side deadline on an upload answers 503 instead of 408. With `body_inactivity_timeout_ms` set, a silent XML request body answers 400 `RequestTimeout` instead of 408. Both 503 and 408 are retried by clients; 400 is not.
- **Reseed callers.** Failures that a retry cannot fix answer 400 or 403 without `Retry-After`.
- **Management Host.** A management request whose Host has an empty or non-numeric port now answers 400. It used to be accepted as the host without its port.
- **`url sign`.** Omitting both `--signer` and `--private-key` now signs as the test signer instead of failing.
- **Permissive signed URLs.** Nothing changes unless you set `signed_urls=verify`.

### Behavior changes in detail

- A request body is bounded only by `body_inactivity_timeout_ms` on every route. Before this release a small body on a route other than an object transfer was bounded by `request_timeout_ms` (180 seconds).
- A batch part inherits its envelope's listener and its browser and Host checks.

## Known limitations

- With the default `body_inactivity_timeout_ms` of 0, a client that stops sending a body holds its connection without any log line.
- The trusted listener keeps web pages out, but any program that reaches it with an accepted Host, such as its IP address, acts as `trusted_principal`. It speaks plain HTTP, and gRPC has none. Responses that hyper writes for a malformed request head carry no added headers.
- Rails Active Storage always sends its own self-signed JWT, so the trusted listener does not change it. In strict mode it signs with the test signer's credentials, as the recipe does.
- The built-in `trusted-app@gcs-mimic.invalid` and the undeclared test signer hold roles only in the projects of the buckets the bucket document creates (each entry's `project`, else the document's, else `seed_project`) and in `seed_project`. Declare an identity to reach other projects. Their implicit roles never count as an explicit grant, so directory synchronization controls, which require an explicit `roles/storage.admin`, still need a declared identity.
- An object that the test signer writes records it as owner, so with fine-grained ACLs it can change that object's ACL, as an owner can on Cloud Storage.
- The permissive `cors_fallback` default allows what Cloud Storage would refuse for a bucket without `cors` rules. The `cors_fallback_default` event names such buckets, and strict mode catches them.
- `signed_host_port=lenient` keeps the brackets of an IPv6 literal, so a signer that also removes them still fails. V2 signatures and POST policies do not sign Host and are unaffected.
- `reconcile` never resets a member an entry stops writing, replaces `labels` and `cors` as a whole, and cannot change a location.
- The limitations listed for [0.13.0](0.13.0.md#known-limitations) still apply, including that any catalog write clears the whole read cache, and these changes do not close the [1.0.0 gate](../release-policy.md#the-100-gate).
