# gcs-mimic 0.4.0

> [!NOTE]
> 0.4.0 was tagged but never published: its Windows release builds failed a
> test cleanup, so no GitHub Release, binary or image exists for it. Use
> [0.4.1](0.4.1.md), which contains every change below. The artifact names in
> these notes describe what 0.4.0 would have published.

0.4.0 closes every case of the
[Go and Ruby SDK scorecard](../../../sdk-scorecard/README.md): gcs-mimic now
passes 57 of 57 Go and 51 of 51 Ruby probes, up from 45 and 40 in 0.3.0. It adds
JSON ACL resources, project HMAC keys and the service agent, bucket
notification configurations, Autoclass, storage class on write, object
retention, customer-supplied encryption keys, V4 signed POST policy uploads and
gRPC appendable objects. It publishes `ghcr.io/shiroemons/gcs-mimic:0.4.0` for
`linux/amd64` and `linux/arm64`, mirrors the same digest to Docker Hub as
`shiroemons/gcs-mimic:0.4.0`, and publishes native archives for all eight
macOS, Windows and Linux targets. The
[0.3.0 release notes](https://github.com/shiroemons/gcs-mimic/blob/v0.3.0/docs/en/releases/0.3.0.md)
describe the previous release; the [feature matrix](../feature-matrix.md) lists
the exact supported subsets. Most new rows are `PARTIAL`: their local choices
and pending cases are recorded in the ledger and the linked contracts.

The first start migrates the data directory to a catalog schema that 0.3.0
cannot open. Read [Compatibility and migration](#compatibility-and-migration)
before upgrading a persistent deployment.

## Changes

### Access control

- Bucket, default object and object ACLs support list, get, insert, patch,
  update and delete. Stored default object ACLs are copied to new object
  generations; buckets and objects without stored entries report the
  project-private default. `projection=full` responses include `acl`,
  `defaultObjectAcl` and `owner` for buckets and `acl` for objects. Uniform
  bucket-level access rejects ACL operations, and public access prevention
  rejects public entities. ACL entries are metadata only: they do not yet grant
  or deny access. See the [ACL contract](../slices/json-acl.md).

### Projects

- `projects.hmacKeys` create, get, list, update and delete persist keys in the
  catalog and return the secret only on creation. At most ten keys that are not
  `DELETED` exist per project and service account. Keys do not yet sign
  requests.
- `projects.serviceAccount.get` returns a deterministic local service agent
  address. See the [project resources contract](../slices/project-hmac-keys.md).

### Buckets

- Notification configurations support insert, get, list and delete with topic
  normalization, payload format, event type and attribute validation.
  gcs-mimic never publishes to Pub/Sub. See the
  [notification contract](../slices/bucket-notifications.md).
- Autoclass can be enabled on create, patch and update over JSON and gRPC,
  with server-computed toggle times and a `NEARLINE` or `ARCHIVE` terminal
  class. Objects in an Autoclass bucket are stored as `STANDARD`; automatic
  class transitions are not modeled.
- `enableObjectRetention=true` on bucket creation enables object retention.

### Objects

- Uploads accept `storageClass` in JSON metadata, the XML
  `x-goog-storage-class` header and gRPC `WriteObjectSpec`.
- Object `retention` with `Unlocked` or `Locked` mode can be set on upload,
  patch and update. Deleting or replacing an object before its
  `retainUntilTime` returns 403; shortening or removing unlocked retention
  needs `overrideUnlockedRetention=true`. See the
  [object retention contract](../slices/sdk-object-retention.md).
- Customer-supplied encryption keys are accepted on JSON and XML uploads,
  downloads, copies, rewrites and compose. Reading data requires the matching
  key; metadata stays readable and reports `customerEncryption`. Only the key's
  SHA-256 is stored. See the
  [customer-supplied key contract](../slices/customer-supplied-keys.md).

### Signed POST policies

- XML `POST /BUCKET` accepts V4 signed policy form uploads with RSA signature,
  condition, size range and expiry checks, and streams the file through the
  shared write path. In strict mode a verified policy may be used from 15
  minutes before its `x-goog-date`, and its expiration may be at most seven
  days after it. See [signed POST policy uploads](../signed-urls.md#signed-post-policy-form-uploads).

### gRPC

- Storage v2 `BidiWriteObject` with `appendable` creates appendable objects that
  support flush, reads while appending, single-writer takeover with a write
  handle and finalization, on standard buckets. See the
  [Rapid append contract](../slices/grpc-v2-rapid-append.md).

### SDK scorecard

- The scorecard runner now resolves a relative `--out` directory before the
  Ruby probe runs, so a relative path no longer loses the Ruby results.

## Compatibility and migration

The first start migrates the catalog from `PRAGMA user_version = 27` (0.2.0
through 0.3.0) to `34`. The migration is one-way: after it runs, 0.3.0 and
earlier releases refuse to open the data directory. Back up the data directory
before upgrading if you may need to roll back. Existing buckets and objects keep
their contents and report the project-private ACL default, no Autoclass, no
object retention and no customer-supplied key.

- Requests that 0.3.0 rejected with 400 as unsupported now succeed: the ACL,
  notification configuration, HMAC key and service agent routes, Autoclass,
  `enableObjectRetention`, `storageClass` on upload, customer-supplied key
  headers and XML `POST /BUCKET`. Tests that relied on that rejection need
  updating.
- `projection=full` responses, including the default for bucket and object
  `PUT`, now contain ACL fields. Clients that compare `full` with `noAcl`
  output should ignore them.
- Creating or deleting a notification configuration and changing an ACL
  increment the parent bucket or object metageneration.
- Objects written with a customer-supplied key report an ETag without the MD5
  hash and omit `md5Hash` and `crc32c` unless the matching key is sent.

## Known limitations

- ACL entries do not grant or deny access, HMAC keys do not sign requests and
  notification configurations never publish events.
- Customer-supplied-key objects are stored unencrypted in the data directory
  and sync tree; gRPC cannot send keys, so it rejects reads of those objects.
- Unfinalized appendable objects are visible only over gRPC, and zonal Rapid
  bucket restrictions are not modeled.
- Autoclass class transitions, lifecycle `SetStorageClass` execution and XML
  object retention headers are not implemented.
- Error reasons chosen where the provider documentation is silent are local
  choices; the feature ledger records them.
- The [0.1.0 known limitations](0.1.0.md) and the feature matrix still apply
  to unimplemented API areas.
