# gcs-mimic 0.22.0

0.22.0 accepts and ignores the requester billing project (`userProject`) on every API, aligns more JSON and gRPC answers with recorded Cloud Storage behavior, and fixes directory synchronization bugs that could leave an API change out of the tree until a restart. It also reports more storage, import and startup failures with their own classification and remedy. Most of the code was rebuilt around typed errors along the way; that work changes no request or response beyond the ones listed here. No command, option, environment variable or configuration setting changes.

It publishes `ghcr.io/shiroemons/gcs-mimic:0.22.0` for `linux/amd64` and `linux/arm64`, mirrors the same digest to Docker Hub as `shiroemons/gcs-mimic:0.22.0`, and publishes native archives for all eight macOS, Windows and Linux targets. The [feature matrix](../feature-matrix.md) lists the exact supported subsets.

## What may need attention

- **`userProject` is ignored everywhere.** The JSON `userProject` parameter, the XML `userProject` query parameter and `x-goog-user-project` header, and the Storage v2 and legacy v1 billing project fields are accepted and ignored, as Cloud Storage serves them for a bucket and a project without Requester Pays. 0.21.0 refused them with 400 `badRequest`. No billing project permission is checked, and Requester Pays itself stays unsupported.
- **More options are served instead of refused.** JSON ignores `quotaUser` and `userIp`, as it already ignored `key`, and an object `kind` that names another resource on insert and PATCH; `oauth_token` and `callback` stay rejected. Storage v2 `ListBuckets` accepts `return_partial_success`, and `GetIamPolicy` serves policy versions 0 to 3.
- **gRPC `ComposeObject` and `MoveObject` answer without `acl` and `owner`,** as Cloud Storage does. `RewriteObject` keeps them.
- **A bucket with uniform bucket-level access carries no `owner` anywhere.** The fake-gcs-server profile added `owner: {"entity": "project-owners-0"}` to such a bucket with `projection=full` on insert, get, PATCH, PUT and restore, even for a strict caller without `storage.buckets.getIamPolicy`; it now omits it like the native profile, Cloud Storage and the pinned fake-gcs-server. Storage v2 returned the bucket `owner` under uniform access in both profiles; it now omits it there too, as recorded from Cloud Storage, which returns no `owner`, `acl` or `defaultObjectAcl` under uniform access. Buckets without uniform access keep their `owner`. The fake-gcs-server profile's `projectNumber` stays `"0"`, so its `owner` and `acl` entities name the local project number instead.
- **A move answers with the creation time it stores.** Storage v2 `MoveObject` returned `finalize_time` with nanosecond digits on Linux; it now carries the microsecond value a later read returns.
- **`fields` follows one grammar on every resource.** Buckets, the bucket list and the IAM policy now take the lenient selector grammar objects already used: whitespace alone and empty parentheses select nothing, and spaces around names and empty segments are ignored. Whitespace inside a name and a wildcard with a child answer 400 `invalidParameter` with Cloud Storage's wording. A resumable upload started with such a selection no longer fails at completion.
- **HMAC key answers match Cloud Storage.** An empty listing omits `items`; a `maxResults` that is not an unsigned 32-bit integer answers 400 `invalidParameter`; an update without `state` answers 400 `Must specify resource.state.`, and `state: DELETED` answers 400 `Cannot set state to 'DELETED'.`.
- **Corrupt stored values read as corrupt.** These now answer as corrupt (JSON 503, gRPC `UNAVAILABLE`) instead of being returned as stored: a bucket row whose location or location type is outside the official table; an Autoclass configuration whose enablement disagrees with its terminal class; a stored ACL entry, owner or IAM policy member whose entity has no valid form, or a stored policy with an unknown role or member type; and a synchronization row whose object name or generation does not fit its type. No release writes such values; they come only from hand-edited catalogs.

## Changes

### Directory synchronization

- An object deleted through the API while the initial baseline was still incomplete (for example, when an API write landed during the first reconciliation) kept its file in the tree forever: the removal waited for a baseline that the pending removal itself kept from completing, through rescans and restarts. API deletions now reach the tree before the baseline completes. A locally edited file is still kept as a conflict, and other removal paths keep the baseline requirement.
- A live export that had to preserve a conflicting external file, and found that file changed again or gone while it captured it, was skipped and not retried until a restart or a later API change to the same object; during the initial reconciliation it also kept the baseline from completing. The observer now runs that export again, with a new capture, once the tree settles, unless a journal replay or an ingested edit has moved the API or tracked generation since.
- When a preserved file changed again before the export installed the API's bytes, the export logged `sync_external_conflict` with the remedy to stop the writer and rescan, but the rescan never exported the API's current generation, and the baseline could not complete. The export now runs again after the next ingest pass, a rescan included, and the newer edit is kept as a separate conflict.
- On macOS, while ingestion could not take in an external edit (an export conflict, or an object under a hold), the observer repeated its ingest pass about every two seconds, because FSEvents reported the pass's own staging clone of the file as a change. A clone of an unchanged file no longer counts as a change, so the pass runs again only when the tree changes, as on Linux.
- Status, findings and deletion pages answer a hold, retention or missing target as a stale revision (409), as queued controls already did, instead of 503 busy.
- Conflict resolution answers catalog contention and a closing catalog with 503 `backendError` and asks for a retry with the same operation ID, and answers corrupt stored state with the guidance to restore a valid data directory. Storage failures keep `disk_full` and `io_failure`. A restore that meets a storage failure while it re-checks the original object stops the batch with 503 instead of reporting a changed target, and so would contention or a closing catalog there, which that check cannot meet today.

### Import

- A JSON sidecar, bucket attribute file or `snapshot.jsonl` that changes while it is read reports every field that changed on both its handle and its name, as a body read already did. A file replaced during the read is no longer reported as change-time-only drift that a resume would retry.
- On Windows, a filesystem-format object created or updated before 1601 is reported by the scan as a `<path>:Created` or `<path>:Updated` blocker, so a dry run reports it ineligible instead of the import failing later.
- A memory snapshot whose bucket ACL or object retention cannot be read is reported as a corrupt snapshot under `.:snapshot` instead of a source I/O failure.

### gRPC

- A read mask that mixes `*` with field names answers `INVALID_ARGUMENT` with Cloud Storage's message.
- An `UpdateBucket` whose update mask names a single label (`labels.KEY`) is refused with the same `INVALID_ARGUMENT` before authorization and preconditions are checked.

### Stored data written by earlier releases

- A lifecycle configuration that v0.17.1 or earlier stored with its keys in another order is read as typed rules, so JSON get and list render its keys in canonical order. The stored bytes do not change.
- A bucket that enabled versioning before catalog schema 49 reads as enabled and is rewritten in the current form on its next update. A buckets file entry with `enabled: true` no longer patches such a bucket, and a fake-gcs-server profile entry with `enabled: null` now disables it instead of leaving it unset; that profile's JSON output is unchanged.
- An ACL entity longer than 272 bytes, which releases before 0.12.0 could store, now renders its derived `email`, `entityId`, `domain` or `projectTeam` field. Authorization is unchanged, since such an entity names no principal.

### Server, startup and diagnostics

- A request that times out answers in the format of the API serving it: a stalled Discovery resumable initiation answers the JSON 408 `uploadBrokenConnection`, and an XML bucket operation without an object path answers in XML.
- In the fake-gcs-server profile with `public_base_url` set, a legacy V2 signature over the public host's root path now verifies against the path-style resource `/`.
- Startup names the setting to fix when the gRPC listener's address cannot be read, when a seed exceeds its fixture metadata budget or `max_object_bytes`, and when a Unix socket cannot be removed at shutdown. A corrupt catalog found by the retention and customer key migrations is reported as corrupt.
- Paths that no request reaches today answer 503 instead of a misleading status or a panic: a management result that cannot be encoded (reset, reseed, lifecycle, synchronization wait, conflict resolution and recovery findings), a resumable session lease from another catalog, a listing whose rendered items no longer match their records, and an ACL projection over a resource that is not a JSON object.
- Log lines and diagnostics no longer repeat the `catalog unavailable:` prefix. A write-back failure's logged cause names the failed conflict store or displaced installation instead of a generic backend failure, and a publication batch's fatal element failure is logged one cause shallower. Rewrite and derived-transfer maintenance sweeps log later failures as `resumable_maintenance_retry` warnings like the other sweeps. A damaged queued notification topic is reported as an invalid topic.
- Exclusive catalog jobs wake when leases drain instead of polling.

## Compatibility and migration

The catalog schema is unchanged at 53, so a data directory moves between 0.21.0 and 0.22.0 in either direction without a migration. Apart from the changes listed under [What may need attention](#what-may-need-attention), each change accepts a request that 0.21.0 refused, reports a failure 0.21.0 misreported, or brings an answer closer to Cloud Storage.

A `gcs-mimic sync` command and the server it manages must still be the same release, so upgrade both together. The Go package accepts a binary of the same minor release, so upgrade `go/fakestorage` to 0.22.0 together with the binary.

## Dependencies and project

- No Rust dependency, Rust toolchain or container base changes. The Go package moves to `google.golang.org/api` v0.315.0; the Go SDK suites and scorecard follow, and the Java scorecard adopts `google-auth-library-oauth2-http` 1.58.0. The package version and the Go package's `moduleVersion` move to `0.22.0`, and the recipes pin `0.22.0`.
- The [feature ledger](../../../compatibility/features.json) promotes ten rows to `IMPLEMENTED` whose remaining items are recorded scoped choices (the five HMAC key routes, three notification routes, and one design and one audit row), and separates Google infrastructure simulations (lifecycle execution, Pub/Sub delivery, strict authentication) from API contract rows by their target fidelity.
- The differential reference grows from 99 to 108 cases, recording bucket edge cases and options gcs-mimic refused; every remaining difference is marked in its case as a local choice with its reason, so the replay still checks it.
- The production lint gate rejects every rule it checks: wildcard matches on project enums, hidden `json!` conversions, downcasts outside panic payloads and immediately invoked closures joined the zero-tolerance rules.
- The differential harness and dependency checks report errors they used to swallow or panic on.

## Known limitations

- The released-data fixtures for 0.22.0 are added after publication, as for earlier releases.
- Directory synchronization ingests a local edit that object retention deferred only on the next tree change, rescan or wait after the retention expires: expiry writes nothing to the catalog and the observer keeps no timer for it. An edit that a hold deferred is preserved as a conflict when the hold is released, like any edit an API change meets, and is published with a conflict restore.
- The limitations listed for [0.21.0](0.21.0.md#known-limitations) still apply, and these changes do not close the [1.0.0 gate](../release-policy.md#the-100-gate).
