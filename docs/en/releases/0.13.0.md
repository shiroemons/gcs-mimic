# gcs-mimic 0.13.0

0.13.0 makes object reads fast. Metadata and downloads no longer wait in line for the one catalog thread, small downloads no longer wait about 40 ms for a delayed acknowledgement, and the container image uses an allocator that scales with its threads. One default changes, so read [Compatibility and migration](#compatibility-and-migration) before upgrading.

It publishes `ghcr.io/shiroemons/gcs-mimic:0.13.0` for `linux/amd64` and `linux/arm64`, mirrors the same digest to Docker Hub as `shiroemons/gcs-mimic:0.13.0`, and publishes native archives for all eight macOS, Windows and Linux targets. The [feature matrix](../feature-matrix.md) lists the exact supported subsets. Rows marked `PARTIAL` keep their listed missing cases.

## Changes

### Object reads

- With the disk backend, object and bucket reads run on up to eight read-only SQLite connections, each on its own thread, beside the one writer. A read still sees every write that finished before it began. Once a reset, reseed or seed commit waits for its turn, reads line up behind it as before. With `--backend memory`, reads stay on the writer.
- Repeated reads of live objects with permissive access answer from memory until the next catalog write: at most 4096 records and 16 MiB of them, and at most 1024 files kept open or a quarter of the open-file limit, whichever is lower. Strict authentication still checks every request, objects under a customer-supplied key never enter, and object bytes stay in the operating system's page cache.
- On Linux, bytes already in the page cache are read with `preadv2(RWF_NOWAIT)` on the request's own worker instead of on the blocking pool. Other bytes, and every read on other systems, use the blocking pool as before.
- The connection pulls a download's body as it can send it, so a slow client holds one frame: up to 1 MiB while more than that remains, then up to 256 KiB. A small object or a gRPC chunk holds a buffer of its own size, and gRPC keeps its 64 KiB chunks.
- Accepted TCP connections disable Nagle's algorithm. It held the last segment of a response until the client acknowledged the earlier ones, and a delayed acknowledgement made every small download take about 42 ms.

### Defaults

| Setting | 0.12.0 | 0.13.0 | Accepted values |
| --- | --- | --- | --- |
| `worker_threads` | 2 | Available CPUs from 2 to 8; on Linux the count honors a container's CPU quota and affinity | 1 to 1024 |

Two workers served eight concurrent 10 MiB downloads at about a third of the rate eight workers did. The upper bound leaves CPUs to the application under test, which usually runs on the same machine.

### Container image and musl binaries

These apply to the container image and the two `unknown-linux-musl` archives. The other native archives keep their C library's allocator and are unchanged.

- `mimalloc` 0.1.52 is the global allocator. musl's own allocator takes one global lock, which held the container near 11,700 metadata reads per second at every concurrency from 1 to 128 connections. Its Microsoft license ships with the other notices.
- The binary disables transparent huge pages for its own process with `prctl(PR_SET_THP_DISABLE)`. With them set to `always`, as in Docker Desktop's VM, the allocator's memory became resident 2 MiB at a time, at the same speed.
- An earlier trial had rejected an allocator dependency because it doubled resident memory. That memory came mostly from huge pages, and the catalog thread then capped reads before the allocator could matter. The [dependency evidence](../evidence/dependency-refresh.md#musl-allocator) records the reversal.
- The image grows by about 0.4 MB.

### JSON API

- A refused object list page token of up to 256 bytes is repeated in the error message, as Cloud Storage repeats it. A longer token still gets the message without it, so an error's size stays independent of the request.

### Dependencies and project

- `mimalloc` 0.1.52 and `libmimalloc-sys` 0.1.49 are new, resolved only for musl targets.
- The Java SDK suite and scorecard use `google-cloud-storage` 2.78.0.
- The recorded Cloud Storage answers are replayed against every push, and a gRPC timestamp that drops trailing zero digits no longer counts as a difference there.
- A daily job proposes container images rebuilt under an unchanged tag as a pull request, which nothing merges automatically. A release tag publishes the archives of its dry run instead of building them again.
- The [read path measurement](../evidence/read-path-performance.md) records the comparison below.

## Compatibility and migration

The catalog schema stays at 51. No migration runs, and 0.12.0 can still open a data directory that 0.13.0 has used.

### Upgrade checklist

- **Worker threads.** Set `GCS_MIMIC_WORKER_THREADS=2` to keep 0.12.0's count, for example when the emulator shares a small machine with a heavy test suite. An explicit value still applies.
- **Memory.** A busy server now holds more memory than 0.12.0. After 1,000 objects of 100 KiB were read at 32 connections, the container image's process held 31.8 MiB against 10.5 MiB. The reader connections, the cached records, reusable buffers of up to 24 MiB and the allocator's retained pages account for it. It does not grow with object size or count beyond the cache limits.
- **Open files.** The read cache can keep up to 1024 object files open, or a quarter of the open-file limit, whichever is lower. Each write closes them.
- **Log events.** `catalog_reader_unavailable` (debug) reports a read-only connection or its thread that could not be prepared; the writer answers that read instead. `tcp_nodelay_failed` (debug) reports a connection on which Nagle's algorithm could not be disabled.

## Known limitations

- Any catalog write clears the whole read cache, and the writer thread closes the cached files, up to 1024 of them. A server that writes steadily, for example one delivering notifications, gains little from the cache.
- At 10 MiB and 128 connections, downloads were 6 to 12% slower than fake-gcs-server in both recorded runs. One 10 MiB download at a time varied by more than its gap to fake-gcs-server between runs on the same build.
- At 1 MiB and 128 connections the median latency is above fake-gcs-server's, though the mean and the 95th and 99th percentiles are lower.
- On macOS, Windows and other systems without `RWF_NOWAIT`, downloads read on the blocking pool as before.
- The measurements come from one Docker Desktop host. Linux hosts, mixed reads and writes, strict authentication, gRPC, TLS and HTTP/2 were not measured.
- The limitations listed for [0.12.0](0.12.0.md#known-limitations) still apply, and these changes do not close the [1.0.0 gate](../release-policy.md#the-100-gate).
