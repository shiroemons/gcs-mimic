# gcs-mimic 0.6.0

0.6.0 is a reliability release. One faulty request, background job or panic no
longer stops the server or leaves it silently degraded, failed writes and
syncs no longer publish short objects, and readiness reports stopped
background work. It regenerates the built-in development TLS CA so Python
3.13+ clients pass their default strict checks, accepts the Node.js SDK's
default single-request resumable upload, and adds official Node.js, Python and
PHP SDK suites. It publishes `ghcr.io/shiroemons/gcs-mimic:0.6.0` for
`linux/amd64` and `linux/arm64`, mirrors the same digest to Docker Hub as
`shiroemons/gcs-mimic:0.6.0`, and publishes native archives for all eight
macOS, Windows and Linux targets. The [0.5.0 release notes](0.5.0.md) describe
the previous published release; the [feature matrix](../feature-matrix.md)
lists the exact supported subsets.

The built-in development CA changed. HTTPS clients that trust a CA exported
from 0.5.0 or earlier must export it again; see
[Compatibility and migration](#compatibility-and-migration).

## Changes

### Uploads

- Resumable uploads accept the open-ended `Content-Range: bytes start-*/total`
  and `bytes 0-*/*` forms as a final request, as the Node.js SDK sends for its
  default single-request upload. A known total, a declared `Content-Length` or
  the end of a chunked body fixes the object size; the body stays bounded by
  the object size limit. Short, long, gapped and conflicting requests fail
  without advancing the acknowledged prefix.

### Local HTTPS

- The built-in development CA, leaf certificate and leaf key now carry Subject
  and Authority Key Identifiers, so Python 3.13+ clients accept the server
  with their default `VERIFY_X509_STRICT` checks. Subject names, P-256 keys,
  SANs and the ten-year validity are unchanged.
  `scripts/tls-development-cert.sh` regenerates the set reproducibly and checks
  the chain with `-x509_strict`. See [Local HTTPS](../local-https.md).

### Durability

- Uploads, resumable chunks and copy, rewrite and compose transfers flush each
  blob before syncing it. A failed final write previously went unreported, so
  an upload could publish metadata for the full size over a shorter blob.
- Appendable objects write and sync through one file descriptor, so a sync
  reports an earlier writeback failure. A failed sync rolls the writer back to
  its persisted size, so the client must send those bytes again.
- A cancelled append keeps its writer slot until its file operation ends, so
  it cannot write through an old descriptor after a takeover.
- Finalizing an appendable object removes its appendable record in the same
  transaction that publishes the generation. A failed separate cleanup could
  previously make a deleted object serve its old bytes again.

### Fault isolation and readiness

- A panicking HTTP connection is logged and closed; the server keeps
  accepting other connections. Previously it stopped the whole server.
- A panic inside a catalog operation rolls back its transaction and fails only
  that request. Previously every later request returned 503 until restart.
- Publication workers and the blob shard creator keep working after a
  panicking job.
- Background tasks run supervised. Resumable maintenance restarts after a
  panic with exponential backoff; readiness turns off after three consecutive
  failed passes and recovers on the next successful one.
- `/_internal/ready` turns off when the sync mirror stops, instead of staying
  200. Transient mirror failures, such as catalog contention or interrupted
  I/O, are retried with backoff; invalid names, permission errors, corruption
  and panics still stop the mirror.
- Seeding fails when the directory walk stops before it finishes, instead of
  marking a partial seed complete.

### Error reporting

- Compose, copy, rewrite and resumable chunk transfers report a corrupt
  catalog or a full disk with the same actionable 503 message as single-shot
  uploads, instead of a generic `backendError`. Status codes are unchanged.
- A closed catalog is reported as closed instead of full.
- On Windows, a blob destination without a file name returns an error instead
  of panicking.

### Downloads

- Object downloads no longer lose their last chunk when the body producer
  finishes. Rarely, and more often under load, a response previously ended
  before its `Content-Length`.

### Performance

- The default `--max-blocking-threads` (`GCS_MIMIC_MAX_BLOCKING_THREADS`) is
  8 instead of 2, so one slow fsync no longer stalls every other transfer. The
  accepted range is still 1–32.
- The catalog runs its operations on a dedicated thread instead of the shared
  blocking pool, so file I/O and gzip work no longer delay metadata requests.
- Request paths and request-driven maintenance reuse cached prepared
  statements.
- HTTP and gRPC object bodies stream without zero-filling or copying each
  frame. Chunk sizes, channel capacities and limits are unchanged.

### SDK tests

- `just check-sdk` also runs pinned official Node.js, Python and PHP SDK
  suites against isolated permissive and strict servers over HTTP and HTTPS,
  beside the Go and Ruby suites. See [sdk-tests](../../../sdk-tests/node/README.md).

### Build and checks

- `just check` also runs Clippy for the Linux glibc target, so size lints that
  depend on Linux std types fail locally rather than only in CI.
- The release workflow's freshness gate checks only inputs that build or ship
  release artifacts: the Rust toolchain, direct Cargo dependencies, GitHub
  Actions and the container build and runtime images. SDK suite dependencies
  and test-only images are still checked daily but no longer block a release.
  See the [dependency policy](../dependency-policy.md#ci-lanes).
- Production code passes a lint gate, `cargo xtask lint`, that rejects
  unsupervised spawns, uncached SQL on request paths, stringified errors and
  file syncs without a preceding flush. See [Development](../development.md).

## Compatibility and migration

0.6.0 uses the same catalog schema, 35, as 0.5.0, so a data directory from
0.5.0 needs no migration. Upgrading from 0.4.1 or earlier also applies the
[0.5.0 migration](0.5.0.md#compatibility-and-migration).

- The built-in development CA is new. A CA exported from gcs-mimic 0.5.0 or
  earlier does not verify the 0.6.0 certificate. Run `gcs-mimic tls ca` again
  and replace the copy that your clients, containers or test profiles trust.
  Deployments that set `GCS_MIMIC_TLS_DIR` to a custom CA are unaffected.
- `/_internal/ready`, and therefore the container healthcheck, now reports not
  ready when the sync mirror stops or resumable maintenance keeps failing.
  0.5.0 reported ready in both cases.
- The default blocking thread cap rose from 2 to 8. Set
  `--max-blocking-threads 2` to keep the earlier bound.
- Resumable requests with `Content-Range: bytes 0-*/*` returned 400 in 0.5.0
  and now finalize the upload.

## Verification

The [release workflow](https://github.com/shiroemons/gcs-mimic/blob/v0.6.0/.github/workflows/binaries.yaml)
creates this Release only after `validate`, including the dependency freshness
check, Foundation and all eight native build/test jobs succeed at the tag's
SHA. The
[container workflow](https://github.com/shiroemons/gcs-mimic/blob/v0.6.0/.github/workflows/ghcr.yaml)
then builds both Linux architectures natively, verifies their SBOM and
provenance, publishes the multi-architecture tag and checks anonymous pulls,
and the Docker Hub workflow mirrors that digest.

Before the release commit, the pre-push checks passed locally on macOS: format,
clippy, cross-compilation checks including the Linux glibc target, all 49 Rust
test binaries and doctests, the compatibility ledger check, the pinned Go,
Ruby, Node.js, Python and PHP SDK suites, and both Linux container smoke
tests. The Foundation checks passed in CI at `526e066`, the last code change
before this release. The release-input freshness check
(`cargo xtask dependencies check --scope release`) reported every input
current.

The full freshness check reports one development-only drift, recorded as the
`composer-riscv64-publication-lag` exception: the official `composer:latest`
index still carries the 2.10.3 riscv64 image, so it differs from the pinned
Composer 2.11.0 index used by the PHP SDK suite and scorecard. The amd64 and
arm64 images are identical under both indexes, and no release artifact
contains Composer.

## Known limitations

- The Node.js, Python and PHP suites cover the basic API milestone and local
  transport, not full SDK compatibility; each suite's README records the
  journeys it does not cover.
- The [0.5.0 known limitations](0.5.0.md#known-limitations) still apply.
