# Stored lifecycle Delete rules now execute

This change targets the next release. Previously, lifecycle rules were stored and returned without executing their actions. Without directory synchronization, stored `Delete` rules now execute automatically after upgrade, including rules already present in the catalog. Existing objects that satisfy those rules can therefore be deleted immediately after maintenance starts.

With `sync_dir`, execution defaults to disabled to preserve host files. To enable it explicitly, use `--lifecycle-execution enabled`, `GCS_MIMIC_LIFECYCLE_EXECUTION=enabled`, or JSON `"lifecycle_execution":"enabled"`. Enabled Delete actions also remove synchronized host files, like ordinary API deletes. Use `disabled` to preserve store-only behavior in either mode. CLI > environment > JSON > default precedence applies. Ready reports the effective `lifecycle_execution`; a diagnostic explains how to opt in when stored rules are disabled by the synchronization default, whether present at startup or first added later.

Deletion respects holds, bucket retention, object retention, versioning and each bucket's soft-delete policy. Versioned live objects first become noncurrent at the physical pass time; noncurrent actions begin on a later pass. Notification and soft/hard-delete times also use the physical clock. Soft-deleted generations remain under their existing expiry policy. Buckets without soft delete permanently lose deleted bytes.

Starting a previously synchronized data directory without `sync_dir` enables lifecycle execution by default. Deletions made during that run can remove previously tracked host files when synchronization resumes; set `lifecycle_execution=disabled` during that run to keep stored rules inactive.

Supported `SetStorageClass` rules now execute in place, preserving object generations and body bytes while updating metageneration, class timestamps and metadata notifications. Class-dependent Delete rules now match the stored class, including after a transition in the same pass. Upgrading can therefore change classes and activate previously deferred deletions as soon as stored rules match. Use `lifecycle_execution=disabled` before startup to preserve store-only behavior. With synchronization enabled, a class change does not rewrite or re-export host file bytes; a matching Delete can still remove the file.

A pass evaluates current rules and facts at the current time. A matching Delete without a storage-class condition wins. If all matching Deletes have `matchesStorageClass` and an applicable transition exists, the coldest eligible supported transition wins instead. This explicit local difference from Google's Delete-first priority protects the common case of Nearline at age 30 plus Standard-only Delete at age 60: a first pass at age 100 retains the object in Nearline. The new class is evaluated again at the same time, so a Delete still matching it runs immediately. A selected protected independent Delete blocks transitions; a class-dependent Delete that yields does not.

Delayed execution can differ from timely execution in either direction. It can retain an object whose class-dependent Delete would have run earlier. It can also delete an object that timely execution would retain in three documented forms: descending scans remove successors needed by an older version's `numNewerVersions` transition; an overwrite during a stop removes a live-only transition opportunity; or class-gated transitions take a different path because a delayed pass chooses a colder class directly. Paired tests fix all three examples. A bounded independent-oracle test finds no delayed-only deletion for a single version with fixed facts when no transition has `matchesStorageClass`; it does not establish a general multi-version or history guarantee.

Rules added to aged objects take effect against current state without historical replay. Custom-Time is effective immediately, including backdated values. Versions are scanned in descending primary-key order, and the strict 1024-action limit can stop midway through a generation's transitions. Continuation resumes from the stored class. No additional persistent state or configuration is introduced.

Opening a data directory upgrades catalog schema 52 to 53, even with lifecycle execution disabled. Back up the complete stopped data directory first. Older binaries supporting schema 52 refuse the upgraded catalog; rollback requires restoring the pre-upgrade backup, not an in-place downgrade.

The guarded `POST /_internal/lifecycle/run` route runs one pass using the current clock and returns `enabled` and action counts, including `transitioned` for class changes and `skipped` for malformed stored versions. Corrupt rules or versions are isolated with a diagnostic emitted once per revision, so healthy objects and buckets continue. `AbortIncompleteMultipartUpload` remains stored without execution. See the [execution contract](../slices/lifecycle-execution.md) and [storage class contract](../slices/lifecycle-storage-class.md) for supported transitions, upgrade evidence and provider differences.
