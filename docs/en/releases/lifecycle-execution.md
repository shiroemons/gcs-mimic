# Stored lifecycle Delete rules now execute

This change targets the next release. Previously, lifecycle rules were stored and returned without executing their actions. Without directory synchronization, stored `Delete` rules now execute automatically after upgrade, including rules already present in the catalog. Existing objects that satisfy those rules can therefore be deleted immediately after maintenance starts.

With `sync_dir`, execution defaults to disabled to preserve host files. To enable it explicitly, use `--lifecycle-execution enabled`, `GCS_MIMIC_LIFECYCLE_EXECUTION=enabled`, or JSON `"lifecycle_execution":"enabled"`. Enabled Delete actions also remove synchronized host files, like ordinary API deletes. Use `disabled` to preserve store-only behavior in either mode. CLI > environment > JSON > default precedence applies. Ready reports the effective `lifecycle_execution`; a diagnostic explains how to opt in when stored rules are disabled by the synchronization default, whether present at startup or first added later.

Deletion respects holds, bucket retention, object retention, versioning and each bucket's soft-delete policy. Versioned live objects first become noncurrent; matching noncurrent generations are removed on later passes. Soft-deleted generations remain under their existing expiry policy. Buckets without soft delete permanently lose deleted bytes.

Starting a previously synchronized data directory without `sync_dir` enables lifecycle execution by default. Deletions made during that run can remove previously tracked host files when synchronization resumes; set `lifecycle_execution=disabled` during that run to keep stored rules inactive.

The guarded `POST /_internal/lifecycle/run` route runs one pass using the current clock and returns `enabled` and action counts, including `skipped` for malformed stored versions. Corrupt rules or versions are isolated with a diagnostic emitted once per revision, so healthy objects and buckets continue. `SetStorageClass` and `AbortIncompleteMultipartUpload` remain stored without execution. Every Delete rule containing `matchesStorageClass` is deferred until storage transitions execute, including after transition rules have been removed. Other Delete rules still execute. No catalog migration is required. See the [execution contract](../slices/lifecycle-execution.md) for scheduling, supported scope and provider differences.
