# Storage v2 bucket operations

<!-- markdownlint-configure-file {"MD013": false} -->

Scope: RPC-STORAGE-001–004, the bucket portion of BEHAVIOR-RPC-001 and AUDIT-008. All broader rows remain PARTIAL until their remaining contracts are verified. The [2026-11-18 bucket changes](#bucket-changes-on-2026-11-18) also cover UpdateBucket, LockBucketRetentionPolicy and SetIamPolicy (RPC-STORAGE-005, 007 and 009) and the bucket cases of BEHAVIOR-RPC-002, whose contract is the [update/copy slice](grpc-v2-update-copy.md).

## Acceptance contract

- Parse `projects/_/buckets/NAME`, reject malformed names with INVALID_ARGUMENT, and decode `x-goog-request-params` routing metadata without allowing it to override the request.
- Get existing buckets, return NOT_FOUND for missing buckets, enforce both metageneration conditions, and project supported read masks. Unsupported mask fields return UNIMPLEMENTED with ErrorInfo. The settings bucket creation and update refuse (`billing`, `custom_placement_config`, `encryption`, `hierarchical_namespace`, `ip_filter`, `logging`, `rpo`, `website`) are never stored, so a read mask may select them and gets them unset, as Cloud Storage answered for a bucket without them (case `grpc-bucket-unset-settings-mask`, recorded 2026-11-15). The Java SDK names every one of them in its default bucket read mask. `satisfies_pzs` and nested paths stay UNIMPLEMENTED.
- Create using empty or `projects/_` parent and `bucket.project = projects/<id>` (including `_`), with the JSON-supported metadata subset. Duplicate names return ALREADY_EXISTS. Unsupported semantics return UNIMPLEMENTED rather than being ignored.
- List by project and prefix with bounded page size and project/prefix-bound continuation tokens.
- Delete empty buckets with atomic metageneration conditions; nonempty buckets return FAILED_PRECONDITION and retain their contents. A live or noncurrent object keeps the bucket; soft-deleted objects and unfinished XML multipart uploads do not, as the proto says (storage.proto lines 76-95), and neither does an unfinalized appendable object, a local choice described below. A bucket with a soft delete policy is kept as a soft-deleted version.
- Reuse shared authorization: strict requests denied without credentials return UNAUTHENTICATED and registered callers without permission receive PERMISSION_DENIED. Anonymous Get/Delete honors effective allUsers grants and public access prevention, exactly like JSON.
- Ordinary Go `storage.NewGRPCClient(ctx)` supports Bucket.Create, Bucket.Attrs, Buckets iteration and Bucket.Delete with omitted optional arguments.
- JSON-created buckets are visible through gRPC and gRPC-created buckets are visible through JSON.

## Boundaries and sources

No setting, dependency, storage implementation or startup change is needed. CreateBucket reuses shared typed retention, soft-delete, PAP, CORS and Autoclass validators. Creation still builds a JSON insert resource for the remaining creation fields; a shared creation builder is not yet implemented, and this operation stays PARTIAL. UpdateBucket constructs shared typed updates directly. Both use shared bucket authorization and the transactional catalog. Bucket deletion and listing retain catalog concurrency and memory bounds.

Deletion implements the shared native empty-bucket contract through the same catalog transaction as JSON, including the soft-deleted version a bucket with a soft delete policy leaves ([bucket soft delete](bucket-soft-delete-restore.md)); the pinned Storage v2 proto has no RPC that lists or restores soft-deleted buckets. An unfinished XML multipart upload does not keep a bucket. Neither does an unfinalized appendable object, a recorded local choice: the proto does not say whether one is a live object, and its open writer finds it superseded at the next flush.

Create supports location, storage class, labels, CORS, versioning, default event hold, retention/soft-delete durations and IAM uniform access/public access prevention through the same native JSON validation. Empty or disabled unsupported configurations that equal their protobuf defaults, and `rpo=DEFAULT`, are accepted; an empty `website` message is the exception and is refused. A retention duration's nanos are rounded down to whole seconds, as the proto says (storage.proto lines 2429-2433) and as UpdateBucket does, so a duration under one second is no period and answers INVALID_ARGUMENT. Fields the proto marks OUTPUT_ONLY (`bucket_id`, `metageneration`, `location_type`, `create_time`, `update_time`, `owner` and the Autoclass `toggle_time` and `terminal_storage_class_update_time`) are ignored, as `google.api.field_behavior` requires, and the new bucket carries the server's values. Autoclass uses the shared configuration rules in [bucket-autoclass-storage-class](bucket-autoclass-storage-class.md). Object retention is enabled by `enable_object_retention` ([SDK parity](grpc-v2-sdk-parity.md)). Billing, encryption, logging, website, custom placement, hierarchical namespace, IP filtering, `satisfies_pzs=true` and an `rpo` other than `DEFAULT` return UNIMPLEMENTED on purpose: the JSON API stores none of them either (SPEC-GRPC-UNMODELED-SETTINGS). A nonempty lifecycle, bucket or default object ACL and the predefined ACLs also return UNIMPLEMENTED today; those are pending work, listed under [ledger cases](#ledger-cases). A fractional soft delete duration, a nonempty `etag`, a retention or soft delete `effective_time`, a locked retention policy and a uniform access `lock_time` are refused as recorded local choices: the proto states no rounding for the first and does not mark the others output only (SPEC-GRPC-LOCAL-CHOICES).

Read masks support the top-level fields `name`, `bucket_id`, `etag`, `project`, `metageneration`, `location`, `location_type`, `storage_class`, `autoclass`, `labels`, `create_time`, `update_time`, `default_event_based_hold`, `versioning`, `cors`, `lifecycle`, `retention_policy`, `soft_delete_policy`, `object_retention` and `iam_config` ([SDK parity](grpc-v2-sdk-parity.md)), and the never-stored settings, which come back unset. Absent/empty masks and a single `*` return this converted subset. `*` beside a name returns INVALID_ARGUMENT with Cloud Storage's recorded message. Nested paths and names that are no Bucket field return UNIMPLEMENTED; `satisfies_pzs` returns UNIMPLEMENTED on purpose. A name that is no Bucket field stays UNIMPLEMENTED as a recorded local choice, although Cloud Storage answered an unknown object path with INVALID_ARGUMENT: no bucket answer was recorded, and an existing status changes only on proto text. GetBucket checks the mask right after the bucket name, before authorization and lookup; ListBuckets checks it after the caller, the project permission, `page_size` and `prefix` and before the page token (SPEC-GRPC-LOCAL-CHOICES). List uses the same mask rules and accepts `return_partial_success`, which changes nothing because every local bucket is reachable.

The bucket resource matches the whole Storage v2 UpdateBucket response Cloud Storage returned on 2026-11-17 (case `bkt-gaps-legacy-class-region`, step `grpc-update-bucket-class-regional`) and the whole GetBucket response under the Java SDK's default mask (case `grpc-bucket-unset-settings-mask`), with no ignored fields. Each bucket and default object ACL entry for a team of the bucket's project carries `entity_alt` naming the project ID (`project-owners-{id}`), as object ACL entries do; a team of another project number has none, because gcs-mimic cannot tell which ID that number stands for ([project numbers](project-numbers.md)). `create_time` and `update_time` carry milliseconds, as recorded; the retention and soft delete effective times, the Autoclass times and the uniform access lock time are floored to the millisecond too, the precision JSON renders every bucket time with (inferred, not recorded for Storage v2). A soft delete policy whose duration is 0 has no `effective_time`, as JSON already reported it. Page size defaults to 1000 and is capped at 1000; a negative size is invalid. Tokens are opaque project/prefix-bound catalog cursors shared with JSON, not provider-compatible token bytes.

Every Storage v2 RPC validates routing metadata at the common entry point.
Routing follows the pinned proto's bucket/project captures and source_bucket for
rewrite sources. Streaming calls compare the first message; rewrite continuations
compare the token's bound names. Values are form-percent-decoded and conflicting
values fail INVALID_ARGUMENT. Create compares project against bucket.project.
Rapid writes also compare appendable. Go direct_connectivity_diagnostic is
accepted as diagnostics. Other semantic keys, including redirect tokens, return
UNIMPLEMENTED. Routing cannot change catalog selection or authorization.
Bucket IDs follow the configured native or fake-gcs-server naming profile in
both bucket and object RPCs. The invalid-name and conflict statuses are a recorded
local choice under SPEC-GRPC-ROUTING-NAMES; a run of the Go and Rust gRPC SDK lanes
against these checks remains pending.

`x-goog-user-project` is ignored on every Storage v2 RPC, including an empty value, as the JSON API ignores userProject since 2026-11-13 (SPEC-SDK-UNSUPPORTED): a local bucket cannot enable Requester Pays, so the billing project cannot change a result. The default Go client does not send this header, and `Bucket.UserProject` with or without a project is accepted alike. Shared `status::from_json` converts adapter failures consistently, including backend HTTP 503 to UNAVAILABLE and unsupported emulator semantics to ErrorInfo-bearing UNIMPLEMENTED even when JSON represents those limitations as HTTP 400.

The [pinned Storage v2 proto](https://github.com/googleapis/googleapis/blob/933dd1be8180a22bca2dc473b53d4f4297ee3b0c/google/storage/v2/storage.proto) was retrieved and its SHA-256 matched `a0df6132967b97a89be248f1f24d277ee8df8f8d885db1d4af6249469ff0c1cf` on 2026-10-27. In particular, CreateBucket.parent is empty or projects/_; the owner belongs in bucket.project. A request may name the project by ID or by the number its buckets render, and a ListBuckets page token continues under either spelling (BEHAVIOR-COMMON-014). Storage v1 and object cross-transport semantics are outside this slice.

## Bucket changes on 2026-11-18

Each change below was pinned by a test of the earlier answer before the code changed; the two behavior changes first failed on the unchanged code.

- UpdateBucket honors `bucket.etag`: the proto says that, "If included in the metadata of an `UpdateBucketRequest`, the operation is only performed if the `etag` matches that of the bucket" (storage.proto lines 2581-2584). After authorization the handler reads the bucket, answers a stale or foreign ETag with the FAILED_PRECONDITION a failed metageneration condition returns, and otherwise passes the matching metageneration to the catalog as an explicit match condition, compared atomically with the write. A bucket ETag encodes only the metageneration, so the two conditions are equivalent. A missing bucket stays NOT_FOUND, and an update without an ETag is unchanged (`grpc_bucket_update_requires_a_matching_etag`).
- CreateBucket rounds a fractional retention duration down and ignores output-only fields, as described above (`create_bucket_rounds_retention_nanos_down`, `create_bucket_ignores_output_only_fields`); UpdateBucket's rounding is pinned by `grpc_bucket_update_rounds_retention_nanos_down`.
- UpdateBucket parses each `update_mask` path once into a typed `UpdatePath` and applies it in mask order. Its answers are unchanged and pinned by `update_mask_paths_select_their_settings_and_refuse_the_rest`: each accepted path changes only its own setting, and every other path, an empty label key, other case spellings, subpaths of the accepted fields and output-only fields included, returns UNIMPLEMENTED naming the path.
- Bucket metageneration conditions keep each RPC's rule by owner decision: GetBucket and DeleteBucket compare the values as they arrive (a zero or negative match never holds, a zero or negative not-match always holds), UpdateBucket refuses 0, negative values and both conditions together, and LockBucketRetentionPolicy refuses 0 and negative values because the proto requires a positive one; the refusals come before the lookup (`bucket_rpcs_keep_their_own_metageneration_condition_rules`).
- DeleteBucket answers authorization first, then a missing bucket, a failed condition and remaining objects (`delete_bucket_reports_authorization_existence_conditions_then_contents`), and the retained-state rules above are pinned by `delete_bucket_follows_the_shared_catalog_for_retained_state`.
- Newly pinned refusals: the `satisfies_pzs`, unknown and nested read masks with their order on GetBucket and ListBuckets (`bucket_read_masks_refuse_unselectable_paths_in_each_rpcs_order`), conditional bindings and audit configs on SetIamPolicy (`grpc_iam_set_refuses_conditional_bindings_and_audit_configs`), an empty `website` on CreateBucket, and strict LockBucketRetentionPolicy, which needs `storage.buckets.update` before the lookup (`grpc_retention_lock_requires_bucket_update_permission`).

Still pending on these rows: nested bucket read masks; CreateBucket lifecycle, ACLs and predefined ACLs; an UpdateBucket `*` mask and predefined ACLs; SetIamPolicy masks that name only some policy fields; TestIamPermissions on an object; whether output-only update paths are ignored on UpdateBucket and UpdateObject alike; and the separate `storage.buckets.setIamPolicy` check on UpdateBucket, which no registered caller can reach today because every role granting `storage.buckets.update` also grants `storage.buckets.setIamPolicy`.
