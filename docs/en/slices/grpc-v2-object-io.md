# Storage v2 object I/O

<!-- markdownlint-configure-file {"MD013": false} -->

Scope: RPC-STORAGE-011, RPC-STORAGE-014, RPC-STORAGE-015, RPC-STORAGE-018, RPC-STORAGE-019, RPC-STORAGE-020, RPC-STORAGE-022, RPC-STORAGE-023 and BEHAVIOR-RPC-003, plus the later CancelResumableWrite addition (RPC-STORAGE-013). RestoreObject and Rapid append are excluded.

## Acceptance contract

- A completed upload is replayed only when the stream starts with that upload_id. If another stream finalizes it after this stream has persisted a message, later messages fail with FAILED_PRECONDITION instead of claiming their bytes were published. Other concurrent-stream behavior remains unverified.

- Ordinary Go `storage.NewGRPCClient(ctx)` Writer, with default chunk size, writes small and multi-MiB bodies; JSON reads the result. JSON uploads are readable through gRPC NewReader and NewRangeReader.
- BidiWriteObject and WriteObject share bounded staging, CRC32C chunk validation, final CRC32C/MD5 validation and transactional publication. Incorrect offsets and checksums never publish an object.
- StartResumableWrite returns a capability; QueryWriteStatus returns a durable offset or the completed resource. Reopening a stream resumes at that offset, including after catalog recovery.
- Every Storage v2 call except QueryWriteStatus and CancelResumableWrite must carry `x-goog-request-params`; without it the call answers INVALID_ARGUMENT, as Cloud Storage did for GetObject, GetBucket, ListBuckets and WriteObject (recorded 2026-11-18; the other RPCs follow by inference). A routed bucket other than the request's, or metadata that routes no bucket, answers INVALID_ARGUMENT naming both bucket IDs. An unknown key, a `routing_token` and a key the RPC does not route are ignored, and a call reads only the keys it routes. The upload ID calls (QueryWriteStatus, CancelResumableWrite and a resumed write) are answered from the ID alone: and the bucket the ID starts with is not compared with a routed one (recorded 2026-11-18: Cloud Storage answered both from the ID).
- Retrying a finalized upload returns OK with its original completion snapshot, even after the live object changes. A clean half-close of an unfinished upload_id stream reports its persisted size even without flush or state_lookup. Non-resumable streams still require finish_write on their last message, as specified by the proto.
- WriteObject and BidiWriteObject answer at `finish_write` and ignore any message that follows it. A `write_object_spec` or `upload_id` repeated on a later message is ignored, and `object_checksums` is accepted on any message (recorded 2026-11-18). An upload persists whole 256 KiB granules until `finish_write`: bytes past the last granule wait for the call's next message, a resumable stream that closes with such bytes fails and drops them, and a flush or state_lookup reports the persisted granules with `persisted_data_checksums`, on a non-resumable BidiWriteObject stream too (there with the CRC32C alone). Every stream message is decoded once into the shared `WriteStep` (`src/grpc/v2/object_io/step.rs`) that the non-resumable, resumable and appendable paths use.
- Object names use the shared flat-namespace validation: dot-only names and the ACME challenge prefix are rejected, while a tab is accepted. Storage I/O failures use the shared storage error classification.
- Generation and metageneration conditions, including create-if-absent, are checked in the publication transaction. Supported fixed/custom metadata is preserved; unsupported semantics return actionable UNIMPLEMENTED. A metageneration match of 0 and a match beside a not-match are evaluated, not refused, on every object RPC except MoveObject, which refuses a match beside a not-match with INVALID_ARGUMENT (recorded for pairs naming the same value; refusing every pair is an inference); a negative value is still refused with INVALID_ARGUMENT.
- ReadObject supports positive/negative offsets, bounded lengths, out-of-range errors, selected generations, per-message CRC32C and complete-object checksums. Response messages stay below 4 MiB.
- GetObject supports generations, conditions, read masks and `soft_deleted` (a soft-deleted generation, which needs a bucket soft delete policy). A `restore_token` answers INTERNAL "We encountered an internal error. Please try again.", as Cloud Storage did for a live object in a bucket without a hierarchical namespace (recorded 2026-11-18). DeleteObject uses shared hold, retention, versioning and soft-delete behavior.
- ListObjects supports prefix, delimiter prefixes, page size and query-bound continuation tokens; Go Objects iterates them. A page ends near 2 MiB with a next page token, whatever page size was asked for, and always holds one entry so paging advances.
- ListObjects builds the shared query directly and keeps the existing NoAcl page-token format. It does not construct JSON URLs or render JSON object pages. Combination errors name soft_deleted, match_glob and include_folders_as_prefixes; malformed globs keep their detailed syntax explanation.
- CancelResumableWrite cancels an active session from StartResumableWrite, including one with persisted bytes. Later QueryWriteStatus, WriteObject and BidiWriteObject on that upload_id fail, staged bytes are released and no object is published.
- Strict authentication uses shared bucket permissions and rechecks them inside catalog operations. No credentials are discovered and no Google Cloud calls are made.

## Sources and boundaries

Single-shot writes use the typed intake shared with legacy v1 for offsets,
CRC32C, complete hashes, size limits and bounded staging. Protocol-specific
validation and messages stay in each adapter. Both adapters await producer and
catalog completion, preserving root storage failures and the producer's error
when storage reports only BodyAborted; closed consumers interrupt input waits.

The contract uses the foundation's pinned [Storage v2 proto](https://github.com/googleapis/googleapis/blob/933dd1be8180a22bca2dc473b53d4f4297ee3b0c/google/storage/v2/storage.proto), SHA-256 `a0df6132967b97a89be248f1f24d277ee8df8f8d885db1d4af6249469ff0c1cf`, and the existing Go Storage v1.70.0 SDK. Existing source gaps remain open; JSON error choices are not assumed to define gRPC status codes. No dependency, setting, catalog schema or startup order is changed.

The [official RPC reference](https://docs.cloud.google.com/storage/docs/reference/rpc/google.storage.v2) and [Rust 1.99.1 stable announcement](https://blog.rust-lang.org/2026/10/15/Rust-1.99.1/) were checked on 2026-10-28. The foundation's verified dependency graph is retained; no dependency is added or updated.

## Supported subset and resource bounds

Object I/O maps the storage domain errors (`ObjectError` and `CatalogError`) to a Status directly, with one exhaustive match per enum in `src/grpc/v2/status.rs`, and does not go through the JSON adapter. A not-match condition that alone fails answers FAILED_PRECONDITION "The resource you requested has not been modified according to the condition you specified." (`ObjectError::SourceNotModified` for a copy or rewrite source, `CatalogError::NotModified` for a bucket deletion), as Cloud Storage did for reads and writes alike (recorded 2026-11-18). Unsupported settings keep UNIMPLEMENTED with ErrorInfo details.

The existing `max_object_bytes` is passed into the gRPC adapter, with its existing default. No new setting is needed. Incoming protobuf messages retain the foundation's 4 MiB limit. Outgoing object-body messages use the shared reader's 64 KiB chunks; upload bridges use two 64 KiB slots. Lists use bounded catalog pages of at most 1000 entries and shared query-bound continuation tokens, without scanning the whole catalog. No database transaction spans network input.

Single-request streams use shared `prepare_object_upload`/`put_object_prechecked`, not retained resumable sessions. The adapter uses the existing incremental hasher to validate final-message digests before sending shared publication's EOF marker. Only shared publication assigns generations and applies conditions/holds/retention. Both streaming RPCs use this same handler. StartResumableWrite uses shared persisted sessions and exclusive per-message writer leases; each message reaches the shared fsync/checkpoint before its offset is acknowledged. Reopening the catalog preserves those offsets. The opaque upload ID includes the bucket name and random shared capability. QueryWriteStatus rechecks current create permission and returns the original completion snapshot even after the live object changes.

CancelResumableWrite reuses the catalog cancellation behind JSON session-URI DELETE. The pinned proto says that after cancellation "Any attempts to write to the resumable upload after cancelling the upload fail", and that in-progress writes may complete first or fail. The local mapping is:

| Case | Result |
| --- | --- |
| Active session, with or without persisted bytes | OK with an empty response. One short catalog transaction marks the session CANCELLED and journals its staging blob; the file is removed after commit, and maintenance retries a failed removal. |
| QueryWriteStatus, WriteObject or BidiWriteObject after cancellation | QueryWriteStatus answers FAILED_PRECONDITION "Upload has already been cancelled." with ErrorInfo reason `GRPC_UPLOAD_ALREADY_CANCELLED`, and a write INVALID_ARGUMENT with the same message (recorded 2026-11-18). A resumed write without `finish_write` is answered alike because the session is looked up before the message is read; that is not recorded. |
| Repeated cancellation | OK with an empty response (recorded 2026-11-18). |
| Upload_id that is no ID, one that cannot be read, or one that names no session | Text that is no upload ID (an empty string, or no bucket part) answers INVALID_ARGUMENT `Invalid upload ID '...'.`, and an ID that cannot be read (a bucket part followed by anything but 64 hexadecimal digits) answers INTERNAL "We encountered an internal error. Please try again."; both were recorded on 2026-11-18. An ID of the issued shape whose session does not exist, belongs to another bucket or has expired answers NOT_FOUND "Upload session not found; start a new resumable write". That is a deliberate local choice and not recorded: INTERNAL would make SDKs retry a call that can never succeed. A session expires seven days after StartResumableWrite on the catalog clock; from that instant QueryWriteStatus, resumed writes and cancellation all answer NOT_FOUND. |
| Finalized upload | FAILED_PRECONDITION "Upload has already been completed." with reason `GRPC_UPLOAD_ALREADY_COMPLETED` (recorded 2026-11-18). QueryWriteStatus keeps reporting the resource, with the caller's ACL and owner view, and the object stays; use DeleteObject to remove it. Resumed WriteObject returns OK with the original completed resource as the proto requires. |
| Session ended by a finishing message of the wrong size | A finishing message whose size misses `object_size` answers OUT_OF_RANGE with reason `GRPC_MISMATCHED_UPLOAD_SIZE` and ends the session; QueryWriteStatus then answers FAILED_PRECONDITION "Upload has already been terminated." (recorded 2026-11-18). Not recorded; inferred from that answer: a finishing message above `object_size` ends the session too, and CancelResumableWrite and a write on such a session answer like the cancelled ones with the terminated wording (`grpc_io_terminated_sessions_refuse_cancels_and_writes`). |
| A writer currently holds the session lease | The cancellation waits for the lease through the shared writer wait, up to `catalog_wait_timeout_ms` on a server (an embedded catalog does not wait). If the writer still holds it when the wait ends, UNAVAILABLE with the session unchanged. This is the proto's unspecified in-progress-write case; retry after the write finishes. |
| Strict mode | gRPC upload IDs are not bearer capabilities, so the caller needs `storage.objects.create` on the bucket, the same check as QueryWriteStatus and resumed writes. The creator is not special: a different caller with that permission, such as a `roles/storage.objectUser` principal, cancels a session someone else started. A viewer receives PERMISSION_DENIED and an anonymous caller UNAUTHENTICATED, as for the other v2 RPCs; the session remains usable. |

Write metadata supports content type/encoding/disposition/language/cache control, custom metadata, temporary/event holds and custom time. Empty/default protobuf values are accepted. Nondefault unhandled object fields, predefined ACLs and appendable objects return actionable UNIMPLEMENTED. Customer-supplied keys follow [grpc-v2-customer-supplied-keys.md](grpc-v2-customer-supplied-keys.md). Write metadata has no 8 KiB limit: Cloud Storage stored WriteObject custom metadata values of 8192 and 40,000 bytes and an UpdateObject value of 20,000 bytes (case grpc-custom-metadata-limit, recorded 2026-11-15). Fixed and custom metadata past the local 40 KiB once encoded as JSON, shared with JSON and XML, return INVALID_ARGUMENT without publication. Explicit object_size is checked before staging and at finish.

ReadObject clamps negative offsets beyond the start to zero, permits offset equal to size (empty read), rejects greater offsets with OUT_OF_RANGE and rejects negative limits with INVALID_ARGUMENT. Returned content ranges use an exclusive end. GetObject/list masks accept every top-level `Object` field and `*`, matching the 2026-10-31 Google observation in [the gRPC object field evidence](../evidence/grpc-object-fields.md) (the official Java SDK sends all 33 fields); ReadObject additionally selects its metadata (`metadata`, `metadata.FIELD`) and top-level response fields. Responses carry the JSON resource's `etag` and `update_storage_class_time` (`timeStorageClassUpdated`). `acl` and `owner` appear only when a mask names them or uses `*` (or ReadObject's whole `metadata`), as the proto's default masks exclude them; they come from the same shared projection as JSON `projection=full`, so uniform bucket-level access, a caller without `storage.objects.getIamPolicy` on the object, or an unfinalized appendable object leaves both empty while the read succeeds. Fields no local object can hold (`kms_key`, `contexts`, the restore token of a live object) stay empty rather than invented.

A member of a singular message is selected on its own on GetObject, ReadObject (under `metadata.`) and ListObjects: `checksums.crc32c`, `checksums.md5_hash`, `owner.entity`, `owner.entity_id`, `customer_encryption.encryption_algorithm`, `customer_encryption.key_sha256_bytes`, `retention.mode` and `retention.retain_until_time` (`src/grpc/v2/object_io/object_mask.rs`). Cloud Storage was recorded serving `owner.entity` on all three and returning it without an owner, so `acl` and `owner` are filled only for a path that names the whole field (recorded 2026-11-18). A path that names no field of the resource answers INVALID_ARGUMENT: an unknown name, `owner.no_such_field` and `acl.role` were recorded on GetObject; a member of a scalar, a repeated field or a map (such as `metadata.k`) is the same answer by inference from the bucket's `labels.<key>`, which is not recorded for objects. The parts of a timestamp (`create_time.seconds`) and the context map (`contexts.custom`) are real members that gcs-mimic does not select; Cloud Storage's answer to them is not recorded, so they answer UNIMPLEMENTED with ErrorInfo and a client requests the whole field.

Which fields a read mask may name does not depend on the object, so GetObject, ReadObject and ListObjects check the mask with the request, before authorization and any lookup, as GetBucket checks its mask; ListBuckets checks its mask after it authorizes the project. A path naming no object field answers INVALID_ARGUMENT, `There is no field for this resource named '...'.` on GetObject and `Invalid read_mask field: '...'.` on ListObjects (both recorded 2026-11-18, GetObject for an existing object, a missing object and a missing bucket, ListObjects for an empty page and a page with an object), and a sub-path gcs-mimic does not select answers UNIMPLEMENTED with ErrorInfo, for a missing object, an empty page or an unauthorized caller too, an anonymous one included, while a valid mask still reports a missing object as NOT_FOUND. A ReadObject path that names no ReadObjectResponse field, such as `read_handle`, or a sub-path of `content_range` or `object_checksums` is refused like an unmodeled setting: UNIMPLEMENTED with ErrorInfo, and UNAUTHENTICATED for an anonymous caller. Not recorded: Cloud Storage's answer to such a ReadObject path, and to an unknown path under ReadObject's `metadata.` prefix, which is worded like GetObject's. A ReadObject mask that selects fields must include `checksummed_data.content` (INVALID_ARGUMENT "The 'read_mask' field must include checksummed_data.content, but was '...'.", recorded), and a mask that selects the content alone gets the bytes without their CRC32C (recorded 2026-11-18). GetObject reports a malformed customer key and a malformed name before the mask, and ReadObject a malformed key and name, then the mask, and the `restore_token` refusal and the `soft_deleted` lookup come after it and after the bucket's authorization. The recorded precedence cases show a malformed key and a mask without the content before a missing object (`grpc-probe-object-precedence`); the order of the remaining checks is a local choice (SPEC-GRPC-LOCAL-CHOICES).

ReadObject reports its failures in this order: a malformed customer key, a malformed name and the read mask, all INVALID_ARGUMENT apart from the refused paths above; the bucket's authorization, which refuses a caller only when the bucket does not exist and the caller holds `storage.objects.get` in no project (UNAUTHENTICATED for an anonymous caller, PERMISSION_DENIED for a principal); a negative generation and a negative condition, both INVALID_ARGUMENT; the object's authorization with the lookup, so in an existing bucket an anonymous caller is denied with PERMISSION_DENIED for a missing object too; NOT_FOUND for a missing object; FAILED_PRECONDITION for a failed condition; OUT_OF_RANGE for an offset past the end; and last INVALID_ARGUMENT for a negative `read_limit`. Recorded 2026-11-18: the key and the mask before a missing object, and a failed condition before an offset past the end; the rest of the order is a local choice. ReadObject returns the stored bytes of an object whose `content_encoding` is gzip without decompressing them, for a whole read and a range (recorded 2026-11-18, `grpc-probe-object-masks`, step `read-gzip`: Storage v2 does not transcode), and the JSON and XML reads follow BEHAVIOR-OBJECT-017.

GetObject, ReadObject and DeleteObject compare the generation and metageneration conditions that arrive, as Cloud Storage does (recorded 2026-11-18, `grpc-probe-object-conditions`): a metageneration match of 0 never holds and fails with FAILED_PRECONDITION, and a match beside a not-match is evaluated, not refused. A negative condition value is still refused with INVALID_ARGUMENT before any lookup; no negative value was recorded on the object RPCs, so that refusal is a local choice.

The broader rows remain PARTIAL; [ledger cases](#ledger-cases) lists what remains. Explicitly resumable writes use the shared resumable engine: sessions are unlimited in number unless `max_resumable_sessions` sets a limit, and they expire seven days after StartResumableWrite. WriteObject and BidiWriteObject answer at `finish_write` and ignore a later message; WriteObject reads nothing past the finishing message (`grpc_io_write_object_answers_at_finish_write_without_reading_further`), so a client that keeps its stream open holds no session. A listing page ends near 2 MiB of encoded objects, so metadata-heavy listings stay under the 4 MiB receive limit (`grpc_object_lists_page_on_their_size_and_reach_every_object`). Every recorded Storage v2 owner carries only `entity`, which is what the emulator returns.

## Ledger cases

The ledger rows list one acceptance case per checkable behavior (decomposed on 2026-11-18). An answer that Google does not document and the recording of 2026-11-18 did not cover is a local choice, recorded as a scoped difference with a pinning test. In summary:

- Refused on purpose (scoped differences under SPEC-GRPC-UNMODELED-SETTINGS): a write resource with `kms_key` or object contexts, on WriteObject, BidiWriteObject and StartResumableWrite, and the ListObjects contexts `filter`. A GetObject `restore_token` is not refused as unsupported: it answers the recorded INTERNAL, since only hierarchical namespace buckets use it.
- Aligned with the 2026-11-18 recording of Cloud Storage: the routing metadata and its refusals; the answers of the write streams and resumable sessions listed above; object conditions and read masks (GetObject, ReadObject and ListObjects); GetObject `soft_deleted` and `restore_token`; the gzip read. The probe cases are `grpc-probe-routing`, `grpc-probe-write-streams`, `grpc-probe-bidi-write`, `grpc-probe-resumable-sessions`, `grpc-probe-object-conditions`, `grpc-probe-object-masks` and `grpc-probe-object-precedence`.
- Local choices that remain (SPEC-GRPC-LOCAL-CHOICES; the gap item lists each with the test that pins it): CancelResumableWrite's UNAVAILABLE while a write holds the session lease, and cancellation by any caller with `storage.objects.create`, not only the session creator; NOT_FOUND for an upload ID of the issued shape whose session is missing or expired, and the seven-day session expiry; the answers on a session the emulator terminated (a finishing message above `object_size`, a write or cancel on it) and the checks of a resumable message that Cloud Storage was not recorded on (a first offset below a persisted size above 0, bytes past `object_size` without `finish_write`, the order of the session's key and conditions against the message's offset, size and data checksum); the order of GetObject's and ReadObject's checks after the mask and of ReadObject's failures; the UNIMPLEMENTED answers to ReadObject response paths and to the parts of a timestamp and `contexts.custom` in a read mask; the refusal of a negative condition value; routing keys read only when the RPC routes them, so that a malformed value under another key is ignored.
- Every Storage v2 row depends on BEHAVIOR-RPC-001, because every RPC passes its routing and request-metadata handling. RPC-STORAGE-013 has no pending case of its own; server-side `grpc-timeout` and gzip message compression are scoped differences under SPEC-GRPC-CALL-METADATA.
- Pending code work: `predefined_acl`, `acl`, `retention` and output-only fields on a write resource (and whether `resource.checksums`, which the proto marks output-only, keeps being verified).
- Pending tests: the order of DeleteObject and WriteObject failures not covered by the recorded precedence cases; non-decreasing QueryWriteStatus answers; write, sync and crash faults at a session checkpoint.
- Decisions: whether the first message of a resumed stream may start before a persisted offset above 0, on which the two proto comments disagree (`write_offset` at lines 1411-1415 and the WriteObject RPC at lines 480-489; the recording always had nothing persisted, so the emulator refuses it, as the `write_offset` field requires); waiting for a busy session lease (as now, up to the catalog wait, then UNAVAILABLE) or answering ABORTED.

## Verification

On 2026-11-18 ten probe cases (`compatibility/differential/cases/grpc-probe-*.json`) were recorded against Cloud Storage and the object I/O answers above were aligned with them; the offline replay matches every recorded case. The write-side tests that pin the aligned answers are `grpc_single_shot_write_message_errors`, `grpc_single_shot_write_error_precedence`, `grpc_resumable_write_message_errors`, `grpc_resumable_write_error_precedence`, `grpc_io_resumable_close_drops_bytes_past_the_last_granule`, `grpc_io_ended_sessions_answer_as_recorded`, `grpc_io_terminated_sessions_refuse_cancels_and_writes` (not recorded; inferred), `grpc_io_write_object_answers_at_finish_write_without_reading_further`, `grpc_io_resumed_write_is_answered_from_its_upload_id_whatever_bucket_is_routed` and `grpc_resumable_persisted_sizes_carry_the_persisted_checksums`.

Also on 2026-11-18, GetObject, ReadObject and ListObjects started to check their read masks before authorization and the lookup, as described above. The tests in `src/grpc/v2/object_io/read/mask_tests.rs` were written first and failed while the masks were checked on the result: an invalid mask on a missing object answered NOT_FOUND and one on an empty listing succeeded. After the change `an_invalid_read_mask_is_reported_for_a_missing_object` and `an_invalid_read_mask_is_reported_for_an_empty_listing` report unknown and nested paths there; `an_invalid_read_mask_precedes_authorization_and_the_other_checks` reports the mask before an anonymous caller is denied (GetObject and ReadObject answer PERMISSION_DENIED and ListObjects UNAUTHENTICATED without it) and before a negative generation and condition or a read offset past the end, which answer INVALID_ARGUMENT and OUT_OF_RANGE without it; `request_checks_before_the_mask_keep_their_order` keeps a malformed key and a malformed name before the mask, while a soft-deleted lookup and a restore token are read after it. `cargo test --locked --offline --lib grpc::` passed 270 tests.

The same day, `src/grpc/v2/object_io/read/request_refusals.rs` pinned the read-side refusals that no test named. They pin existing answers and passed unchanged: `get_object_refuses_restore_tokens_and_negative_values` answers a `restore_token` with the recorded INTERNAL, refuses `soft_deleted` true without a generation, treats `soft_deleted` false as the default lookup, and refuses a negative generation and a negative condition with INVALID_ARGUMENT (the soft-deleted lookup itself is pinned by `get_object_reads_a_soft_deleted_generation` and `get_object_soft_deleted_needs_a_soft_delete_policy`); `read_object_refuses_negative_limits_and_offsets_past_the_end` refuses a negative `read_limit`, an offset past the end with Cloud Storage's OUT_OF_RANGE wording, and a negative generation and condition; `list_objects_refuses_a_filter_and_a_negative_page_size` refuses a contexts `filter` with ErrorInfo and a negative `page_size` with INVALID_ARGUMENT.
