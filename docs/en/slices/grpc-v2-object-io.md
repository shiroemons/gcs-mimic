# Storage v2 object I/O

<!-- markdownlint-configure-file {"MD013": false} -->

Scope: RPC-STORAGE-011, RPC-STORAGE-014, RPC-STORAGE-015, RPC-STORAGE-018, RPC-STORAGE-019, RPC-STORAGE-020, RPC-STORAGE-022, RPC-STORAGE-023 and BEHAVIOR-RPC-003, plus the later CancelResumableWrite addition (RPC-STORAGE-013). RestoreObject and Rapid append are excluded.

## Acceptance contract

- A completed upload is replayed only when the stream starts with that upload_id. If another stream finalizes it after this stream has persisted a message, later messages fail with FAILED_PRECONDITION instead of claiming their bytes were published. Other concurrent-stream behavior is described under [Write streams](#write-streams).

- Ordinary Go `storage.NewGRPCClient(ctx)` Writer, with default chunk size, writes small and multi-MiB bodies; JSON reads the result. JSON uploads are readable through gRPC NewReader and NewRangeReader.
- BidiWriteObject and WriteObject share bounded staging, CRC32C chunk validation, final CRC32C/MD5 validation and transactional publication. Incorrect offsets and checksums never publish an object.
- StartResumableWrite returns a capability; QueryWriteStatus returns a durable offset or the completed resource. Reopening a stream resumes at that offset, including after catalog recovery.
- Retrying a finalized upload returns OK with its original completion snapshot, even after the live object changes. A clean half-close of an unfinished upload_id stream reports its persisted size even without flush or state_lookup. Non-resumable streams still require finish_write on their last message, as specified by the proto.
- Object names use the shared flat-namespace validation: dot-only names and the ACME challenge prefix are rejected, while a tab is accepted. Storage I/O failures use the shared storage error classification.
- Generation and metageneration conditions, including create-if-absent, are checked in the publication transaction. Supported fixed/custom metadata is preserved; unsupported semantics return actionable UNIMPLEMENTED.
- ReadObject supports positive/negative offsets, bounded lengths, out-of-range errors, selected generations, per-message CRC32C and complete-object checksums. Response messages stay below 4 MiB.
- GetObject supports generations, conditions and read masks. DeleteObject uses shared hold, retention, versioning and soft-delete behavior.
- ListObjects supports prefix, delimiter prefixes, page size and query-bound continuation tokens; Go Objects iterates them. A page ends near 2 MiB with a next page token, whatever page size was asked for, and always holds one entry so paging advances.
- ListObjects builds the shared query directly and keeps the existing NoAcl page-token format. It does not construct JSON URLs or render JSON object pages. Combination errors name soft_deleted, match_glob and include_folders_as_prefixes; malformed globs keep their detailed syntax explanation.
- CancelResumableWrite cancels an active session from StartResumableWrite, including one with persisted bytes. Later QueryWriteStatus, WriteObject and BidiWriteObject on that upload_id fail, staged bytes are released and no object is published.
- Strict authentication uses shared bucket permissions and rechecks them inside catalog operations. No credentials are discovered and no Google Cloud calls are made.

## Sources and boundaries

Single-shot writes use the typed intake shared with legacy v1 for offsets,
CRC32C, complete hashes, size limits and bounded staging. Protocol-specific
validation and messages stay in each adapter. Both adapters await producer and
catalog completion, preserving root storage failures and the producer's error
when storage reports only BodyAborted; closed consumers interrupt input waits.

The contract uses the foundation's pinned [Storage v2 proto](https://github.com/googleapis/googleapis/blob/933dd1be8180a22bca2dc473b53d4f4297ee3b0c/google/storage/v2/storage.proto), SHA-256 `a0df6132967b97a89be248f1f24d277ee8df8f8d885db1d4af6249469ff0c1cf`, and the existing Go Storage v1.70.0 SDK. Existing source gaps remain open; JSON error choices are not assumed to define gRPC status codes. No dependency, setting, catalog schema or startup order is changed.

The [official RPC reference](https://docs.cloud.google.com/storage/docs/reference/rpc/google.storage.v2) and [Rust 1.99.1 stable announcement](https://blog.rust-lang.org/2026/10/15/Rust-1.99.1/) were checked on 2026-10-28. The foundation's verified dependency graph is retained; no dependency is added or updated.

## Supported subset and resource bounds

Object I/O uses the common status::from_json conversion shared with bucket RPCs. Read conditions mapped from JSON 304 retain FAILED_PRECONDITION, and unsupported JSON 501 retains UNIMPLEMENTED with ErrorInfo details.

The existing `max_object_bytes` is passed into the gRPC adapter, with its existing default. No new setting is needed. Incoming protobuf messages retain the foundation's 4 MiB limit. Outgoing object-body messages use the shared reader's 64 KiB chunks; upload bridges use two 64 KiB slots. Lists use bounded catalog pages of at most 1000 entries and shared query-bound continuation tokens, without scanning the whole catalog. No database transaction spans network input.

Single-request streams use shared `prepare_object_upload`/`put_object_prechecked`, not retained resumable sessions. The adapter uses the existing incremental hasher to validate final-message digests before sending shared publication's EOF marker. Only shared publication assigns generations and applies conditions/holds/retention. Both streaming RPCs use this same handler. StartResumableWrite uses shared persisted sessions and exclusive per-message writer leases; each message reaches the shared fsync/checkpoint before its offset is acknowledged. Reopening the catalog preserves those offsets. The opaque upload ID includes the bucket name and random shared capability. QueryWriteStatus rechecks current create permission and returns the original completion snapshot even after the live object changes.

CancelResumableWrite reuses the catalog cancellation behind JSON session-URI DELETE. The pinned proto says that after cancellation "Any attempts to write to the resumable upload after cancelling the upload fail", and that in-progress writes may complete first or fail. The local mapping is:

| Case | Result |
| --- | --- |
| Active session, with or without persisted bytes | OK with an empty response. One short catalog transaction marks the session CANCELLED and journals its staging blob; the file is removed after commit, and maintenance retries a failed removal. |
| QueryWriteStatus, WriteObject or BidiWriteObject after cancellation | NOT_FOUND, the existing status for an invalidated session, so a client restarts with StartResumableWrite. |
| Repeated cancellation | NOT_FOUND. Cancellation is not reported as a second success, because the session no longer exists for the caller. |
| Malformed or unknown upload_id, an upload_id under another bucket, or an expired session | NOT_FOUND, consistent with `parse_upload_id` and QueryWriteStatus. |
| Finalized upload | FAILED_PRECONDITION. The proto cancels an in-progress upload; a finalized one is not in progress. This local cancellation choice is separate from resumed WriteObject, which returns OK with the original completed resource as the proto requires. The object and QueryWriteStatus completion stay unchanged; use DeleteObject to remove the object. |
| A writer currently holds the session lease | UNAVAILABLE with the session unchanged. This is the proto's unspecified in-progress-write case; retry after the write finishes. |
| Strict mode | gRPC upload IDs are not bearer capabilities, so the caller needs `storage.objects.create` on the bucket, the same check as QueryWriteStatus and resumed writes. A viewer receives PERMISSION_DENIED and an anonymous caller UNAUTHENTICATED, as for the other v2 RPCs; the session remains usable. |

Write metadata supports content type/encoding/disposition/language/cache control, custom metadata, temporary/event holds and custom time. Empty/default protobuf values are accepted. Nondefault unhandled object fields, predefined ACLs and appendable objects return actionable UNIMPLEMENTED. Customer-supplied keys follow [grpc-v2-customer-supplied-keys.md](grpc-v2-customer-supplied-keys.md). Write metadata has no 8 KiB limit: Cloud Storage stored WriteObject custom metadata values of 8192 and 40,000 bytes and an UpdateObject value of 20,000 bytes (case grpc-custom-metadata-limit, recorded 2026-11-15). Fixed and custom metadata past the local 40 KiB once encoded as JSON, shared with JSON and XML, return INVALID_ARGUMENT without publication. Explicit object_size is checked before staging and at finish.

ReadObject clamps negative offsets beyond the start to zero, permits offset equal to size (empty read), rejects greater offsets with OUT_OF_RANGE and rejects negative limits with INVALID_ARGUMENT. Returned content ranges use an exclusive end. GetObject/list masks accept every top-level `Object` field and `*`, matching the 2026-10-31 Google observation in [the gRPC object field evidence](../evidence/grpc-object-fields.md) (the official Java SDK sends all 33 fields); ReadObject additionally selects its metadata (`metadata`, `metadata.FIELD`) and top-level response fields. Responses carry the JSON resource's `etag` and `update_storage_class_time` (`timeStorageClassUpdated`). `acl` and `owner` appear only when a mask names them or uses `*` (or ReadObject's whole `metadata`), as the proto's default masks exclude them; they come from the same shared projection as JSON `projection=full`, so uniform bucket-level access, a caller without `storage.objects.getIamPolicy` on the object, or an unfinalized appendable object leaves both empty while the read succeeds. Fields no local object can hold (`kms_key`, `contexts`, the restore token of a live object) stay empty rather than invented. Nested object-field masks remain UNIMPLEMENTED.

The broader rows remain PARTIAL. Pending scope includes nested field masks, explicit soft-deleted GetObject requests (soft-deleted listings: [SDK parity](grpc-v2-sdk-parity.md)), other unhandled request fields, owner `entity_id`, QueryWriteStatus on an expired session and exhaustive recovery/fault-injection combinations. The shared resumable engine's 128 retained-session/seven-day bound applies only to explicitly resumable writes. Large metadata-heavy listings can reach the existing 4 MiB encoded-response limit and are not claimed as complete pagination conformance.

## Write streams

WriteObject and BidiWriteObject check each message of a single-shot, resumed or appendable stream and answer a refused one with the status below; tests in `src/grpc/v2/object_io/write/message_tests.rs` send each case through the RPC service and pin its status, message, the replies sent before it and what the write leaves behind. The pinned proto names a status only for an object_size mismatch (OUT_OF_RANGE); the other statuses, the wording and the precedence are the emulator's (gap SPEC-GRPC-WRITE-ERRORS). A refused single-shot write publishes nothing, a refused resumed message stages nothing and leaves the session at its persisted offset, and a refused appendable opening message creates or takes over nothing.

| Message | Status |
| --- | --- |
| No first message, or a first message after the first | INVALID_ARGUMENT |
| Negative `write_offset`, an offset past the received bytes, or a resumed stream's first offset other than the persisted size | OUT_OF_RANGE |
| Chunk CRC32C, complete-object checksum, malformed MD5 or conflicting `object_checksums` | INVALID_ARGUMENT |
| `object_checksums` on a later single-shot message without `finish_write`, or on an appendable message without it | INVALID_ARGUMENT |
| `object_checksums` on an upload_id message without `finish_write`, or `flush`/`state_lookup` on a non-resumable message without it | UNIMPLEMENTED |
| `object_size` mismatch | OUT_OF_RANGE |
| More than `max_object_bytes` | RESOURCE_EXHAUSTED |
| A key after a keyless start | INVALID_ARGUMENT (customer-supplied key wording) |
| No `finish_write` on a single-shot stream's last message | INVALID_ARGUMENT |
| A message after `finish_write` on WriteObject | INVALID_ARGUMENT |

When one message breaks several rules, a single-shot write checks a later key, the first message, `flush`/`state_lookup`, checksum placement, the MD5 length, conflicting checksums and the offset before the chunk CRC32C. A resumed write checks the first message and checksum placement before it looks up the session, then the key, the publication conditions, the checksums and the offset before the chunk CRC32C. An appendable write checks the key, the first message and the chunk CRC32C before checksum placement, MD5 and the offset, and checks its opening message before it creates or takes over the object. A complete-object mismatch uses the adapter's wording on single-shot writes and the shared catalog's on resumable and appendable writes.

- Owner decision, kept: BidiWriteObject answers `finish_write` with the resource and ends the call with OK without reading further, so a message sent after it is never seen. The proto says such a message "causes an error"; WriteObject reads to the end of its stream and answers it with INVALID_ARGUMENT, after the finishing message's own checks (gap SPEC-GRPC-WRITE-STREAMS).
- WriteObject reads past `finish_write` before it leases a resumed upload's session, so a client that keeps its stream open holds no session and another stream or CancelResumableWrite can use it.
- Owner decision, kept: a resumed stream's first `write_offset` must equal the persisted size, as the proto requires ("must be equal to the `persisted_size` that a call to `QueryWriteStatus()` would return"). Any other value, including one that only resends persisted bytes, is OUT_OF_RANGE, a status the proto does not name. A later message may resend persisted bytes; they are skipped.
- Of several streams on one upload_id the proto says only that ABORTED from WriteObject indicates concurrent attempts to update the resumable write, after which the client resumes; it does not say how the service orders such streams. The server orders them on the session lease: a message for a session another stream is writing waits for the lease up to `catalog_wait_timeout_ms` and then continues at the persisted offset. Past that wait it fails with UNAVAILABLE, which the proto lists among the errors a client resumes after, and changes nothing. Streams that take turns each continue at the persisted offset; bytes a later message resends over another stream's persisted bytes are skipped without comparison, so the bytes persisted first stay. A stream whose upload another stream finalized gets FAILED_PRECONDITION. QueryWriteStatus takes no lease: it answers at once with the persisted size and checksums of the last checkpoint.
- WriteObjectResponse, BidiWriteObjectResponse and QueryWriteStatusResponse carry `persisted_data_checksums` with the CRC32C and MD5 of the persisted bytes whenever they report a persisted size, zero included, as the proto says ("If persisted_size is set, contains checksums of persisted data"). A resource answer carries none. A session staged by a release before 0.26.0 keeps no running digests and reports none until it finishes or expires. Appendable acknowledgements keep their CRC32C-only checksums.
- WriteObject, BidiWriteObject and StartResumableWrite refuse a predefined ACL and the resource fields the emulator does not model with UNIMPLEMENTED and ErrorInfo before anything is created; StartResumableWrite also refuses an appendable spec (gap SPEC-GRPC-WRITE-REFUSALS).

## Verification

On 2026-11-18, `cargo test --locked --offline --lib grpc::v2` passed with the write-stream tests: `grpc_single_shot_write_message_errors`, `grpc_single_shot_write_error_precedence`, `grpc_resumable_write_message_errors`, `grpc_resumable_write_error_precedence`, `grpc_appendable_write_message_errors`, `grpc_appendable_write_error_precedence`, `grpc_resumable_write_waits_for_a_leased_session`, `grpc_resumable_write_to_a_session_leased_past_the_catalog_wait_is_unavailable`, `grpc_resumable_streams_sharing_an_upload_keep_the_bytes_persisted_first`, `grpc_resumable_persisted_sizes_carry_the_persisted_checksums`, `grpc_write_specs_refuse_unhandled_fields`, `grpc_io_write_object_awaits_the_stream_end_without_holding_the_session` and `append_refuses_an_invalid_opening_message_before_creating_or_taking_over`. The last two failed before their fixes: WriteObject held the session lease while it waited for the stream to end, and an appendable opening message with a bad CRC32C, a negative offset or an MD5 checksum created the object, or superseded the current writer, before it was refused. `grpc_resumable_persisted_sizes_carry_the_persisted_checksums` failed before persisted sizes carried `persisted_data_checksums`. The two lease tests apply the session settings a server applies at startup; the other tests use a catalog no server configured, which fails a message for a leased session without waiting. `cargo test --locked --offline --lib storage::catalog::resumable::golden_tests` passed `a_running_hash_must_cover_the_persisted_offset`, which pins that a session staged before 0.26.0 has no running digests. The Go SDK suite was not rerun for these changes.

On 2026-11-03, `CARGO_BUILD_JOBS=4 cargo check --workspace --all-targets`, `CARGO_BUILD_JOBS=4 cargo test --lib grpc:: -- --test-threads=4` (96 passed), and `CARGO_BUILD_JOBS=4 cargo xtask lint` (zero production violations) passed. `CARGO_BUILD_JOBS=4 cargo test --lib name -- --test-threads=4` passed 63 tests across JSON, import, administrative publication, seed, URL and gRPC name handling. SDK and real-cloud suites were not run for these checks.

For upload_id streams, object_checksums on a non-final message is an explicit local UNIMPLEMENTED subset: the pinned proto permits first-message checksums, but the current shared session interface cannot persist a changed checksum. Silently retaining it only for the current stream would bypass validation after reconnect. Supply checksums in StartResumableWrite, where the shared options persist them, or in a finish_write=true message. Rejection leaves the durable offset unchanged. Persisted CRC32C/MD5 is enforced after reconnect and catalog reopen; a final mismatch returns INVALID_ARGUMENT, publishes no object and invalidates the session, so QueryWriteStatus and retries return NOT_FOUND.
