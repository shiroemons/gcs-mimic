# Storage v2 object I/O

<!-- markdownlint-configure-file {"MD013": false} -->

Scope: RPC-STORAGE-011, RPC-STORAGE-014, RPC-STORAGE-015, RPC-STORAGE-018, RPC-STORAGE-019, RPC-STORAGE-020, RPC-STORAGE-022, RPC-STORAGE-023 and BEHAVIOR-RPC-003, plus the later CancelResumableWrite addition (RPC-STORAGE-013). RestoreObject and Rapid append are excluded.

## Acceptance contract

- A completed upload is replayed only when the stream starts with that upload_id. If another stream finalizes it after this stream has persisted a message, later messages fail with FAILED_PRECONDITION instead of claiming their bytes were published. Other concurrent-stream behavior remains unverified.

- Ordinary Go `storage.NewGRPCClient(ctx)` Writer, with default chunk size, writes small and multi-MiB bodies; JSON reads the result. JSON uploads are readable through gRPC NewReader and NewRangeReader.
- BidiWriteObject and WriteObject share bounded staging, CRC32C chunk validation, final CRC32C/MD5 validation and transactional publication. Incorrect offsets and checksums never publish an object.
- StartResumableWrite returns a capability; QueryWriteStatus returns a durable offset or the completed resource. Reopening a stream resumes at that offset, including after catalog recovery.
- Every Storage v2 call must carry `x-goog-request-params`; without it, or with an empty value, the call answers INVALID_ARGUMENT, as Cloud Storage did for every RPC asked (recorded 2026-11-18, cases `grpc-probe-routing` and `grpc-probe-inferred-routing`; BidiReadObject was not recorded and follows by inference). A routed bucket other than the request's, or metadata that routes no bucket, answers INVALID_ARGUMENT naming both bucket IDs. A call reads every pair under a key some RPC routes once, checks that its value has the key's form (a `project` is `projects/<id>`) and refuses a key sent twice, even with the same value (recorded for `bucket`; the other keys follow it by inference); it ignores an unknown key, a `routing_token` and a malformed pair under an unknown key, and compares only the keys the RPC routes (`routing_requires_the_metadata`, `routing_validates_every_routed_key_whichever_rpc_is_called`, `routing_refuses_a_duplicated_key`, `routing_ignores_unknown_keys_and_compares_only_the_routed_keys`, `grpc_calls_need_routing_metadata_and_ignore_unknown_keys`). QueryWriteStatus and CancelResumableWrite read the upload ID first: text that is no upload ID is answered without the metadata (recorded), and for a readable ID the metadata is required and must route the bucket the ID names (recorded for both RPCs). The caller is authenticated and authorized for that bucket before the routed bucket is compared, so a caller without access is refused for its access whatever it routes; that order is a local choice. A resumed WriteObject or BidiWriteObject compares the routed bucket with the ID's bucket in the same place, which is inferred from those two RPCs and not recorded (`grpc_io_upload_id_calls_read_the_id_before_the_routing_metadata`, `grpc_io_upload_id_calls_authorize_before_comparing_the_routing`, `grpc_io_resumed_write_compares_the_routed_bucket_after_authorization`).
- Retrying a finalized upload returns OK with its original completion snapshot, even after the live object changes. A clean half-close of an unfinished upload_id stream reports its persisted size even without flush or state_lookup. Non-resumable streams still require finish_write on their last message, as specified by the proto.
- WriteObject and BidiWriteObject answer at `finish_write` and ignore any message that follows it. A `write_object_spec` or `upload_id` repeated on a later message is ignored, and `object_checksums` is accepted on any message (recorded 2026-11-18). An upload persists whole 256 KiB granules until `finish_write`: bytes past the last granule wait for the call's next message, a resumable stream that closes with such bytes fails and drops them, and a flush or state_lookup on a resumable stream reports the persisted granules with `persisted_data_checksums`. A write's answer carries the CRC32C of the persisted bytes alone, where QueryWriteStatus reports their MD5 too (recorded 2026-11-18 for BidiWriteObject, and in cases `grpc-probe-inferred-session-states` and `grpc-probe-inferred-granules` for WriteObject; `grpc_resumable_persisted_sizes_carry_the_persisted_checksums`). A flush or state_lookup on a non-resumable BidiWriteObject stream always reports persisted size 0 with the CRC32C of no bytes, because a write that no upload ID can resume keeps nothing before it finishes: recorded after three bytes and after one whole granule (case `grpc-probe-inferred-granules`, step `bidi-single-granule-lookups`), and inferred for several granules. Every stream message is decoded once into the shared `WriteStep` (`src/grpc/v2/object_io/step.rs`) that the non-resumable, resumable and appendable paths use.
- Object names use the shared flat-namespace validation: dot-only names and the ACME challenge prefix are rejected, while a tab is accepted. Storage I/O failures use the shared storage error classification.
- Generation and metageneration conditions, including create-if-absent, are checked in the publication transaction. Supported fixed/custom metadata is preserved; unsupported semantics return actionable UNIMPLEMENTED. A metageneration match of 0, a match beside a not-match and a negative value are evaluated, not refused, on every object RPC except MoveObject, which refuses a match beside a not-match with INVALID_ARGUMENT whatever the values (recorded 2026-11-18, cases `grpc-probe-object-conditions` and `grpc-probe-inferred-conditions`). A negative match never holds and a negative not-match of -1 holds, except for a write or rewrite that creates a new object, where it fails (recorded for WriteObject, UpdateObject, GetObject, ReadObject, ComposeObject, RewriteObject and DeleteObject; BidiReadObject follows GetObject and ReadObject by inference). A negative generation is still refused with INVALID_ARGUMENT.
- ReadObject supports positive/negative offsets, bounded lengths, out-of-range errors, selected generations, per-message CRC32C and complete-object checksums. Response messages stay below 4 MiB.
- GetObject supports generations, conditions, read masks and `soft_deleted` (a soft-deleted generation, which needs a bucket soft delete policy). A `restore_token` answers INTERNAL "We encountered an internal error. Please try again.", as Cloud Storage did for a live object in a bucket without a hierarchical namespace (recorded 2026-11-18). DeleteObject uses shared hold, retention, versioning and soft-delete behavior.
- ListObjects supports prefix, delimiter prefixes, page size and query-bound continuation tokens; Go Objects iterates them. A page ends near 2 MiB with a next page token, whatever page size was asked for, and always holds one entry so paging advances.
- ListObjects builds the shared query directly and keeps the existing NoAcl page-token format. It does not construct JSON URLs or render JSON object pages. Combination errors name soft_deleted, match_glob and include_folders_as_prefixes; malformed globs keep their detailed syntax explanation.
- CancelResumableWrite cancels an active session from StartResumableWrite, including one with persisted bytes. Later QueryWriteStatus, WriteObject and BidiWriteObject on that upload_id fail, staged bytes are released and no object is published.
- Strict authentication uses shared bucket permissions and rechecks them inside catalog operations. No credentials are discovered and no Google Cloud calls are made.

## Sources and boundaries

Single-shot writes use the typed intake shared with legacy v1 for offsets,
CRC32C, complete hashes, size limits and bounded staging. Protocol-specific
validation and messages stay in each adapter. Both adapters await producer and
catalog completion, preserving root storage failures and the producer's error
when storage reports only BodyAborted; closed consumers interrupt input waits.

The contract uses the foundation's pinned [Storage v2 proto](https://github.com/googleapis/googleapis/blob/933dd1be8180a22bca2dc473b53d4f4297ee3b0c/google/storage/v2/storage.proto), SHA-256 `a0df6132967b97a89be248f1f24d277ee8df8f8d885db1d4af6249469ff0c1cf`, and the existing Go Storage v1.70.0 SDK. Existing source gaps remain open; JSON error choices are not assumed to define gRPC status codes. No dependency, setting, catalog schema or startup order is changed.

The [official RPC reference](https://docs.cloud.google.com/storage/docs/reference/rpc/google.storage.v2) and [Rust 1.99.1 stable announcement](https://blog.rust-lang.org/2026/10/15/Rust-1.99.1/) were checked on 2026-10-28. The foundation's verified dependency graph is retained; no dependency is added or updated.

## Supported subset and resource bounds

Object I/O maps the storage domain errors (`ObjectError` and `CatalogError`) to a Status directly, with one exhaustive match per enum in `src/grpc/v2/status.rs`, and does not go through the JSON adapter. A not-match condition that alone fails answers FAILED_PRECONDITION "The resource you requested has not been modified according to the condition you specified." (`ObjectError::SourceNotModified` for a copy or rewrite source, `CatalogError::NotModified` for a bucket deletion), as Cloud Storage did for reads and writes alike (recorded 2026-11-18). Unsupported settings keep UNIMPLEMENTED with ErrorInfo details.

The existing `max_object_bytes` is passed into the gRPC adapter, with its existing default. No new setting is needed. Incoming protobuf messages retain the foundation's 4 MiB limit. `ReadObject` sends up to 256 KiB of data per message. Upload bridges use two 64 KiB slots. Lists use bounded catalog pages of at most 1000 entries and shared query-bound continuation tokens, without scanning the whole catalog. No database transaction spans network input.

Single-request streams use shared `prepare_object_upload`/`put_object_prechecked`, not retained resumable sessions. The adapter uses the existing incremental hasher to validate final-message digests before sending shared publication's EOF marker. Only shared publication assigns generations and applies conditions/holds/retention. Both streaming RPCs use this same handler. StartResumableWrite uses shared persisted sessions and exclusive per-message writer leases; each message reaches the shared fsync/checkpoint before its offset is acknowledged. Reopening the catalog preserves those offsets. The opaque upload ID includes the bucket name and random shared capability. QueryWriteStatus rechecks current create permission and returns the original completion snapshot even after the live object changes.

CancelResumableWrite reuses the catalog cancellation behind JSON session-URI DELETE. The pinned proto says that after cancellation "Any attempts to write to the resumable upload after cancelling the upload fail", and that in-progress writes may complete first or fail. The local mapping is:

| Case | Result |
| --- | --- |
| Active session, with or without persisted bytes | OK with an empty response. One short catalog transaction marks the session CANCELLED and journals its staging blob; the file is removed after commit, and maintenance retries a failed removal. |
| QueryWriteStatus, WriteObject or BidiWriteObject after cancellation | QueryWriteStatus answers FAILED_PRECONDITION "Upload has already been cancelled." with ErrorInfo reason `GRPC_UPLOAD_ALREADY_CANCELLED`, and a write INVALID_ARGUMENT with the same message (recorded 2026-11-18). A resumed write without `finish_write` is answered alike (recorded 2026-11-18, case `grpc-probe-inferred-session-states`, step `cancelled-write-without-finish`; `grpc_io_ended_sessions_answer_as_recorded`). |
| Repeated cancellation | OK with an empty response (recorded 2026-11-18). |
| Upload_id that is no ID, one that cannot be read, or one that names no session | Text that is no upload ID (an empty string, or no bucket part) answers INVALID_ARGUMENT `Invalid upload ID '...'.`, and an ID that cannot be read (a bucket part followed by anything but 64 hexadecimal digits) answers INTERNAL "We encountered an internal error. Please try again."; both were recorded on 2026-11-18. An ID of the issued shape that names no session the catalog knows answers INTERNAL with the same message, on QueryWriteStatus, a resumed WriteObject and CancelResumableWrite. Recorded 2026-11-18 for an issued ID with one character changed in the middle or at the end (case `grpc-probe-inferred-upload-ids`), an ID with a character appended and an unissued ID under a bucket's resource name (case `grpc-probe-resumable-sessions`); a session under another bucket finds nothing and answers alike. A session expires seven days after StartResumableWrite on the catalog clock, and from that instant the same three calls answer INTERNAL as well. That is not recorded: the catalog answers an expired session as a missing one and its maintenance deletes the row, so the emulator cannot tell an expired ID from one it never issued (`grpc_io_upload_ids_are_looked_up_after_the_permission_check`, `grpc_io_resumable_sessions_expire_seven_days_after_start`). The lookup follows the permission check, so a caller without access is denied whatever the ID. |
| Finalized upload | FAILED_PRECONDITION "Upload has already been completed." with reason `GRPC_UPLOAD_ALREADY_COMPLETED` (recorded 2026-11-18). QueryWriteStatus keeps reporting the resource, with the caller's ACL and owner view, and the object stays; use DeleteObject to remove it. Resumed WriteObject returns OK with the original completed resource as the proto requires. |
| Session ended by a finishing message of the wrong size | A finishing message whose size misses `object_size` answers OUT_OF_RANGE with reason `GRPC_MISMATCHED_UPLOAD_SIZE` and ends the session; QueryWriteStatus, CancelResumableWrite and a resumed WriteObject, with and without `finish_write`, then answer FAILED_PRECONDITION "Upload has already been terminated." with reason `GRPC_UPLOAD_ALREADY_TERMINATED` (recorded 2026-11-18, case `grpc-probe-inferred-session-states`; `grpc_io_terminated_sessions_refuse_cancels_and_writes`). A message without `finish_write` whose bytes go past `object_size` ends the session the same way (recorded, case `grpc-probe-inferred-granules`). Not recorded; inferred: a finishing message above `object_size` ends the session too, because only Cloud Storage's refusal of it was recorded, and a session the emulator ended for another reason answers alike. |
| A writer currently holds the session lease | The cancellation waits for the lease through the shared writer wait, up to `catalog_wait_timeout_ms` on a server (an embedded catalog does not wait). If the writer still holds it when the wait ends, UNAVAILABLE with the session unchanged. This is the proto's unspecified in-progress-write case; retry after the write finishes. |
| Strict mode | gRPC upload IDs are not bearer capabilities, so the caller needs `storage.objects.create` on the bucket, the same check as QueryWriteStatus and resumed writes. The creator is not special: a different caller with that permission, such as a `roles/storage.objectUser` principal, cancels a session someone else started. A viewer receives PERMISSION_DENIED and an anonymous caller UNAUTHENTICATED, as for the other v2 RPCs; the session remains usable. |

Write metadata supports content type/encoding/disposition/language/cache control, custom metadata, temporary/event holds and custom time. Empty/default protobuf values are accepted. Nondefault unhandled object fields, predefined ACLs and appendable objects return actionable UNIMPLEMENTED. Customer-supplied keys follow [grpc-v2-customer-supplied-keys.md](grpc-v2-customer-supplied-keys.md). Write metadata has no 8 KiB limit: Cloud Storage stored WriteObject custom metadata values of 8192 and 40,000 bytes and an UpdateObject value of 20,000 bytes (case grpc-custom-metadata-limit, recorded 2026-11-15). Fixed and custom metadata past the local 40 KiB once encoded as JSON, shared with JSON and XML, return INVALID_ARGUMENT without publication. Explicit object_size is checked before staging and at finish.

ReadObject clamps negative offsets beyond the start to zero, permits offset equal to size (empty read), rejects greater offsets with OUT_OF_RANGE and rejects negative limits with INVALID_ARGUMENT. Returned content ranges use an exclusive end. GetObject/list masks accept every top-level `Object` field and `*`, matching the 2026-10-31 Google observation in [the gRPC object field evidence](../evidence/grpc-object-fields.md) (the official Java SDK sends all 33 fields); ReadObject additionally selects its metadata (`metadata`, `metadata.FIELD`) and top-level response fields. Responses carry the JSON resource's `etag` and `update_storage_class_time` (`timeStorageClassUpdated`). `acl` and `owner` appear only when a mask names them or uses `*` (or ReadObject's whole `metadata`), as the proto's default masks exclude them; they come from the same shared projection as JSON `projection=full`, so uniform bucket-level access, a caller without `storage.objects.getIamPolicy` on the object, or an unfinalized appendable object leaves both empty while the read succeeds. Fields no local object can hold (`kms_key`, `contexts`, the restore token of a live object) stay empty rather than invented.

A member of a singular message is selected on its own on GetObject, ReadObject (under `metadata.`) and ListObjects: `checksums.crc32c`, `checksums.md5_hash`, `owner.entity`, `owner.entity_id`, `customer_encryption.encryption_algorithm`, `customer_encryption.key_sha256_bytes`, `retention.mode` and `retention.retain_until_time` (`src/grpc/v2/object_io/object_mask.rs`). Cloud Storage was recorded serving `owner.entity` on all three and returning it without an owner, so `acl` and `owner` are filled only for a path that names the whole field (recorded 2026-11-18). A path that names no field of the resource answers INVALID_ARGUMENT: an unknown name, `owner.no_such_field` and `acl.role` were recorded on GetObject (2026-11-18), and so were a map key (`metadata.somekey`), a path under a scalar (`name.x`) or under a member (`owner.entity.x`), an empty path, a trailing dot and a leading dot (case `grpc-probe-inferred-object-masks`). A path under a name that is no field, under the context map or under a part of a timestamp is the same answer by inference. The parts of a timestamp (`create_time.seconds`, `create_time.nanos`) and `contexts.custom` are selected: Cloud Storage answered `create_time.seconds` with a timestamp of whole seconds and `contexts.custom` with an empty message for an object without contexts (recorded; `a_part_of_a_timestamp_and_the_context_map_are_selected_as_members`), and the `nanos` part and the other timestamps follow by inference. The parts of the retention's timestamp (`retention.retain_until_time.seconds`, `.nanos`) are the one member Cloud Storage was not recorded on, so they answer UNIMPLEMENTED with ErrorInfo and a client requests the whole field.

Which fields a read mask may name does not depend on the object, so GetObject, ReadObject and ListObjects check the mask with the request, before authorization and any lookup, as GetBucket checks its mask; ListBuckets checks its mask after it authorizes the project. A path naming no object field answers INVALID_ARGUMENT, `There is no field for this resource named '...'.` on GetObject and `Invalid read_mask field: '...'.` on ListObjects (both recorded 2026-11-18, GetObject for an existing object, a missing object and a missing bucket, ListObjects for an empty page and a page with an object), and a sub-path gcs-mimic does not select answers UNIMPLEMENTED with ErrorInfo, for a missing object, an empty page or an unauthorized caller too, an anonymous one included, while a valid mask still reports a missing object as NOT_FOUND. A ReadObject path that names no ReadObjectResponse field, such as `read_handle`, or a sub-path of `content_range` is refused like an unmodeled setting: UNIMPLEMENTED with ErrorInfo, and UNAUTHENTICATED for an anonymous caller. `object_checksums.crc32c` selects that digest alone (recorded 2026-11-18, case `grpc-probe-inferred-object-masks`, step `read-mask-content-and-object-checksums`), and `object_checksums.md5_hash` selects the MD5 alone by inference (`a_read_mask_keeps_only_the_response_fields_it_names`). Not recorded: Cloud Storage's answer to a refused ReadObject path, and to an unknown path under ReadObject's `metadata.` prefix, which is worded like GetObject's. A ReadObject mask that selects fields must include `checksummed_data.content` (INVALID_ARGUMENT "The 'read_mask' field must include checksummed_data.content, but was '...'.", recorded), and a mask that selects the content alone gets the bytes without their CRC32C (recorded 2026-11-18). GetObject reports a malformed customer key and a malformed name before the mask, and ReadObject a malformed key and name, then the mask, and the `restore_token` refusal and the `soft_deleted` lookup come after it and after the bucket's authorization. The recorded precedence cases show a malformed key and a mask without the content before a missing object (`grpc-probe-object-precedence`); the order of the remaining checks is a local choice (SPEC-GRPC-LOCAL-CHOICES).

ReadObject reports its failures in this order: a malformed customer key, a malformed name and the read mask, all INVALID_ARGUMENT apart from the refused paths above; the bucket's authorization, which refuses a caller only when the bucket does not exist and the caller holds `storage.objects.get` in no project (UNAUTHENTICATED for an anonymous caller, PERMISSION_DENIED for a principal); a negative generation, INVALID_ARGUMENT; the object's authorization with the lookup, so in an existing bucket an anonymous caller is denied with PERMISSION_DENIED for a missing object too; NOT_FOUND for a missing object; FAILED_PRECONDITION for a failed condition; OUT_OF_RANGE for an offset past the end; and last INVALID_ARGUMENT for a negative `read_limit`. Recorded 2026-11-18: the key and the mask before a missing object, and a failed condition before an offset past the end; the rest of the order is a local choice. ReadObject returns the stored bytes of an object whose `content_encoding` is gzip without decompressing them, for a whole read and a range (recorded 2026-11-18, `grpc-probe-object-masks`, step `read-gzip`: Storage v2 does not transcode), and the JSON and XML reads follow BEHAVIOR-OBJECT-017.

GetObject, ReadObject and DeleteObject compare the generation and metageneration conditions that arrive, as Cloud Storage does (recorded 2026-11-18, `grpc-probe-object-conditions`): a metageneration match of 0 never holds and fails with FAILED_PRECONDITION, and a match beside a not-match is evaluated, not refused. A negative value is evaluated as well: a match of -1 never holds, so it fails with FAILED_PRECONDITION, and a not-match of -1 holds (recorded 2026-11-18, case `grpc-probe-inferred-conditions`: GetObject and DeleteObject; ReadObject shares GetObject's rule). BidiReadObject, which was not recorded, reads the same object under the same rule by inference. The tests are `read_object_refuses_negative_limits_and_offsets_past_the_end`, `get_object_refuses_restore_tokens_and_negative_values` and `write_and_delete_object_compare_negative_conditions`.

The broader rows remain PARTIAL; [ledger cases](#ledger-cases) lists what remains. Explicitly resumable writes use the shared resumable engine: sessions are unlimited in number unless `max_resumable_sessions` sets a limit, and they expire seven days after StartResumableWrite. WriteObject and BidiWriteObject answer at `finish_write` and ignore a later message; WriteObject reads nothing past the finishing message (`grpc_io_write_object_answers_at_finish_write_without_reading_further`), so a client that keeps its stream open holds no session. A listing page ends near 2 MiB of encoded objects, so metadata-heavy listings stay under the 4 MiB receive limit (`grpc_object_lists_page_on_their_size_and_reach_every_object`). Every recorded Storage v2 owner carries only `entity`, which is what the emulator returns.

## Ledger cases

The ledger rows list one acceptance case per checkable behavior (decomposed on 2026-11-18). An answer that Google does not document and the recording of 2026-11-18 did not cover is a local choice, recorded as a scoped difference with a pinning test. In summary:

- Refused on purpose (scoped differences under SPEC-GRPC-UNMODELED-SETTINGS): a write resource with `kms_key` or object contexts, on WriteObject, BidiWriteObject and StartResumableWrite, and the ListObjects contexts `filter`. A GetObject `restore_token` is not refused as unsupported: it answers the recorded INTERNAL, since only hierarchical namespace buckets use it.
- Aligned with the 2026-11-18 recording of Cloud Storage: the routing metadata and its refusals; the answers of the write streams and resumable sessions listed above; object conditions and read masks (GetObject, ReadObject and ListObjects); GetObject `soft_deleted` and `restore_token`; the gzip read. The probe cases are `grpc-probe-routing`, `grpc-probe-write-streams`, `grpc-probe-bidi-write`, `grpc-probe-resumable-sessions`, `grpc-probe-object-conditions`, `grpc-probe-object-masks` and `grpc-probe-object-precedence`.
- Aligned with the second recording of 2026-11-18, which asked about answers the emulator had decided by inference (cases `grpc-probe-inferred-routing`, `grpc-probe-inferred-upload-ids`, `grpc-probe-inferred-session-states`, `grpc-probe-inferred-granules`, `grpc-probe-inferred-conditions`, `grpc-probe-inferred-object-masks` and `grpc-probe-inferred-destinations`): the routing of every RPC, an unknown upload ID answering INTERNAL, a terminated session answering FAILED_PRECONDITION, a first offset at or below the persisted size being accepted with the overlap skipped, bytes past `object_size` ending the session, object checksums declared on a stream holding for that stream, negative conditions being compared, and the timestamp-part, `contexts.custom` and single-digest read masks. Where the recording matched the inference the text above says it is now recorded; where it did not, the emulator was changed.
- Resumable and single-shot writes check a message in one order, held by `WriteStep::admit` (`src/grpc/v2/object_io/step.rs`): the offset, the size, the data CRC32C, then the message's object checksums, which must be readable and agree with the ones declared before, then the conditions, then the finished-object verification. Recorded: a first offset past the persisted size and an `object_size` the bytes miss answer before a wrong data CRC32C and before a failing condition, a wrong data CRC32C answers before a failing condition, a failing condition alone is FAILED_PRECONDITION, and a first offset past the persisted size answers before a malformed `md5_hash` (case `grpc-probe-inferred-session-states`). Declared object checksums are verified when the stream finishes: a mismatch answers INVALID_ARGUMENT `Object crc32c mismatch: server computed: '...', client provided: '...'.` before anything is written and leaves the session open (recorded for a CRC32C declared earlier in the finishing stream). Not recorded, inferred: the same for an MD5, a checksum declared by the finishing message or StartResumableWrite, a non-resumable write's first message reading its object checksums after its data, the session's key being checked before the message, and a malformed `md5_hash` against the size, the data checksum and the conditions (`grpc_resumable_write_error_precedence`, `grpc_single_shot_write_error_precedence`, `grpc_resumable_object_checksums_hold_for_their_stream`).
- A resumed stream's first message at or below the persisted size is accepted and the bytes it repeats are skipped; the persisted size is unchanged (recorded, case `grpc-probe-inferred-granules`, steps `first-offset-zero` and `first-offset-inside-persisted`). A first offset past the persisted size still answers OUT_OF_RANGE with `GRPC_UPLOAD_INVALID_START_OFFSET`. The repeated bytes are not compared with the persisted ones: that is the emulator's choice, since the recording repeated identical bytes, and `grpc_repeated_bytes_are_skipped_without_comparison` pins that the bytes received first stay, on a resumable stream and on a non-resumable write's later message. A finishing message whose bytes all lie inside the persisted ones finalizes the object at the persisted size when no `object_size` was declared and ends the session when `object_size` differs (not recorded).
- Local choices that remain (SPEC-GRPC-LOCAL-CHOICES; the gap item lists each with the test that pins it): CancelResumableWrite's UNAVAILABLE while a write holds the session lease, and cancellation by any caller with `storage.objects.create`, not only the session creator; the seven-day session expiry and INTERNAL for an expired session, which the catalog cannot tell from an ID never issued; the state after a finishing message above `object_size`, a session the emulator ended for another reason, the repeated bytes of a resumed message being skipped without comparison, a finishing message wholly inside the persisted bytes, and the checks of a resumable message that Cloud Storage was not recorded on (the places of the session's key and of a malformed `md5_hash`, the MD5 wording, a non-resumable first message's object checksums read after its data); the routing keys that were not recorded (a malformed `source_bucket` or `appendable`, a duplicated key other than `bucket`, a routed project refused alone, no project routed on ListBuckets), the routed bucket of a resumed write, and the comparison after authorization; the order of GetObject's and ReadObject's checks after the mask and of ReadObject's failures; the UNIMPLEMENTED answers to ReadObject response paths and to the retention's timestamp parts in a read mask; BidiReadObject's negative-condition comparison.
- Every Storage v2 row depends on BEHAVIOR-RPC-001, because every RPC passes its routing and request-metadata handling. RPC-STORAGE-013 has no pending case of its own; server-side `grpc-timeout` and gzip message compression are scoped differences under SPEC-GRPC-CALL-METADATA.
- Pending code work: `predefined_acl`, `acl`, `retention` and output-only fields on a write resource (and whether `resource.checksums`, which the proto marks output-only, keeps being verified).
- Pending tests: the order of DeleteObject and WriteObject failures not covered by the recorded precedence cases; non-decreasing QueryWriteStatus answers; write, sync and crash faults at a session checkpoint.
- Decisions: waiting for a busy session lease (as now, up to the catalog wait, then UNAVAILABLE) or answering ABORTED.

## Verification

On 2026-11-18 ten probe cases (`compatibility/differential/cases/grpc-probe-*.json`) were recorded against Cloud Storage and the object I/O answers above were aligned with them; the offline replay matches every recorded case. The tests in `src/grpc/v2/object_io/read/mask_tests.rs` were written first and failed while the masks were checked on the result: an invalid mask on a missing object answered NOT_FOUND and one on an empty listing succeeded. After the change `an_invalid_read_mask_is_reported_for_a_missing_object` and `an_invalid_read_mask_is_reported_for_an_empty_listing` report unknown and nested paths there; `an_invalid_read_mask_precedes_authorization_and_the_other_checks` reports the mask before an anonymous caller is denied (GetObject and ReadObject answer PERMISSION_DENIED and ListObjects UNAUTHENTICATED without it) and before a negative generation or a read offset past the end, which answer INVALID_ARGUMENT and OUT_OF_RANGE without it; `request_checks_before_the_mask_keep_their_order` keeps a malformed key and a malformed name before the mask, while a soft-deleted lookup and a restore token are read after it. `cargo test --locked --offline --lib grpc::` passed 270 tests.
