# Native write-back restart recovery

<!-- markdownlint-configure-file {"MD013": false} -->

This storage slice supports DESIGN-072 and DESIGN-074. It adds bounded restart recovery beneath the runtime mirror; actor startup, strict control authorization, CLI/HTTP projection and final distribution checks belong to their owning slices. The feature ledger remains authoritative and the broad synchronization rows remain partial.

## Recovery contract

`Writeback::recover_pending` owns the existing write-back execution permit and root/catalog leases until its file and SQL transitions finish. It scans pending operations by ordinal in keyset pages of at most 256 entries. It uses existing bounded file workers and short transactions with static cached statements; it never collects the entire pending catalog or object body.

Prepared operations have not armed target replacement. Only their opaque private API-copy entry may be removed, including an incomplete or empty copy. Recovery verifies the original root and workspace directory identities, removes only that owned entry, synchronizes the workspace and root, and then cancels the checked intent and releases its reservation. Unrelated workspace entries and current targets remain untouched.

An armed operation's workspace entry is reclaimed when it holds no bytes that anyone else made. The entry must be a regular file that no other name links, unchanged while it is hashed, whose size, MD5 and CRC32C match a publication's API copy, or which matches the body the catalog tracks at the target by size, MD5 and CRC32C. Its modification time is not compared: a time alone never decides that a body differs, and in a container bind mount a stale read comes with an equally stale size and modification time, so the time would protect nothing. A removal has no API copy: the hashes its operation records are the tracked body's, and only the second rule proves it. That second rule is the one installation unlinks a displaced body by, decided by one function, so recovery removes no body that installation would have kept; a tracked body whose bytes are unchanged but whose modification time moved is reclaimed. Installation and recovery unlink an entry only with a proof that it holds one of these bodies, or the copy of an operation not yet armed, and only while its name still holds the body that was proved. A process stopped after arming and before the rename leaves the API copy there, and one stopped after an overwrite's exchange or a removal's move leaves the tracked body that the API change replaced; installation would have unlinked it next. Recovery unlinks that entry, synchronizes the workspace and root, and cancels the operation, so the restart reports no conflict. The bytes alone never prove that installation finished: the target is not trusted because the workspace is empty or because its bytes match.

Armed or durable operations with no workspace body are cancelled only after verifying and synchronizing that absence. The current target is left for ordinary full reconciliation. Any other surviving body becomes protected under its original owner, bucket incarnation and root: one differing byte, another link to the entry, or a body left by a durable operation, which installation never leaves, keeps it. Actual size is charged in full, including empty files and displaced bodies beyond the configured quota; an over-limit body is never evicted. Existing protected operations remain protected, including those protected before reclamation existed and those an installation failure protected while the process ran. Only registered conflict transfer or an explicitly confirmed operator discard can release them, through the existing conflict backend.

Recovery attempts the existing root/workspace/quota resume validation only after every pending operation has resolved. File, parent-sync or SQL failures retain the intent and stop until retry; a committed cancellation cannot release its charge twice after a lost response. Neither recovery nor its cancellation checks the current API generation to retarget retained data or alter API objects.

## Reusing a captured path

`RootLease::capture_path` can reuse a registered conflict copy when the catalog, root, logical target, bucket incarnation, original owner and full source observation still match. Both the opened source and owned read-only copy are checked with bounded incremental hashes, size, device, inode and nanosecond timestamps. Missing or changed copies and changed external files do not reuse a proof. Only the ephemeral proof binds to the current expected API generation; the retained record keeps its original observed generation and owner.

This avoids retaining the same external file repeatedly when an API generation changes just after capture and the runtime safely defers replacement. Direct `capture_conflict` calls still create independently requested retained copies. No schema, cache, dependency or broader deduplication service is added.

## Verification boundary

The focused tests cover real same-directory restarts, prepared short/zero/full copies, armed/durable absence and surviving bodies, exact quota and over-quota boundaries, a 1 TiB plus one-byte sparse body without reading it in full, unrelated workspace entries, current external targets, repeated recovery and exact quota release. A 257-operation test crosses the 256-entry page boundary. API change, object deletion and cross-project bucket recreation preserve the original retained owner, generation and incarnation. Unexpected unarmed removal bodies become protected, and workspace replacement blocks recovery without removing the original bytes. Live-export tests restart at prepare, copied, armed, installed, durable-state and acknowledged boundaries.

Recovery cancellation injects failures before and after unlink, parent synchronization and SQL completion. Paired catalog and actual working-tree Snapshot/PowerLoss seams reopen the captured catalog, verify API record/body/checksums, reactivate the original root and run recovery through quota release. A protected-state checkpoint separately retains bytes and full quota through restart, then resumes only after an exact, explicitly confirmed discard. The snapshots restore copied file contents into the original root/workspace directories, preserving their actual directory identities; production identity checks are unchanged. Live-export seams cover copying, file synchronization, installation and acknowledgement.

`durable_replace_between` records its rename in the fault model right after the rename and before the parent syncs inside it: a create or a removal as a move between the private workspace and the target directory, an overwrite as an exchange. Installation then records the unlink of the displaced or removed body. The power-loss model keeps the rename volatile until both parents are synced and the unlink until installation's workspace sync, so a crash test fails when either parent sync inside the call or the workspace sync after the unlink is missing. Installation's own sync of the target directory after the call repeats one the call made and changes no modeled entry. A separate `fsutil` test of the call alone also fails when the staged file's sync is missing; the installation tests do not, because the copy step synced that file already. The model assumes a rename is atomic: a power loss keeps a move or an exchange whole or undoes it whole. A snapshot fails rather than skip an undo whose names no longer fit, since skipping it would invent a state no power loss leaves.

A create, an overwrite and a removal are each crashed and power-loss-snapshotted after the copy is durable, after the rename and the parent syncs inside its call, after installation, and after acknowledgement. The restart recovers write-back, rescans and reconciles the tree, and runs the wait that `sync wait` uses. The target converges to the API state, neither API nor external bytes are lost, and the wait succeeds without a conflict: a private copy or displaced body the restart finds in the workspace is reclaimed. One changed byte in the API copy, in an overwrite's displaced body or in a removal's moved body keeps it protected, so the restart moves it into the conflict store and the wait reports it; so does a displaced or moved body whose last byte changed or that grew by one byte while its modification time was set back to the recorded one. A displaced or moved body whose bytes are unchanged and whose modification time alone moved is reclaimed: the wait succeeds without a conflict and a file beside the target keeps its bytes. Crashes and power losses while recovery reclaims an entry, before and after the unlink, the parent syncs and the SQL completion, recover on the next restart the same way, and failed unlinks, syncs and completions there keep the operation for a retry. Snapshots and their restores keep each copied file's access and modification times. Before reopening a snapshot, the tests rewrite the stored fingerprint of each restored file that holds its tracked bytes, because a copied file has a new inode number and change time. A parent sync that fails inside the rename's call is injected for each kind and each parent. Restarted as a process abort after the failure is recorded, the failure protects the displaced or removed body while the process runs, so it stays in the conflict store after the restart. Crashed or power-loss-snapshotted right after the failed attempt, before the failure is recorded, the restart recovers without a conflict: a power loss undoes the rename whole and leaves the API copy in the private entry, and an abort keeps the rename with the displaced or removed body there; recovery reclaims either. A failed attempt marks the operation for recovery and is never retried in the same process, so no retry reaches installation's check for a rename an earlier attempt already made. A hard link that leaves the private copy also at the target is protected without removing the target or recording the installation.

An export whose target name an empty directory holds removes that directory just before the rename, and the model records the removal as volatile until a sync of the target's parent; undoing it creates the empty directory again, and fails if its name is taken. That export is crashed and power-loss-snapshotted before the removal, after the removal and before its sync, after the rename and after installation. A power loss that undoes the removal leaves the empty directory, and the restart removes it and exports the same way; a power loss after the rename finds the name free. The removal's own sync of the parent changes no checkpoint, because the rename's call syncs the same directory before the next one, so removing it passes these tests; it keeps the removal durable before the name is taken again on a filesystem that could otherwise keep the rename without the removal. An injected refusal of the removal keeps the directory as a collision, any other failure of the removal or of its sync fails the attempt for a retry, and an entry put into the directory just before the removal stays with it.

The root directory sync after installation changes no modeled entry, so removing it passes these tests. The copy step records the private copy's new entry, which stays volatile until the copy step's workspace sync, so a power loss after the copy step fails the test when that sync is missing. A lost copy entry leaves recovery nothing to protect, so it cancels the operation.

The seam model covers only instrumented operations, not every instruction or physical host power loss. Native tests do not establish Linux checked-exchange races, Windows filesystem behavior, final SDK/container behavior, or performance improvement. Sparse oversized files are tested by metadata inspection rather than snapshot materialization. The final runtime owners run heavy combined checks after source freeze.
