  These are configured/source bounds, distinct from the measurements below.
- One 8 MiB /dev/urandom chunk file is repeated to construct each logical
  object. curl -T streams this disk file; neither client nor server receives
  an object-sized input array. No compression is requested. Repetition means
  this is not a unique-random-byte, compression or deduplication benchmark.
- Raw JSON initiation POST returns a fixed client-reachable Location, consumed
  unchanged. Each PUT carries Content-Range and an 8 MiB body. Assert HTTP 308
  and exact Range for intermediate requests, then HTTP 200/201 and exact final
  metadata size. All observed final responses were 200.
- Upload wall time uses Perl Time::HiRes around the upload wave, excluding
  initiation, expected hashing and verification downloads. Throughput is total
  uploaded MiB divided by that interval, including client process/loop overhead.
- ps -p <server-pid> -o rss= samples native process RSS (KiB) every 0.05 seconds
  plus ps execution overhead, from before uploads through their completion.
  Sampled peaks can miss short transients. Baselines follow session initiation.
- /usr/bin/time -l wraps the server itself. Its maximum resident set size is
  bytes, covers startup, upload, verification downloads and orderly SIGTERM,
  and is reported separately from upload-only samples and peak footprint.
- Server upload CPU is the difference of ps -o time= immediately before/after
  the upload wave (0.01-second display precision); this excludes downloads.
  Whole-lifetime user/sys CPU comes separately from time -l. No child clients
  or samplers are included in server CPU/RSS.
- curl time_total measures each request including upload and response wait;
  final-request latency includes its last chunk and finalization work. p50/p95
  are sorted lower empirical quantiles: index floor((n-1)*p)+1, not interpolated.
  They describe chunk requests in one run, not independent repeated trials.
- Slow case uses curl --limit-rate 1M (1 MiB/s) on each of its two PUTs.
  Concurrent case initiates all eight sessions before launching eight clients,
  each with a 256 MiB object (2 GiB aggregate), then waits for every client.

  it excludes the 8 MiB client fixture and is not a time-sampled disk peak.
