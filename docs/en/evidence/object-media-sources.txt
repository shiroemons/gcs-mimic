Research findings (paraphrased; pending integration, not execution evidence):
- The JSON media subsection of data-validation explicitly permits X-Goog-Hash.
  The omission of that header from the JSON common-header inventory is not a ban.
- Content-MD5 is explicitly described for XML, not established for JSON media.
- The JSON status catalog specifies mediaDownloadRedirect/303 when /download is omitted.
  The get reference and endpoint guide do not explain when direct success versus redirect
  applies. SPEC-009 tracks this; do not claim direct 200 on both paths is exact.
- False not-match has 304 in the preconditions guide; the generic 412 catalog and missing
  method-specific precedence leave mutation/combined-condition choices in SPEC-008.
- JSON header docs require upload Content-Type, while resource docs give a serving fallback;
  missing-request-header acceptance is not established (SPEC-011).
- Response header completeness and opaque resource encodings remain SPEC-012.
- Hash duplicate/unknown-algorithm parsing, JSON Content-MD5 and exact mismatch reason remain
  SPEC-010. Expected checksum mismatch is HTTP 400; no invalid object may become visible.
- Name recommendations are distinct from required flat-namespace Unicode/byte/name rules.
- Full Object resource and permission support are not claimed by this slice.
