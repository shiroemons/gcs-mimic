# 段階的な実装順序

1つの段階にも複数の小さな実装があります。AIへは機能IDを指定し、1回で1つの動作経路を完成させます。台帳の `phase` は順序、`priority` は同じ段階内の優先度です。実装前に依存関係を具体化します。

| 段階 | 作るもの | 完了を判断する証拠 |
| --- | --- | --- |
| P0 基盤 | Rust構成、CLI、設定、ヘルスチェック、Docker amd64/arm64、台帳と表の生成、仕様の固定、時刻の抽象化 | 起動・停止、表の同期、状態検証。GCS機能は未実装のまま |
| P1 データ基本 | バケットとオブジェクトのCRUD、ストリーミング、media/JSON multipart、メタデータ、一覧、基本Range、チェックサム、世代・条件更新、永続化 | Go/Ruby、異常系、同時作成、再起動、本文容量に比例しないバッファ |
| P2 公開・URL | ローカル認証、IAM/ACL、UBLA/PAP、XMLの本文経路、公開URL生成、V4署名、CORS、Docker内外の接続 | 公開/非公開、期限切れ、改ざん、異なるHost、署名者権限、Railsの公開/限定配信 |
| P3 転送とHTTP | 再開可能アップロード、再試行、copy/rewrite/compose、JSON batch、残りのXML、multipart、V2/HMAC、条件ヘッダー、変換 | 中断復旧、継承、部分失敗、ストリーミング、プロトコル間の整合 |
| P4 保護 | Versioning、Soft deleteと復元、hold、保持期間、Lifecycle、Autoclassのローカル状態 | 仮想時刻と組合せ試験、保持違反を拒否、早すぎる削除を防止 |
| P5 階層・制御 | HNS、フォルダrename、Managed Folder、継承、Storage Layout、長時間操作 | 原子的変更、一覧への反映、権限継承、キャンセル制約、操作状態取得 |
| P6 gRPC・Rapid | Storage v2の単方向/双方向通信、field mask、Rapid追記型オブジェクト | SDKのgRPC試験、writer交代、書き込み中の読み取り、非対応の組合せを拒否 |
| P7 拡張 | キャッシュ、Insights/Intelligence、Batch、Contexts/Enrichments、MCP、通知、暗号化と外部連携、追加SDK | ローカルで厳密再現する部分と模擬の区別、ジョブ/イベント/結果の再現、制約の公開 |

## 最初の実用版

P1とP2の主要部分を最初の実用版の範囲とします。分析・キャッシュ・ML機能の完成まで公開を待つ必要はありません。一方、この時点で完全互換を名乗らず、対応API・認証モード・SDKの組合せを明記します。

最初の依頼はP0に限定します。その次はバケットCRUD、本文のアップロード/ダウンロード、一覧とメタデータ、公開/非公開、V4署名の順に進めます。

例えば `objects.insert` はmediaのみ動いても、multipartとresumableが残っていれば一部実装です。`objects.list` も、条件なしの最初のページが返るだけでは完了にしません。台帳の小さな動作項目から順番に埋めます。

## 更新とリリース

高度な機能へ進む前とリリース前に、Discovery、protobuf、リリースノートの差分を確認します。新しいAPI・フィールド・Previewを未実装として追加し、過去の項目を消して見かけの進捗率を上げません。

資源使用量に関係する変更は同条件で測定し、2つのCPUアーキテクチャ、対応SDK、英語/日本語資料、完了証拠を確認します。実際のイメージ・パッケージ公開は、その時点の依頼と権限に従います。
