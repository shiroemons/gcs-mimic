# 計画資料の使い方

Rust製Google Cloud Storageエミュレーターを段階的に実装するための計画キットです。プロジェクト名・CLI名は **gcs-mimic** です。現時点ではサーバー実装、公開済みDockerイメージ、互換性試験の合格実績、性能測定値はありません。

## 言語方針

コード、コメント、CLI、ログ、コミット、Issue・PR、READMEを含むプロジェクトの正本ドキュメントは英語です。実装指示と作業報告は日本語です。この `notes-ja/` は補助資料であり、実装台帳の正本ではありません。当初の日本語資料の希望も、この補助資料で扱います。

## 着手する順番

1. プロジェクト名は **gcs-mimic** で確定しました。「mimic」が擬態・エミュレーションを連想させるため、という命名理由を[名称の記録](../naming.md)に残しています。
2. 元のキットの`project/`はリポジトリ直下へ配置済みです。現在実行できる台帳ツールの手順は[英語README](../../README.md)にあります。
3. [日本語共通プロンプト](../prompts/00-master.ja.md)と[初回プロンプト](../prompts/01-bootstrap.ja.md)でP0だけを実装します。
4. 以後は[機能別プロンプト](../prompts/02-implement-feature.ja.md)に台帳の機能IDを指定し、小さな単位で実装します。
5. 対象の受け入れ条件と検証証拠が揃った行だけ、正本JSONを更新して表を再生成します。

コマンド・リポジトリ・Dockerイメージ名は `gcs-mimic` に統一しています。`REPOSITORY_URL` だけは、将来作成する実在のリポジトリURLに置き換えます。

## 全体の導入フロー

| 手順 | 実装後に成立させる体験 |
| --- | --- |
| 1. 前提を用意 | Git、Docker、Compose、curl。Docker利用者にRustの導入を必須にしない |
| 2. ソース取得 | 実在するリポジトリをclone。最初はソースからDocker build |
| 3. 設定 | 待受、API接続先、公開URL、認証モード、保存先、資源上限を設定 |
| 4. 初期データ | 読み取り専用fixturesと永続volumeを分離。再起動で上書きしない |
| 5. 起動 | Compose起動後、復旧とseedが完了してからready |
| 6. 最初の操作 | curlでbucket作成、upload、metadata、download、list、delete |
| 7. SDK接続 | ホストPCとCompose内アプリのそれぞれでGo／Rubyを検証 |
| 8. 公開範囲 | strictモードで匿名拒否、IAM/ACL公開、公開解除、UBLA/PAPを検証 |
| 9. 署名URL | 実際にアクセスするHostで署名し、有効・期限切れ・改変・権限不足を確認 |
| 10. ブラウザ | XMLとJSONのCORS差、Railsの公開／非公開・direct uploadを確認 |
| 11. 永続性 | 再起動後も本文・世代・メタデータ・権限が維持される |
| 12. 終了・初期化 | 停止とデータ削除を分ける。初期化は対象を明示した操作 |
| 13. CI | ポート、project名、volumeを分離し、並列実行・ログ・終了時の後片付けを検証 |

詳細な予定コマンドは[英語導入仕様](../../docs/en/getting-started-spec.md)にあります。未実装コマンドを現在利用可能なものとして案内しません。

## 最新版の方針

実装時点の最新安定版Rustと、選択した依存ライブラリの最新安定版を使います。2026-10-21の確認時点ではRust 1.99.1ですが、実装開始時に公式情報を再確認します。毎日の更新検出、作業開始時・リリース前の確認、テストを通した更新をP0の要件とします。

採用した状態は `rust-toolchain.toml`、`Cargo.lock`、Docker digest等に記録します。通常ビルドはその状態を再現し、更新作業で最新版へ進めます。依存先の互換性によって最新版同士が両立しない場合は、移行または依存の置き換えを検討し、解消できない理由を明記します。古い版を黙って固定し続ける方針にはしません。

## 表の読み方

[全機能表](feature-matrix.md)は正本JSONから生成した日本語の補助ビューです。`NOT_STARTED` は未着手、`PARTIAL` は一部実装、`IMPLEMENTED` は対象の受け入れ条件を検証済みという意味です。実装済みでも `LOCAL_SIMULATION` ならGoogleの実サービスそのものを再現したことにはなりません。

API操作・動作要件・プロジェクト要件は別々に集計します。たとえばDocker起動が完成しても、GCS APIの対応率は増えません。APIの個数だけで実装工数や互換性を判断しません。
