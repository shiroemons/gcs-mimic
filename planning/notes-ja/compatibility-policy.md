# 実装状態の管理と完了条件

## 正本は1つ

`compatibility/features.json` だけを進捗の正本にします。英語・日本語の表はそこから生成します。API、動作仕様、プロジェクト基盤は別の種類です。合計件数を「独立したGCS機能数」と解釈しません。

現在は全件 `NOT_STARTED`、実際の再現精度は `NONE`、テストと検証結果は空です。資料を作ったことをAPI実装済みと数えません。実装を始める際に、対象行の受け入れ条件と依存関係を先に具体化します。

| 状態 | 意味 |
| --- | --- |
| `NOT_STARTED` | 未実装 |
| `IN_PROGRESS` | 実装中 |
| `PARTIAL` | 一部実装。未対応の条件を明記 |
| `IMPLEMENTED` | 定義した範囲の受け入れ条件を証拠付きで満たした |
| `BLOCKED` | 依存関係や仕様確認で停止 |
| `NOT_APPLICABLE` | 宣言した対象範囲外。理由を残す |

| 再現精度 | 意味 |
| --- | --- |
| `EXACT` | 明示して試験した範囲の観測可能な契約を再現 |
| `LOCAL_SIMULATION` | 時刻・基盤・分析などをローカルのモデルで模擬 |
| `METADATA_ONLY` | 設定を保存・取得できるが効果は未実装 |
| `EXTERNAL` | 別サービスとの接続が必要 |
| `PROJECT` | Docker・CLIなどエミュレーター独自の要求 |
| `NONE` | 実装・検証前 |

「目指す再現精度」と「確認できた再現精度」を分けます。模擬機能のテストが通っても、Googleの基盤を厳密再現したことにはしません。

## 実装済みにする条件

1. 対象API・バージョン・公式仕様・確認日と、対応するパラメータ・ヘッダー・フィールドが明確である。
2. 正常系、異常系、境界値、該当する権限・他機能との組合せに受け入れ条件がある。
3. HTTP/gRPCの実際の入出力と、関係するSDKのテストが通る。基盤項目はCLI・Docker・資料の検証を行う。
4. 競合、再起動、クラッシュ、時刻、資源使用量に影響する場合は、それを検証する。
5. 実行コマンド・結果・成果物・SDKバージョンを記録し、差異を隠さない。
6. JSON台帳と英語/日本語資料を同じ変更で更新する。

エンドポイントが存在する、200が返る、フィールドを保存できる、認証を省略すれば動く、だけでは実装済みにしません。成功経路しかない場合は一部実装です。最初のコミットでは、まだ存在しない自身のコミットハッシュを捏造せず、検証成果物を記録して後から履歴と結びます。

## 表の更新方法

P0でRustの `xtask` を実装し、台帳検証と英語/日本語表の生成を行います。次は設計上のコマンドであり、この資料だけではまだ実行できません。

```sh
cargo xtask compatibility validate
cargo xtask compatibility render
cargo xtask compatibility check
```

ID重複、存在しない依存先、循環、状態の値、出典、実装済み行の証拠不足を検出し、生成表が古い場合はCIを失敗させます。メソッド・動作・フィールド・プロジェクト基盤の進捗は別々に表示します。

Googleの実環境を使う差分試験は明示的に有効化した場合だけ実行します。ローカルの結果だけでGoogleの課金、KMS、BigQuery、認証発行、地理冗長化まで再現したとしないことが、この台帳の重要なルールです。
